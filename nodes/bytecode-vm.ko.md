# 바이트코드 가상 머신

## 요약

바이트코드 가상 머신(virtual machine, VM)은 느린 트리 순회 [[interpreter]]와 완전한 네이티브 컴파일러 사이에 자리 잡은, 프로그램을 실행하는 2단계 방식이다. 먼저 컴파일러가 소스를 **바이트코드(bytecode)** — 작고 고정된 형식의 연산(오피코드 하나에 몇 개의 오퍼랜드)으로 이루어진, 새로 고안된 컴팩트한 명령어 집합 — 로 한 번 번역한다. 그 다음 VM 자신도 하나의 [[interpreter]]로서, "기계어"가 바로 그 바이트코드인 셈이며, 평평한 명령어 배열 위에서 촘촘한 페치-디코드-실행(fetch–decode–execute) 루프를 돈다. 명령어들이 균일하고 지저분한 소스로부터 미리 디코딩되어 있기 때문에, 디스패치는 매번 구문 구조를 다시 순회하는 것보다 훨씬 빠르면서도 프로그램은 이식성을 유지한다: VM을 갖춘 어떤 플랫폼에서도 같은 바이트코드를 실행할 수 있다. VM은 중간값을 담아 둘 곳이 필요한데, 여기에는 두 가지 고전적인 설계가 있다 — 오퍼랜드 [[stack]] 위에 오퍼랜드를 밀어 넣고 꺼내는 **스택 기반(stack-based)** 모델과, 고정된 가상 레지스터 배열의 슬롯에 이름을 붙이는 **레지스터 기반(register-based)** 모델이다.

## 상세 설명

**중심 대상과 바이트코드가 존재하는 이유.** 평범한 트리 순회 [[interpreter]]는 프로그램을 실행할 때 그 파싱된 구조를 반복해서 순회하며, 매 단계마다 각 노드가 무엇을 의미하는지 다시 판단한다. 그 재판단은 순전한 오버헤드로, 모든 구문이 실행될 때마다 매번 치러야 하는 비용이다. 바이트코드 VM은 *한 번만 컴파일함으로써* 이를 제거한다: 소스를 작고 균일한 명령어들의 선형 시퀀스 — 바이트코드 — 로 낮추고, 이후 실행은 배열에 대한 단순한 루프가 된다. VM은 여전히 하나의 [[interpreter]]다 — 페치하고, 디코드하고, 실행한다 — 그러나 그 명령어들은 이제 평평하고 규칙적이므로 디코딩이 값싸고 루프가 빠르다. "가상 머신"이라는 이름은, 바이트코드가 실제 CPU를 겨냥하는 대신 VM이 소프트웨어로 흉내 내는 *고안된* 프로세서(자신만의 명령어 집합과 오퍼랜드 모델을 가진)를 겨냥한다는 발상을 가리킨다.

**오퍼랜드 모델 — 중간값이 어디로 가는가.** "더하기" 같은 명령어에는 오퍼랜드와 결과를 놓을 자리가 필요하다. 두 가지 설계가 지배적이다. **스택 기반** VM은 오퍼랜드 [[stack]]을 유지한다: 대부분의 명령어가 이를 밀어 넣거나(push) 꺼내므로(pop), `ADD`는 맨 위 두 값을 꺼내 그 합을 밀어 넣는다. 스택 머신용 바이트코드는 매우 컴팩트하지만(오퍼랜드가 암묵적이다 — "[[stack]]의 맨 위") 하나의 계산에 많은 작은 명령어가 필요하다. **레지스터 기반** VM은 대신 명령어에 고정된 가상 레지스터 배열의 슬롯을 가리키는 명시적 오퍼랜드를 부여하므로, `ADD R3, R1, R2`는 한 명령어로 "R3 ← R1 + R2"를 의미한다; 이는 더 적지만 더 두꺼운 명령어를 사용하며, 명령어가 커지는 대가로 더 빠른 경향이 있다(Lua의 VM이 유명한 레지스터 기반 설계다). 별도로, 함수 호출과 반환은 프레임들의 호출 [[stack]] 위에서 추적된다 — 가장 최근에 호출된 함수가 항상 가장 먼저 반환되므로, 후입선출(last-in-first-out) [[stack]] 규율을 직접 활용하는 사례다.

**구체적인 예시.** 식 `3 + 4 * 2`(곱셈이 덧셈보다 우선순위가 높다)를 **스택 기반** VM용으로 컴파일하면:

```
PUSH 3      ; operand stack: [3]
PUSH 4      ; [3, 4]
PUSH 2      ; [3, 4, 2]
MUL         ; pop 4,2 → push 8   → [3, 8]
ADD         ; pop 3,8 → push 11  → [11]
```

오퍼랜드 [[stack]]을 오른쪽 끝을 맨 위로 두고 추적해 보자: `[3, 4, 2]`로 늘어난 뒤, `MUL`이 맨 위 두 개를 `8`로 접고, 다시 `ADD`가 접어서 최종적으로 `11`이 되어 [[stack]]에 결과로 홀로 남는다. 명령어의 *순서*가 우선순위를 인코딩한다 — `MUL`이 `ADD`보다 먼저 방출되어 `4`와 `2`를 먼저 소비한다 — 이것이 이 예시가 비퇴화적인 이유다: 단순한 `3 + 4`였다면 [[stack]] 규율이 중요해지는 그 순서 관계를 전혀 드러내지 못했을 것이다. 같은 계산을 **레지스터 기반** VM에서 하면 더 짧다 — `MUL R1, 4, 2` 다음 `ADD R0, 3, R1` — 다섯 개가 아니라 두 개의 명령어이며, 이는 두 오퍼랜드 모델 사이의 컴팩트함 대 명령어 개수의 트레이드오프를 보여준다.
