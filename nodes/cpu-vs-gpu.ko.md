# CPU와 GPU

## 의미

CPU와 GPU는 모두 프로그램을 실행하지만 하드웨어 자원을 배분하는 방식이 다르다. CPU는 소수의 유연한 명령 흐름을 낮은 지연시간으로 처리하는 데, GPU는 규칙적인 병렬 작업을 높은 총처리량으로 실행하는 데 중점을 둔다. 둘 다 [[memory-hierarchy]]에 의존하며 어느 쪽도 항상 더 빠르지는 않다. 이는 설계 경향이지 모든 프로세서와 프로그램에 적용되는 절대 규칙이 아니다.

## 동작 원리

CPU 코어는 독립적인 명령 흐름을 실행하며 캐시, 분기 예측, 비순차 실행 같은 장치로 정체를 줄인다. CPU도 벡터 명령과 여러 스레드를 실행하므로 단순히 순차적이라고 부르면 비교의 중요한 부분을 놓친다.

GPU는 산술 연산과 다수의 실행 문맥 유지에 많은 자원을 쓴다. 한 문맥이 기다릴 때 스케줄러는 다른 준비된 문맥을 선택할 수 있다. 충분한 독립 작업과 상주 자원이 있을 때에만 일부 지연시간을 숨길 수 있다. 의존성, 데이터 대기, 동기화, 저장 공간 부족 때문에 실행할 작업이 없을 수도 있다. GPU에도 캐시가 있으므로 지연시간 감내와 메모리 왕복 회피는 상호 배타적 전략이 아니다.

광고에 표시되는 CUDA 코어 수는 CPU처럼 독립적으로 실행하는 프로세서의 수가 아니다. 물리적 산술 레인, 스레드 스케줄링 자원, 소프트웨어 실행 문맥은 서로 다르다. 레인 하나가 CPU 코어 하나보다 일정 배수만큼 약하다는 보편적 환산은 없다. 실제 비교는 명령, 정밀도, 클럭, 활용도, 데이터 이동에 달려 있다.

핵심은 **시작 요청된 작업과 상주 작업**의 구분이다. 애플리케이션이 논리적 스레드 실행 백만 개를 지정해도 백만 개가 동시에 칩에 적재되는 것은 아니다. 레지스터, 공유 저장 공간, 장치 제한이 동시에 상주할 수 있는 수를 제한한다. 나머지는 자원이 확보될 때 실행한다. 논리적 스레드는 특정 물리적 레인에 영구 배정된 대상이 아니다.

## 구체 사례

원소가 각각 백만 개인 배열 두 개를 더해 세 번째 배열에 저장하자. 원소당 4바이트라면 유효한 스트리밍 트래픽은 읽기 두 번과 쓰기 한 번이다. 1,000,000 * (4+4+4) = 12,000,000바이트, 십진 단위로 12 MB다. 추가 트래픽, 캐시 효과, 메모리 할당은 제외한 값이다.

가상 실행 경로가 실제로 120 GB/s를 유지한다면 이동 시간의 하한은 12,000,000 / 120,000,000,000초 = 100마이크로초다. 실제 유지 대역폭을 1.2 TB/s로 가정하면 하한은 10마이크로초다. 이는 가정한 측정 대역폭으로 계산한 이동 시간 하한이지 CPU/GPU 벤치마크의 보장이 아니다. 작은 작업에서는 시작 비용, 호스트-장치 복사, 동기화 때문에 유리한 쪽이 바뀔 수 있다. 입력과 출력을 장치에 유지하면 조건도 달라진다.

CPU 구현은 원소를 작업자에게 나누고 각 작업자의 루프를 벡터화할 수 있다. GPU 구현은 원소마다 논리적 스레드를 지정하고 일부씩 상주시켜 실행할 수 있다. 둘 다 같은 독립성을 활용하되 실행 자원과 이동 비용이 다르다. 반대로 단일 파싱 흐름처럼 다음 동작이 이전 결과를 기다리는 작업에는 산술 레인을 늘리는 것만으로 병렬성이 생기지 않는다. 독립적인 여러 파싱 흐름을 묶으면 그것은 또 다른 작업 부하다.

## 검증과 대안

같은 출력 조건에서 전체 경로를 비교한다. 입력 크기, 숫자 형식, 데이터 위치, 동시성, 전송 포함 여부를 명시한다. 코어 수에서 속도를 추론하지 말고 측정한다. 준비 비용과 정상 상태를 분리하고 메모리 트래픽과 독립 작업의 양을 확인한다. 관측 결과에 따라 CPU, GPU, 혼합 설계를 선택한다. 작은 제어 의존 작업은 CPU에 두고 큰 규칙적 구간만 GPU에서 실행하는 편이 모든 연산을 오프로딩하는 것보다 나을 수 있다.

## 이해 확인

스레드 백만 개를 지정하면 백만 개가 상주하는가? 아니다. 논리적 작업, 상주 실행 상태, 물리적 레인은 서로 다르며 장치 자원 제한이 상주 수를 결정한다.
