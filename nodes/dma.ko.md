# 직접 메모리 접근

## 요약

디스크, 네트워크 카드, GPU와 같은 장치가 메인 메모리([[memory-hierarchy]]의 RAM 단)로 데이터 블록을 옮겨 넣거나 옮겨 내야 할 때, 이를 수행하는 방법에는 두 가지가 있다. 순진한 방식은 프로세서(프로그램의 명령을 실행하는 칩인 CPU)로 하여금 모든 바이트를 직접 나르게 하는 것이다: 장치로부터 바이트 하나를 읽고, 그것을 메모리에 쓰고, 반복 — 1메가바이트를 옮기는 데 백만 번을. **직접 메모리 접근(Direct Memory Access, DMA)**은 그 대안이다: 별도의 하드웨어 조각 — 전형적으로 장치 자신의 컨트롤러 안에 내장된 *DMA 엔진* — 이 **CPU가 어떤 바이트도 건드리지 않은 채 장치와 메모리 사이를 직접** 대량으로 옮긴다. CPU가 할 일은 오직 전송을 미리 *프로그래밍*하는 것뿐이다(이를테면 어디서 읽어서 어디에 쓸지, 몇 바이트를 옮길지). 그 후에는 CPU는 자리를 뜨고 다른 작업을 실행한다; 옮기기가 끝나면, 엔진은 "완료"를 알리기 위해 CPU가 무엇을 하고 있든 그것을 선점하여 커널 핸들러로 강제 진입시키는 하드웨어 신호인 **[[interrupt]]**를 발생시킨다. 그 이유는 [[memory-hierarchy]]에서 곧바로 나오는 경제학적 논증이다: CPU는 희소하고, 비싸고, 빠른 자원이며, 그것의 사이클을 바이트를 한 번에 하나씩 실어 나르는 데 쓰는 것은 낭비다; DMA는 그 지루한 일을 저렴한 전용 하드웨어에게 위임함으로써 CPU가 배달 트럭 노릇을 하는 대신 계산을 할 수 있게 해준다. DMA는 빠른 디스크 I/O, 네트워킹, CPU↔GPU 전송의 밑바탕에 있는 기본 요소다.

## 상세 설명

### DMA가 대체하는 기준선: CPU가 손으로 바이트를 옮긴다 (프로그램 I/O)

DMA가 *무엇인지* 보려면, 먼저 그것이 무엇을 제거하는지 보라. 가장 근본적인 수준에서 CPU는 **이동 명령(move instruction)**(x86에서는 문자 그대로 `MOV`라 불린다)을 실행함으로써 데이터를 옮긴다: CPU는 칩과 RAM을 연결하는 물리적 배선인 **메모리 버스(memory bus)**에 주소를 올려놓고, 그곳에 저장된 워드를 읽거나 그곳에 워드를 쓴다. (여기서 "워드"란 그저 CPU가 한 번에 옮기는 고정 크기 덩어리 — 몇 바이트 — 를 뜻한다.) 디스크 컨트롤러 같은 장치는 CPU가 메모리 주소처럼 읽을 수 있는, 장치 위의 이름 붙은 저장 슬롯인 작은 **레지스터**를 통해 자신의 데이터를 노출한다. 그래서 디스크에서 데이터를 손으로 끌어오는 방식인 **프로그램 I/O(programmed I/O)**는 하나의 루프다: CPU는 디스크 컨트롤러의 레지스터로부터 워드 하나를 자신 안으로 읽어들이고, 그 워드를 다시 RAM으로 써내고, 반복한다. 1기가바이트 파일이라면 이는 대략 10억 번의 읽고-쓰는 단계에 해당하며, 그 매 순간 CPU는 완전히 점유되어 있다. CPU는 다른 프로그램을 실행할 수 없다; CPU는 상자를 한 번에 하나씩 나르는 배달원이다. 그것이 바로 DMA가 존재하여 없애려는 낭비다.

### DMA란 *무엇인가*: 대량 이동을 전용 엔진에게 위임하기

DMA는 나르는 것을 **위임하는 것**으로 대체한다. 장치의 컨트롤러는 CPU가 하는 것과 정확히 똑같이, 하지만 자율적으로 메모리 버스에 주소를 올리고 RAM에 쓰거나(또는 읽을) 수 있는 자신만의 작은 회로 — **DMA 엔진(DMA engine)** — 를 담고 있다. CPU는 더 이상 바이트를 옮기지 않는다; CPU는 그저 명령을 내릴 뿐이다. 구체적으로 CPU는 다음을 말하는 몇 개의 값 — **전송 서술자(transfer descriptor)** — 을 컨트롤러에 써넣는다:

- **원본(source)** — 바이트들이 어디서 오는지(예: 어느 디스크 블록들인지),
- **대상 주소(destination address)** — RAM의 어디에 그것들을 둘지,
- **길이(length)** — 몇 바이트를 옮길지.

그런 다음 CPU는 "실행" 비트를 설정하고 다른 프로세스를 실행하러 자리를 뜬다. DMA 엔진은 전체 블록 — 킬로바이트, 메가바이트, 기가바이트 — 을 장치와 RAM 사이에서 CPU 관여 없이 바이트 단위로 스트리밍한다. 마지막 바이트가 안착하면, 엔진은 **인터럽트**를 발생시킨다: CPU가 무엇을 하고 있든 그것을 중단시키고 짧은 *핸들러* 루틴으로 뛰어들게 만드는 전용 회선 위의 전기 신호로, 여기서는 그저 "네가 요청한 데이터가 이제 RAM에 있다"고 알린다. 그러므로 DMA를 정의하는 구조는 노동의 분할이다: CPU는 전송이 아무리 크든 작고 일정한 양의 *설정(setup)* 작업만 하고, 엔진은 CPU의 다른 계산과 병렬로 모든 바이트 단위 *이동(movement)* 작업을 한다.

### 왜 작동하는가: 희소한 빠른 자원을 대량 이동에 쓰지 마라

그 근거는 [[memory-hierarchy]]의 핵심 교훈이다: CPU는 빠르고 희소한 자원이고, 큰 바이트 블록을 옮기는 것은 느리고 대역폭에 제약받는 잡일이다. CPU가 `MOV` 루프로 그 잡일을 수행하면, 두 가지 나쁜 일이 일어난다. 첫째, 유용한 산술을 할 수도 있었을 CPU의 사이클이 전적으로 복사에 소진된다. 둘째, 더 미묘하게, 1메가바이트를 CPU를 통해 끌고 가는 것은 그것을 CPU의 작고 빠른 캐시([[memory-hierarchy]]의 상위 단들)를 통해서도 끌고 간다는 뜻이다: 한 번 쓰이고 다시는 쓰이지 않는 그 스트리밍된 데이터가 CPU가 작업 중이던 진짜로 뜨거운 데이터를 *축출*해버려서, 복사가 끝난 뒤에도 프로그램은 더 느리게 실행된다. 이것이 **캐시 오염(cache pollution)**이다. DMA는 이 둘 다를 피한다: 바이트는 CPU나 그 캐시를 결코 거치지 않는 경로(장치 → 메모리 버스 → RAM)를 흐르므로, 엔진은 메모리 대역폭 속도로 블록을 옮기는 동안 CPU의 빠른 단들은 *CPU 자신의* 작업 집합으로 가득 찬 채 남아있는다. DMA가 유지하는 불변식은 CPU의 관여가 전송 크기에 대해 **O(1)**이라는 것 — 고정된 서술자 설정에 인터럽트 하나 — 이지 O(바이트 수)가 아니라는 것이다. 대량 이동은 오직 대량 이동만이 임무인 하드웨어에게 넘겨지며; 비싼 범용 칩은 오직 자신만이 할 수 있는 일을 위해 자유로워진다.

### 구체적 사례: 디스크에서 4KB를 읽는 두 가지 방법

구체적이고 퇴화하지 않은 전송을 들어보자: 디스크로부터 **4킬로바이트**(4096바이트)를 RAM 주소 `X`로 읽는다. CPU가 `MOV`당 8바이트를 옮기고 초당 30억 사이클로 실행된다고 하자.

**프로그램 I/O (기준선).** 4096바이트를 8바이트씩 옮기는 것은 `4096 ÷ 8 = 512`번의 루프 반복이며, 각 반복은 최소한 장치 레지스터로부터의 읽기와 RAM으로의 쓰기 — 몇 사이클이라 치자 — 이지만, 디스크가 느리기 때문에 장치 읽기 하나만으로도 CPU를 훨씬 더 오래 정체시킨다. 정체를 무시하더라도, CPU는 대략 천 개 정도의 명령을 실행하며 그 읽기 전체 시간 동안 *다른 어떤 일에도 쓸 수 없다.* 4KB 블록 하나라면 견딜 만하지만, 실제 I/O에서 이를 수백만 개의 블록으로 곱하면 CPU는 복사 말고는 아무것도 하지 못한다.

**DMA.** 대신 CPU는 서술자를 쓴다 — 원본 = 그 4KB를 담고 있는 디스크 블록들, 대상 = RAM 주소 `X`, 길이 = 4096 — 그리고 실행 비트를 설정한다. 이는 몇 개의 레지스터 쓰기, 아마도 수십 사이클로, *4096과 무관하다.* 그런 다음 CPU는 다른 프로그램을 실행하러 돌아간다. 디스크 컨트롤러의 DMA 엔진은 플래터나 플래시로부터 4KB를 읽어 곧바로 RAM의 `X`로 스트리밍한다. 4096번째 바이트가 쓰이면, 엔진은 인터럽트를 발생시킨다; CPU는 잠깐 자신의 핸들러로 들어가서 블록이 준비되었음을 알고 다시 진행한다. 결정적인 대비는 이렇다: 프로그램 I/O에서는 *4096*이 CPU가 직접 갈아야 하는 루프 카운트로 나타나는 반면, DMA에서는 *4096*은 그저 CPU가 넘겨주는 숫자일 뿐이다 — 그것은 CPU의 명령 스트림에 전혀 나타나지 않는다. 블록을 4KB에서 4GB로 늘려보면 DMA 하에서 CPU의 비용은 거의 변하지 않지만(같은 서술자, 같은 하나의 인터럽트), 프로그램 I/O 하에서는 백만 배로 늘어난다. 그 평평한 비용이야말로 요점 전부다.

### 스캐터-개더: 연속되지 않은 여러 버퍼에 걸친 하나의 전송

위의 기본 서술자는 대상이 하나의 연속된 RAM 구간이라고 가정한다. 현실은 더 지저분하다: 파일의 블록들은 디스크 여기저기에 흩어져 있을 수 있고, 그것들을 받는 RAM 페이지들도 전형적으로 물리 메모리 여기저기에 흩어져 있다(운영체제가 하나의 긴 구간이 아니라, 공간이 있는 아무 곳에나 놓인 고정 크기 *페이지*로 메모리를 나눠주기 때문이다). 각각의 작은 조각마다 — 자신만의 설정과 자신만의 완료 인터럽트를 가진 — 별도의 DMA를 발행하는 것은 CPU 절감분의 상당 부분을 도로 갉아먹을 것이다.

**스캐터-개더 DMA(scatter-gather DMA)**가 이를 해결한다. 하나의 원본/대상/길이 삼중항 대신, CPU는 RAM에 **스캐터-개더 목록** — 조각마다 하나씩인 그러한 항목들의 배열 — 을 만든다: "이것을 여기서 읽어서, RAM `0x10000`에 4KB를 놓아라; 저것을 읽어서, `0x85000`에 4KB를 놓아라; 그다음 것을 읽어서, `0x200000`에 8KB를 놓아라; …끝." 그런 다음 CPU는 그 목록에 대한 단일 포인터와 하나의 "실행"으로 엔진을 프로그래밍한다. 엔진은 그 목록을 항목별로 스스로 순회하며, 각 덩어리를 자신만의 주소에 놓고 — 읽기에서는 조각들을 *모으고(gathering)*, 쓰기에서는 그것들을 *흩뿌리며(scattering)* — 전체 목록이 끝나면 오직 **하나**의 인터럽트만 발생시킨다. 그러므로 하나의 위임된 명령이 연속되지 않은 버퍼들의 더미 전체를 옮기며, CPU의 관여는 여전히 O(1)이다: 목록을 만들고, 그것을 가리키고, 인터럽트 하나를 받는다. 현대의 NVMe SSD는 명령 하나당 수천 개의 스캐터-개더 항목을 처리하며, CPU가 다른 일을 하는 동안 수 기가바이트의 조각난 데이터를 옮긴다 — 이것이 바로 현대의 I/O가 빠른 이유다: CPU는 실제 이동에 거의 참여하지 않는다.

### 어디에서 나타나는가

같은 위임-프로그래밍-그리고-인터럽트받기 패턴은 장치와 [[memory-hierarchy]]의 RAM 단 사이에서 데이터가 넘나드는 모든 곳에서 반복된다. 디스크 읽기는 블록들을 메모리로 DMA한다. 네트워크 카드는 도착하는 패킷을 RAM으로 DMA하고 그것을 처리하도록 CPU에게 인터럽트를 걸며, 나가는 패킷을 RAM에서 회선으로 DMA한다. GPU 전송은 DMA 엔진을 프로그래밍하여 버퍼를 호스트 RAM으로부터 링크를 건너 GPU 자신의 메모리로 스트리밍한다(그리고 그 반대도). 각 경우마다 CPU의 역할은 *바이트를 옮기는 것*에서 *하드웨어에게 바이트를 옮기라고 말하는 것*으로 옮겨갔다 — 이것이 정확히 [[memory-hierarchy]]가 우리에게 아끼라고 가르친 희소하고 빠른 자원을 자유롭게 해주는 것이다.
