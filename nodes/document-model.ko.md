# 문서 데이터 모델

## 요약

**문서 데이터 모델**은 각 레코드를 **문서**로 저장한다: 자기 완결적이고 중첩된 키-값
쌍의 트리로, 실제로는 JSON으로 작성된다. [[relational-model]]과 대비되는 두 가지
선택이 이 모델을 정의한다. 첫째, **값이 구조를 가질 수 있다**: 관계형 컬럼이 평평한
타입 값을 담는 곳에서, 문서 필드는 또 다른 문서나 그 배열을 담을 수 있어서, 레코드가
자신에게 속한 데이터를 *내장(embed)*할 수 있다 — 일대다 관계가 읽기 시점에 다시
조인되는 별도 테이블이 아니라 레코드 *내부에* 존재한다. 둘째, 스키마가 **테이블
단위가 아니라 문서 단위**다: 같은 컬렉션 안의 두 문서가 서로 다른 필드를 가질 수
있으므로, 데이터의 형태는 데이터베이스가 쓰기 시점에 강제하는 것이 아니라 애플리케이션이
읽기 시점에 강제한다("스키마-온-리드"). 그 대가로 얻는 것은 **지역성(locality)과
유연성**이다 — 레코드와 그 하위 레코드가 한 번의 조회로 도착하고, 테이블 마이그레이션
없이 형태가 진화할 수 있다. 그 값은 관계형 모델의 강점의 거울상이다: 내장된 데이터는
*반대 방향에서* 도달하기 어렵고(다대다 관계와 레코드 간 질의는 조인 메커니즘을
잃는다), 중복된 내장 데이터는 애플리케이션이 직접 일관성을 유지해야 한다.

## 상세 설명

### 문서는 키-값 쌍의 트리다

[[key-value]] 매핑에서 시작하자: 고유한 키를 가진 (키, 값) 쌍의 집합으로, 키의
내용으로 접근한다. **문서**는 이 매핑을 **재귀적으로** 만든 것이다 — 각 값은 스칼라일
수도, 배열일 수도, *또는 또 다른 키-값 매핑*일 수도 있다. 따라서 문서는 유한한
트리다: 내부 노드는 키-값 매핑이고, 잎은 스칼라다. JSON으로 작성하면 다음과 같다.

```json
{
  "_id": 7,
  "title": "Why B-trees are wide",
  "author": { "name": "alice", "joined": "2024-01-10" },
  "tags": ["storage", "trees"],
  "comments": [
    { "who": "ada",  "text": "nice worked example" },
    { "who": "alan", "text": "what about LSM trees?" }
  ]
}
```

하나의 최상위 키(`_id`)가 문서를 식별한다. [[key-value]] 매핑에서 키가 쌍을
식별하는 것과 정확히 같다; 나머지 모든 것은 중첩 구조로 그 위에 매달려 있다.
데이터베이스는 *키로 문서 전체*를 저장하고 조회한다 — [[key-value]]의 연관 배열식
인터페이스 — 그러면서 값이 중첩된 레코드 전체를 담도록 허용한다. (MongoDB에서 이
트리의 구체적인 전송·디스크 인코딩은 **BSON** — "이진 JSON" — 인데, 날짜나 이진
블롭 같은 타입을 추가하고 빠른 순회를 위해 각 요소에 길이 접두사를 붙인다 — 하지만
이 인코딩은 구현 세부사항일 뿐이며, *모델*은 트리다.)

### 결정적인 대조 — 내장(embedding) vs. 정규화(normalizing)

[[relational-model]]이라면 같은 블로그 글을 **세 개의 릴레이션**으로 표현했을
것이다: `posts` 테이블, `authors` 테이블, `comments` 테이블 — 각각 타입이 있는
컬럼에 대한 평평한 튜플의 집합이며, `comments.post_id`는 `posts._id`를 참조하는
외래 키다. 행은 오직 평평한 값만 담으므로, 일대다 관계인 "글이 댓글을 가진다"는
반드시 테이블 *사이*에 존재해야 하고, 글과 그 댓글을 함께 읽으려면 **조인**이
필요하다 — 애플리케이션이 하나의 객체로 여기는 것을 데이터베이스가 질의 시점에
재조립하는 것이다.

문서 모델은 반대 선택을 한다: 댓글은 글 문서 자체에 **내장**된다. 이것이 모델의
핵심적인 트레이드오프다.

- **지역성이 이긴다.** "글 페이지 보여주기" — 지배적인 접근 패턴 — 는 `_id`로 문서
  *하나*를 조회한다: 저자 스냅샷, 태그, 댓글이 함께 도착하며, 조인도 없고 두 번째
  조회도 없다. 레코드의 트리 구조가 곧 페이지의 구조다.
- **반대 방향은 진다.** "alan이 지금까지 쓴 모든 댓글을 모든 글에 걸쳐 나열하라"는
  관계형 형태에서는 단일 테이블 스캔(또는 인덱스 조회)이었지만, 문서 형태에서는
  alan의 댓글이 여러 글 문서 안에 흩어져 있으므로, 질의는 모든 글의 `comments`
  배열 *안으로* 파고들어야 한다. 다대다 관계(한 댓글 작성자가 수천 개의 글에
  등장하는 경우)는 각 문서에 데이터를 복제하거나 — 애플리케이션이 직접 일관성을
  유지해야 하는 복사본으로, 관계형 모델의 외래 키와 조인이 대신 해주던 일을 손으로
  하는 것 — 참조를 저장하고 애플리케이션 코드에서 조인하는 방식으로 후퇴한다.

**스키마 유연성**도 같은 선택에서 따라 나온다. 릴레이션은 *모든* 튜플에 대해 하나의
컬럼 집합을 고정하지만, 문서의 컬렉션은 아무것도 고정하지 않는다 — 다음 글 문서는
`"video"` 필드를 추가하거나 `"tags"`를 완전히 생략할 수 있으며, 데이터베이스는
이를 받아들인다. 이는 레코드 형태의 진화를 저렴하게 만들고(테이블 마이그레이션이
없다), "이 레코드는 어떤 필드를 가지는가?"라는 부담을 데이터베이스의 스키마에서
애플리케이션의 읽기 코드로 옮긴다.

### 각 모델이 적합한 경우

이 결정 규칙은 위의 트레이드오프에서 직접 나온다. **트리**인 데이터 — 레코드가
하위 레코드를 소유하고, 함께 읽고 쓰는 경우(글과 그 댓글, 주문과 그 항목들) — 는
문서에 적합하다: 내장은 한 번의 조회로 얻는 지역성과 레코드별 스키마 자유를
제공한다. **웹**인 데이터 — 모든 방향에서 질의되는 다대다 관계(학생 × 강좌,
부품 × 공급업체) — 는 [[relational-model]]에 적합하다: 정규화된 테이블과 조인이
데이터를 중복시키지 않고도 *어떤* 방향의 질문에도 답할 수 있다. 문서 데이터베이스가
존재하는 이유는 많은 종류의 애플리케이션이 트리 형태를 띠기 때문이며, 관계형
모델이 지속되는 이유는 웹이 결코 사라지지 않았기 때문이다.

## 선행 개념

- [[key-value]] — 문서가 그로부터 만들어지는 원자: 고유한 키를 값에 매핑하며
  연관적인 get/set/delete를 지원하는 매핑; 문서는 이 매핑을 재귀적으로 만든 것이고
  (값이 매핑일 수 있다), 컬렉션은 최상위 수준에서 키-값이다(`_id` → 문서).
- [[relational-model]] — 이 모델을 정의하는 대조: 정규화된 릴레이션에 담긴 평평한
  타입 튜플이 외래 키로 테이블 사이를 연결되고 조인으로 재조립된다 — 이것이 바로
  내장이 지역성과 스키마 유연성을 위해 포기하는 메커니즘이다.
