# 가비지 컬렉션

## 요약

가비지 컬렉션(garbage collection, GC)은 자동 메모리 관리다: 프로그래머가 다 쓴 객체를 하나하나 명시적으로 해제하는 대신, 언어 런타임이 주기적으로 어떤 객체가 아직 *도달 가능*(reachable)한지 알아내고 나머지의 메모리를 회수한다. 핵심 통찰은, 실행 중인 프로그램이 참조를 따라가서 여전히 도달할 수 있는 객체만이 여전히 필요하다는 것이다 — 그래서 런타임은 살아 있는 모든 객체와 그 사이의 참조를 유향 [[graph]]로 모델링하고, **루트**(root, 전역 변수와 현재 실행 중인 함수들의 지역 변수)로부터 어떤 노드에 도달할 수 있는지를 묻는다. 순회가 도달하지 못한 것은 다시는 이름으로 지칭될 수 없으므로, 그것을 해제하는 것은 증명 가능하게 안전하다. 이로써 누수, 이중 해제, 허상 참조(dangling reference)라는 버그 부류 전체가 제거된다 — 런타임이 객체 [[graph]]를 추적하는 데 시간을 쓰고, 그 추적이 유발할 수 있는 수집 일시 정지(pause)를 감수하는 대가로.

## 상세 설명

**GC가 푸는 문제.** 프로그램은 실행하면서 객체를 할당하고, 언젠가는 그 메모리를 반드시 해제해야 한다. 그러지 않으면 메모리가 가득 찬다. 이를 수작업으로 하는 것은 악명 높게 오류가 잦다: 너무 늦게(또는 영영) 해제하면 메모리가 누수되고; 너무 일찍 해제하면 이후의 사용이 *허상 참조*가 되며; 두 번 해제하면 할당자를 망가뜨린다. 가비지 컬렉션은 대신 런타임에게 책임을 지운다. 이는 *필요*에 관한 단 하나의 관찰에 근거한다: 프로그램은 여전히 **도달할** 수 있는 객체만 — 루트에서 출발해 참조의 사슬을 따라가 다다를 수 있는 객체만 — 사용할 수 있다. 아무것도 도달할 수 없는 객체는 무력하다; 미래의 어떤 명령도 그것을 언급할 수 없으므로, 그것을 회수해도 프로그램이 관찰할 수 있는 것은 아무것도 변하지 않는다. GC의 정확성은 정확히 이 논증이다.

**도달 가능성은 [[graph]] 순회다.** 상황을 유향 [[graph]]로 모델링하자: 살아 있는 각 객체가 노드이고, 객체 *A*가 객체 *B*에 대한 참조를 들고 있을 때마다 *A*에서 *B*로 간선이 놓인다. **루트**는 지금 이 순간 프로그램이 직접 접근할 수 있는 진입점 — 전역 변수와 현재 실행 중인 함수들의 지역 변수 — 이다. "어떤 객체가 아직 필요한가?"는 고전적인 [[graph]] 질문 "루트에서 어떤 노드에 도달할 수 있는가?"가 되고, 이는 루트에서 간선을 따라가며 닿는 모든 것을 방문하는 순회로 답한다. **마크 앤 스위프**(mark-and-sweep) 컬렉터는 정확히 이것을 두 단계로 수행한다: (1) *마크*(mark) — 루트에서 객체 [[graph]]를 순회하며 도달하는 모든 노드에 표시를 남긴다; (2) *스위프*(sweep) — 할당된 객체 전체를 훑으며 표시되지 **않은** 것을 모두 해제한다. 표시됨 = 도달 가능 = 유지; 표시 안 됨 = 도달 불가 = 가비지.

**구체적인 작동 예시.** 객체가 `A, B, C, D` 네 개 있고, 단 하나의 루트 변수가 `A`를 참조한다고 하자. 참조 관계는 `A → B`, `B → C`이고, `D`는 아무것도 참조하지 않으며 아무에게도 참조되지 않는다(마지막 들어오는 참조가 방금 끊어졌다).

- **마크**: 루트에서 시작해 `A`를 방문(표시), `A → B`를 따라가 `B`를 표시, `B → C`를 따라가 `C`를 표시. `D`에는 결코 도달하지 않는다.
- **스위프**: `A`, `B`, `C`는 표시됨 → 유지; `D`는 표시 안 됨 → 해제.

이제 프로그램이 `A`의 참조를 덮어써서 간선 `A → B`가 사라지고, 컬렉터가 다시 실행된다고 하자:

- **마크**: 루트에서 `A`만 방문한다. `B`와 `C`는 더 이상 도달 불가능하다 — *간선 `B → C`가 여전히 존재함에도*, 아무것도 `B`에 닿지 못하므로 `B → C` 클러스터 전체가 죽은 것이다.
- **스위프**: `A`는 유지; `B`와 `C`는 해제.

두 번째 라운드가 퇴화하지 않은(non-degenerate) 부분이다: 루트에서 클러스터에 아무것도 닿지 않는다면 내부 참조(`B → C`)가 객체를 살려두지 **못한다**는 것 — 단순히 "무언가에게 참조되고 있음"이 아니라 도달 가능성이야말로 중요한 기준임 — 을 보여준다. (더 단순한 방식인 *참조 카운팅*(reference counting)은 객체마다 들어오는 참조의 개수를 세어 0이 되면 해제한다; 더 저렴하지만, 서로를 참조하면서도 루트에서는 도달할 수 없는 객체들의 순환(cycle)은 회수하지 못한다 — 바로 추적(tracing) 방식 수집이 처리하는 경우다.)
