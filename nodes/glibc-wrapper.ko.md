# glibc 래퍼

## 요약

프로그램은 거의 날것의 [[system-call]]을 직접 호출하지 않는다. 대신 `read()`, `write()`,
`open()` 같은 평범한 C 라이브러리 함수를 호출하며, **glibc 래퍼(glibc wrapper)**가 그
친근한 함수 호출을 순수한 커널 요청으로 바꾸는 궂은일을 대신한다. **glibc**는 GNU C
라이브러리(GNU C Library)로, 대부분의 리눅스 시스템에 함께 딸려 오는 완제품 함수들의
모음이며, 각 커널 서비스마다 이런 **래퍼 함수(wrapper function)** 하나씩을 노출한다.
래퍼는 네 가지 일을 한다. (1) 평범한 C 인자를 받고; (2) **시스템콜 번호(syscall
number)**와 그 인자들을 커널이 기대하는 정확한 CPU **레지스터(register)**에, 합의된
**호출 규약(calling convention)**을 따라 적재하고; (3) [[system-call]]을 수행하는 단
하나의 트랩 명령을 실행하며(그 부분은 해당 선행 개념이 담당한다); (4) 커널의 날것
응답을 C 프로그래머가 기대하는 관례로 번역한다 — 음수로 도착하는 커널 오류를, 반환값
`-1`과 전역 오류 변수 `errno`로 바꾸는 것이다. 래퍼가 존재하는 이유는 기계 종속적인
날것의 커널 인터페이스 위에 이식 가능하고 인체공학적이며 아키텍처에 독립적인 표면을
씌우고, glibc가 버퍼링 등의 편의 기능을 덧붙일 자리를 마련하기 위해서다. 모두가 이를
쓰는 것은 아니다: Go는 C 라이브러리 없이 커널과 직접 통신하고, **musl**은 glibc와
동일한 래핑 역할을 하는 더 작은 대안 라이브러리다.

## 상세 설명

### 이 개념이 무엇이고, 무엇이 아닌가

[[system-call]]로부터 우리는 사용자 모드 프로그램이 특권 있는 커널 서비스를 얻는
유일하게 승인된 방법을 알고 있다: 서비스를 지칭하는 정수인 작은 **시스템콜 번호**와
인자들을 이름 붙은 CPU **레지스터** — 프로세서 내부의 작은 저장 슬롯 — 에 적재하고,
커널로 넘어갔다가 결과를 레지스터에 담아 돌아오는 하나의 특별한 트랩 명령
(`syscall`)을 실행하는 것이다. 그 메커니즘이 선행 개념이며, 이 노드는 그것을 다시
유도하는 대신 그 위에 기댄다.

*여기서* 다루는 개념은 그 메커니즘 **위에** 올라앉아 프로그램과 그 메커니즘 사이에
거의 항상 끼어 있는 평범한 코드의 층이다. 실제 프로그램은 레지스터 값을 직접
조립하고 `syscall`을 발동시키지 않는다; 그들은 `read()` 같은 평범한 C 함수를
호출하고 라이브러리가 조립을 대신하게 한다. glibc 래퍼가 바로 그 함수다: 친근한
C 함수 호출을 커널의 호출 규약으로 **연결하는**, 비특권 모드에서 실행되는(커널
내부가 아닌) **사용자 공간(userspace)** 코드다. 그러므로 이 개념은 트랩
명령(그것은 문의 걸쇠이며, 선행 개념의 소유물이다)도 아니고 실제 작업을 수행하는
커널 핸들러도 아니다; 그것은 문의 프로그램 쪽에 있는, 중간의 번역자다.

이름에 대해 한마디. **glibc**는 *GNU C 라이브러리(GNU C Library)*의 줄임말이다 —
"GNU"는 그것이 나온 자유 소프트웨어 프로젝트의 이름이고, "C 라이브러리"는 모든
C 프로그램이 존재한다고 가정할 수 있는 표준 함수 묶음(출력을 위한 `printf`,
메모리를 얻기 위한 `malloc`, 파일을 위한 `open`/`read`/`write`)을 말한다. glibc는
대부분의 리눅스 배포판이 사용하는, 그 묶음의 구체적인 구현체다. **래퍼**는
일반적으로 다른 무언가에 대한 호출을 포장하는 것만이 유일한 임무인 얇은 함수를
말한다; glibc 래퍼는 하나의 커널 서비스에 대한 호출을 포장한다.

### 래퍼가 존재하는 이유

날것의 [[system-call]] 인터페이스는 의도적으로 헐벗어 있다: 그것은 시스템콜
번호와 특정 레지스터로 말하며, *어떤* 번호가 *어떤* 서비스를 뜻하는지, *어떤*
레지스터가 *어떤* 인자를 담는지는 CPU 아키텍처마다 다르다. 그 인터페이스를 직접
다루며 코드를 쓴다면 모든 프로그램이 아키텍처별 레지스터 조작을 내장하고 "write는
번호 1"이라는 것을 외워야 한다는 뜻이 된다. 래퍼는 그 모든 것을 단 하나의
이식 가능하고 인체공학적인 함수 뒤로 숨기기 위해 존재한다. 모든 기계에서 똑같이
`write(...)`를 호출하면 된다; glibc의 `write()` 사본이 그 지역의 번호와 레지스터
배치를 알고 있다. 이것이 첫 번째이자 주된 이유다: **기계 종속적인 날것의 인터페이스
위에 이식 가능하고 친근한 표면을 씌우는 것.**

두 번째 이유는 여러분이 제어하는 함수가 커널이 제공하지 않는 편의를 덧붙이기에
자연스러운 장소라는 것이다. 자주 등장하는 두 가지는 다음과 같다.

- **버퍼링(Buffering).** [[system-call]]은 공짜가 아니다 — 커널로 넘어갔다가
  돌아오는 각 왕복에는 실제 시간 비용이 든다 — 그래서 바이트 하나마다 하나씩
  수행하는 것은 낭비다. glibc의 출력 함수들은 그래서 메모리 내 **버퍼(buffer)**(임시
  저장 영역)를 유지하며, 여러 개의 작은 쓰기를 하나의 더 큰 커널 `write()`로
  **묶는다(batch)**. C 호출 `printf("hi")`는 그 자체로는 [[system-call]]을 수행하지
  않는다; `hi`를 glibc의 버퍼에 복사하고 반환한다. 버퍼가 가득 차거나 프로그램이
  그것을 비울 때에만 glibc는 누적된 바이트에 대해 실제 `write()` 하나를 수행한다.
- **POSIX 관례.** POSIX는 아래에서 설명하는 `-1`과 `errno` 오류 규약을 포함해,
  이 C 함수들이 어떻게 동작해야 하는지를 명시하는 이식 가능한 유닉스 표준이다.
  커널은 그 규약을 말하지 않는다; glibc가 그것으로 번역해 주므로 어디에서나 C
  코드가 그 규약에 의존할 수 있다.

### 래퍼가 수행하는 네 단계

대표적인 래퍼로 `write()`를 예로 들어 보자. 프로그램이 이를 호출하면 glibc의
`write()`는:

1. **평범한 C 인자를 받는다** — 열려 있는 파일을 가리키는 작은 정수인 파일
   디스크립터(여기서는 표준 출력을 위한 `1`), 바이트를 가리키는 포인터, 그리고
   길이.
2. **커널을 위해 마샬링한다(marshal).** write에 대한 **시스템콜 번호**를 커널이
   번호를 읽는 레지스터에, 그리고 세 인자를 커널이 인자를 읽는 레지스터에,
   양쪽이 같은 자리를 보도록 하는 아키텍처의 고정된 합의인 **호출 규약**에 정확히
   맞춰 배치한다. (64비트 리눅스에서는 번호가 `1`이고 레지스터는 번호를 위한
   `rax`, 인자를 위한 `rdi`, `rsi`, `rdx`다 — [[system-call]] 노드가 설명하는
   것과 같은 규약이다.)
3. **트랩을 발동한다.** [[system-call]]을 수행하는 단 하나의 `syscall` 명령을
   실행한다 — 커널로 넘어가 검증과 작업을 수행하고 레지스터에 결과를 담아
   돌아온다. 이 단계가 *바로* 선행 개념이다; 래퍼는 그것을 촉발할 뿐이다.
4. **결과를 다시 번역한다.** 커널의 반환 규약과 C의 반환 규약은 *다르며*, 그것을
   화해시키는 것이 래퍼의 대표적인 동작이다. 커널은 성공 시 음이 아닌 수를,
   오류 시 **음수**를 반환한다(예를 들어 "잘못된 파일 디스크립터"에 대해서는
   `-9`). 하지만 C 프로그래머는 성공 시 개수를, 실패 시 원인을 별도의 전역
   변수에 남긴 채 `-1`을 기대한다. 그래서 래퍼는 반환된 레지스터를 검사한다:
   음이 아니면 그 값을 그대로 반환하고; 음수면 그 음수의 절댓값을 **`errno`**
   ("오류 번호")라는 프로그램별 전역 변수에 저장하고 `-1`을 반환한다. 음수
   방식은 커널의 것이고; `errno`는 그 위에 얹힌 glibc 자체의 발명품이다.

### 하나의 실행 사례: `printf("hi")`를 끝까지 따라가기

한 가지 구체적인 호출을 실행하며 각 단계를 이전 단계로부터 유도해 보자.

1. **C 호출.** 프로그램이 `printf("hi")`를 실행한다. `printf`는 glibc의 서식
   있는 출력 함수다; 형식 문자열을 처리하고(여기서는 치환할 것이 없으므로
   출력은 그저 두 글자 `h`와 `i`다) **그 바이트들을 glibc 내부 출력
   버퍼로 복사한다.** 아직 [[system-call]]은 일어나지 않았다 — 이것이
   버퍼링 편의가 작동하는 모습이다. `printf`는 생성된 문자 수인 `2`를 반환한다.

2. **플러시.** 나중에 — 버퍼가 가득 차거나, 프로그램이 종료하거나, 대화형
   터미널에서 개행 문자를 만났을 때 — glibc는 자신의 `write()` 래퍼를 호출해
   버퍼를 비운다: `write(1, <"hi"의 주소>, 2)`. 여기서 `1`은 표준 출력의
   파일 디스크립터이고, 주소는 버퍼링된 바이트를 가리키며, `2`는 길이다.

3. **마샬링.** `write()` 래퍼는 write의 **시스템콜 번호**(64비트 리눅스에서는
   `1`)를 번호 레지스터에, 세 인자 — `1`, 버퍼 주소, `2` — 를 **호출 규약**에
   따라 세 인자 레지스터에 적재한다.

4. **트랩.** 래퍼가 `syscall`을 실행하여 [[system-call]]을 수행한다. 이제
   특권을 얻은 커널은 두 바이트를 표준 출력으로 보내고 개수를 반환한다.

5. **성공 경로.** 커널이 결과 레지스터에 `2`(두 바이트가 쓰였음)를 반환한다.
   래퍼는 음이 아닌 값을 보고 `errno`를 건드리지 않은 채 `2`를 glibc의 플러시
   로직에 반환한다. 문자 `hi`가 나타난다.

이제 번역 단계가 그저 가정되지 않고 실제로 드러나도록 **실패 경로**를 보자.
프로그램이 앞서 파일 디스크립터 `1`을 닫아버려 더 이상 열린 파일을 가리키지
않는다고 하자. 1~4단계는 동일하다 — 래퍼는 미리 알 수 없으므로 정확히 같은
방식으로 마샬링하고 트랩한다. 하지만 5단계에서 커널은 닫힌 디스크립터에 쓸 수
없다; 결과 레지스터에 **`-9`**를 반환하는데, 이는 "잘못된 파일 디스크립터"
오류(그 기호명은 `EBADF`)의 음수 형태다. 래퍼는 음수 값을 보고 그 대표적인
번역을 수행한다 — `9`(`EBADF` 코드)를 전역 **`errno`**에 저장하고 호출자에게
**`-1`**을 반환한다. C 프로그램은 이제 표준적인 일을 한다: `write`가 `-1`을
반환한 것을 보고, `errno`를 읽어 `EBADF`를 발견하고, "잘못된 파일 디스크립터"를
보고한다. 같은 반환 채널이 이렇게 성공 시에는 개수를, 실패 시에는 C 코드가
기대하도록 작성된 `-1`과 `errno`를 실어 날랐다 — 그리고 그 재구성이야말로 이
함수를 순수한 트랩이 아닌 *래퍼*로 만드는 바로 그것이다.

### 모두가 이것을 쓰는 것은 아니다

래퍼는 흔히 가는 길이지, 강제되는 길이 아니다. [[system-call]] 메커니즘은
커널과 CPU의 것이다; 레지스터를 직접 조립하고 트랩을 스스로 실행할 의지가 있는
프로그램이라면 C 라이브러리를 완전히 건너뛸 수 있다. **Go**가 바로 이렇게 한다 —
그 런타임은 glibc 없이 직접 시스템콜을 발행하며, 이것이 Go 바이너리가 C
라이브러리 없이도 동작하는 이유다. 그리고 C 라이브러리가 *쓰이는* 곳에서도
glibc만이 유일한 선택지는 아니다: **musl**은 같은 래핑 역할을 수행하는 더 작고
가벼운 대안 C 라이브러리다. 이것들은 별개의 개념이 아니라 경계를 보여주는 곁가지
사례일 뿐이다: 그것들은 glibc 래퍼가 [[system-call]]로 가는 다리의 한
편리한 구현일 뿐이지, 그 다리 자체는 아니라는 것을 보여준다.
