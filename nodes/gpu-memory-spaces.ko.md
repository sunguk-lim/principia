# GPU 메모리 공간

## 요약

GPU 프로그램을 작성할 때, 당신이 건드리는 모든 데이터는 몇 가지 뚜렷한 **메모리 공간(memory space)** — 레지스터, 공유 메모리, 전역 메모리 같은 이름 붙은 영역 — 중 하나에 산다. 이 공간들은 새로운 하드웨어가 아니다; 그것들은 [[memory-hierarchy]]의 물리적 단계들(작지만 즉각적인 레지스터 슬롯, 빠른 온칩 SRAM, 크지만 느린 오프칩 HBM)의 **프로그래머에게 보이는 얼굴**이다. 정의적인 사실은 각 공간의 **범위(scope)** — 그 안의 데이터를 누가 볼 수 있는지 — 가 [[cuda-thread-hierarchy]]의 한 단계와 정확히 일치한다는 것이다: 레지스터는 하나의 **스레드**에게 사적이고, 공유 메모리는 하나의 **블록**에게 사적이며, 전역 메모리는 전체 **그리드**에게(그리고 그것을 실행한 호스트에게도) 보인다. [[memory-hierarchy]]가 온칩 저장소를 오프칩 HBM보다 엄청나게 빠르게 만들기 때문에, *포인터가 어디에 사는지*가 그것을 읽는 속도를 결정한다. 이것이 메모리 공간을 GPU 프로그래밍의 **핵심** 성능 레버로 만든다: 좋은 프로그램은 자주 사용되는 데이터를 빠르고 작고 사적인 공간에 두고, 크고 느리고 공유된 공간으로의 왕래를 최소화한다.

## 상세 설명

### 개념이 *무엇인가*: 물리적 단계가 프로그래머를 향한 이름을 쓰고, 각각이 범위에 묶여 있다

[[memory-hierarchy]]는 물리적 그림을 제공한다: 각 단이 *아래로* 갈수록 더 많은 바이트를 담지만 더 느리게 이동시키는 저장소들의 사다리다 — 연산 유닛 옆의 수백 킬로바이트짜리 레지스터 슬롯(사실상 즉각적), 수십 메가바이트짜리 온칩 SRAM(매우 빠름), 그리고 GPU의 주 메모리인 수십 기가바이트짜리 오프칩 HBM(크지만 느림). 이것이 *하드웨어*의 시각이다.

GPU 프로그램은 결코 "단"을 직접 이름 붙이지 않는다. 대신 **메모리 공간**과 함께 작업한다: 메모리 공간은 프로그램이 데이터를 넣을 수 있는 이름표가 붙은 영역이며, 그 이름표는 컴파일러에게 *데이터가 어느 물리적 단에 사는지*와 *어떤 스레드들이 그것에 도달할 수 있는지*를 알려준다. 그래서 메모리 공간은 **물리적 거처**([[memory-hierarchy]]의 한 단)와 **범위**([[cuda-thread-hierarchy]]의 한 단계)를 짝짓는다. [[cuda-thread-hierarchy]]로부터 병렬성의 세 겹으로 중첩된 단계들을 떠올려 보자: 단일 **스레드**는 가장 작은 워커이고; 스레드들은 **블록**으로 묶이며; 블록들이 함께 한 번의 실행이 실행하는 **그리드**를 이룬다. 이 노드의 핵심 구조적 사실은 그 공간들의 범위가 정확히 이 단계들이라는 것이다:

| 메모리 공간 | 물리적 거처 ([[memory-hierarchy]]의 단) | 범위 ([[cuda-thread-hierarchy]]의 단계) | 누가 읽고/쓸 수 있는가 |
|---|---|---|---|
| **레지스터** | 연산 유닛 옆의 레지스터 슬롯 (가장 빠름, 작음) | **스레드** | 하나의 스레드 — 자신만의 사적 조각 |
| **공유 메모리** | 온칩 SRAM (빠름) | **블록** | 같은 블록 안의 모든 스레드 |
| **전역 메모리** | 오프칩 HBM (크지만 느림) | **그리드** + 호스트 | 그리드 안의 모든 스레드, 그리고 호스트 |

완결성을 위해 한 번만 언급하고 다시는 쓰이지 않는 두 개의 공간이 더 있다: **상수(constant)** 메모리는 HBM에 살지만 무겁게 캐시되는 작은 읽기 전용 영역이라서 캐시가 그것을 담고 있을 때는 거의 레지스터만큼 빠르게 읽힌다; **로컬(local)** 메모리는 이름이 오해를 부른다 — 레지스터처럼 *스레드당* 사적이지만, 실제로는 느린 HBM에 의해 뒷받침되며, 스레드가 자신의 레지스터 조각이 담을 수 있는 것보다 더 많은 사적 저장 공간을 필요로 할 때만 쓰인다. 표에 있는 세 행이 중요한 것들이다.

이것이 개념의 전부다: **레지스터 ↔ 스레드, 공유 ↔ 블록, 전역 ↔ 그리드.** 포인터의 공간은 그 정체성의 일부다. 두 포인터가 같은 숫자 형태의 주소 값을 담고 있더라도 서로 다른 공간을 가리킬 수 있고, 컴파일러는 각각에 대해 *다른* 로드/저장 명령을 내보낸다. 레지스터, 온칩 SRAM, 오프칩 HBM에 도달하는 것은 물리적으로 다른 연산이기 때문이다.

### 왜 중요한가: 온칩/오프칩 속도 격차가 "어디에 사는가"를 지배적인 비용으로 만든다

프로그래머가 왜 값이 어느 공간에 앉아 있는지 신경 써야 하는가? [[memory-hierarchy]]가 이미 답을 알려주었기 때문이다: 그 단들은 속도가 엄청나게 다르다. 레지스터나 온칩 SRAM에서 값을 읽는 것은 한 사이클에서 수십 사이클 정도의 비용이 든다. *같은* 값을 오프칩 HBM(전역 메모리)에서 읽는 것은 수백 사이클 정도의 비용이 든다 — [[memory-hierarchy]]의 느린 바닥 단이다. 온칩과 오프칩 접근 사이의 격차는 크며, 대략 한 자릿수 이상이다.

그래서 값이 사는 공간이 *곧* 그것의 접근 비용이다. 범위들은 이것을 우연이 아니라 진짜 설계 선택으로 만든다:

- **레지스터(스레드당)**는 가장 빠르고 가장 작다. 스레드는 여기에 자신의 뜨거운 작업 값을 보관한다. 다른 아무것도 그것들을 볼 수 없으며, 정확히 그래서 그것이 가장 빠를 수 있는 것이다 — 다른 스레드와의 조율이 필요 없다.
- **전역 메모리(그리드당)**는 프로그램의 전체 입력과 출력 배열을 담을 만큼 충분히 크고, 호스트가 실행 전에 채우고 실행 후에 다시 읽을 수 있는 유일한 공간이다. 그러나 이것은 느린 HBM 단에 앉아 있으므로, 그것에 대한 모든 접근은 비싸다.
- **공유 메모리(블록당)**는 다리다. 이것은 빠른 온칩 SRAM 단에 앉아 있으면서도, 레지스터와 달리 블록 안의 *모든* 스레드에게 보인다 — 그래서 한 블록의 스레드들은 아무도 HBM으로의 느린 왕래를 하지 않고, 이것을 통해 **협력**할 수 있다: 한 스레드가 값을 쓰고, 다른 스레드가 그것을 읽는다.

이것이 GPU 성능의 가장 중요한 규칙을 낳으며, [[memory-hierarchy]]의 교훈 — *느린 단에서 바이트를 옮기는 것이 대가를 치르는 것*이다 — 으로부터 직접 따라 나온다: **좋은 프로그램은 자주 재사용되는 데이터를 빠르고 사적인 공간(레지스터와 공유 메모리)에 두고, 느린 전역 메모리로의 왕래 횟수를 최소화한다.** [[memory-hierarchy]] 노드는 알고리즘이 큰 조각을 빠른 저장소에 *한 번* 로드하고 그것을 여러 번 재사용함으로써 이긴다는 것을 보여주었다; 메모리 공간은 정확히 그것을 하기 위한 프로그래머의 제어 장치이며, **공유 메모리**가 그 레버의 손잡이다 — 블록 전체가 한 번 로드하고 재사용하는 온칩 스크래치패드다. (공유 메모리 자체의 메커니즘은 별도의 주제다; 여기서는 그저 "블록 전체가 볼 수 있는 빠른 공간"일 뿐이다.)

범위에 관해 한 문장으로 언급할 가치가 있는 시간적 측면도 있다: 그리드의 한 번의 실행이 끝나고 다른 실행이 시작될 때, 레지스터와 공유 메모리는 **증발한다** — 오직 전역 메모리(HBM)만이 실행들을 가로질러 살아남는다. 그것이 입력/출력 배열이 전역 메모리에 살아야 하는 또 다른 이유다: 그것들이 단 하나의 그리드보다 오래 살아남는 유일한 데이터이기 때문이다.

### 실전 사례: 256개의 스레드로 이루어진 블록이 256개짜리 타일을 재사용하는 경우

구체적이고 무의미하지 않은 사례를 보자. **256개의 스레드**로 이루어진 블록이 각각 *같은* 256개 원소짜리 배열 — **타일**이라 부르자 — 에 의존하는 무언가를 계산해야 하며, 그 타일은 그 블록의 작업 동안 **여러 번**(예를 들어 스레드의 내부 루프 패스당 한 번씩, 256번) 재사용된다고 하자. 그 타일은 모든 입력 데이터와 마찬가지로 **전역 메모리**(HBM)에서 시작한다. 문제는 *우리가 그 타일을 어느 공간에서 읽는가*이며, [[memory-hierarchy]]의 속도 격차가 그 비용을 결정한다.

**계획 A — 매번 전역 메모리에서 타일을 읽기.** 256개의 스레드 각각이 256개의 타일 원소 전부를 256번씩 읽는다. 느린 HBM 읽기를 세어 보자:

```
global reads = 256 threads × 256 elements × 256 reuses
             = 256 × 256 × 256
             = 16,777,216 reads from HBM.
```

이 약 1,680만 번의 읽기 하나하나가 [[memory-hierarchy]]의 바닥 단의 느린 오프칩 지연(각각 수백 사이클)을 지불한다. 블록은 거의 모든 시간을 HBM을 기다리며 보낸다 — 정확히 [[memory-hierarchy]]가 경고하는 *메모리 병목* 함정이다.

**계획 B — 타일을 공유 메모리에 한 번 로드한 뒤 온칩에서 재사용하기.** 블록은 자신의 **공유 메모리** 공간(빠른 온칩 단, 범위 = 블록 전체)을 사용한다. 먼저 256개의 스레드가 협력하여 타일을 전역 메모리에서 가져온다 — 자연스러운 분할은 스레드당 원소 하나이므로, *전체* 타일이 256번의 전역 읽기로 **한 번의 패스**에 도착한다:

```
global reads = 256 elements × 1 (each loaded once, by one thread) = 256 reads from HBM.
```

그 로드 이후, 타일은 공유 메모리에 앉아 있으며, 그곳에서는 블록 안의 **모든** 스레드가 그것을 볼 수 있다(그것이 바로 블록 범위가 사주는 것이다). 이제 모든 재사용이 온칩에서 일어난다:

```
shared reads = 256 threads × 256 elements × 256 reuses = 16,777,216 reads from shared memory.
```

재사용 횟수는 계획 A와 *동일*하다 — 더 적은 작업을 한 것이 아니다. 바뀐 것은 *어느 단*이 그것을 서비스했느냐다. [[memory-hierarchy]]가 우리가 비싸게 지불한다고 말하는 유일한 항목인 느린 단 트래픽을 비교해 보자:

```
HBM reads, Plan A : 16,777,216
HBM reads, Plan B :        256
reduction         : 16,777,216 ÷ 256 = 65,536× fewer trips to slow global memory.
```

약 1,680만 번의 비싼 HBM 읽기가 256번의 비싼 읽기와 약 1,680만 번의 *저렴한* 온칩 공유 읽기로 붕괴한다. 온칩 단이 접근당 대략 한 자릿수 더 빠르기 때문에, 블록의 실행 시간은 비슷한 배수로 떨어진다. 더 빠른 하드웨어를 산 것도 아니고 산술을 줄인 것도 아니다 — 우리는 오직 **재사용되는 데이터가 어디에 사는지**만 바꿔서, 그리드 범위의 느린 공간에서 블록 범위의 빠른 공간으로 옮겼을 뿐이다. 그것이 메모리 공간을 이해하는 것의 전체 보상이며, "이 포인터는 어디에 사는가?"가 GPU 프로그래머가 던지는 첫 번째 질문인 이유다.
