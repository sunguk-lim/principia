# 힙

## 요약

힙(heap)(더 정확히는 *이진 힙(binary heap)*)은 데이터를 완전히 정렬하지 않고도 가장
작은 항목을 반복해서 꺼낼 수 있게 해 주는 컨테이너다. 항목을 삽입하고 현재 최솟값을
꺼낼 수 있으며, 이 두 연산은 각각 소박한 최솟값 훑기가 요구할 `n` 단계 대신 약 `log n`
단계(`n`은 항목의 개수)만 비용이 든다. 이는 항목들을 영리하게 절반쯤 정렬된 배치로
유지함으로써 이루어진다 — 가장 작은 항목이 항상 맨 앞에 있을 만큼만 정렬되어 있을 뿐,
나머지를 정렬하는 데는 비용을 치르지 않는다. 그래서 프로그램이 변화하는 컬렉션에서
가장 극단적인 원소를 계속 꺼내 주어야 할 때 선택되는 구조다: 다음으로 가장 빠른 작업을
고르는 스케줄러, 스트림에서 가장 작은 k개를 찾는 문제, 최단 경로 탐색에서 항상 가장
가까운 경계를 진행시키는 것 등이다.

## 상세 설명

**이 구조가 푸는 문제.** 숫자 뭉치를 들고 있고 계속해서 "가장 작은 것을 줘, 제거해,
그리고 계속 더 추가할 수 있게 해 줘"라고 요청한다고 하자. 뭉치를 정렬하지 않은 채로
두면, 최솟값을 찾는 데는 매번 모든 항목을 훑어야 한다 — `n`번의 비교. 대신 뭉치를
완전히 정렬된 채로 유지하면 최솟값을 찾는 것은 즉시지만, 새 항목을 *삽입*하는 것은
올바른 슬롯에 밀어 넣고 그 뒤의 모든 것을 밀어내야 한다는 뜻이다 — 다시 `n`에
비례한다. 힙은 이 두 비용을 모두 피한다: 데이터를 *부분적으로만* 정렬된 채로 유지하며,
최솟값이 항상 알려져 있을 정도로만 정렬한다. 그래서 삽입과 최솟값 제거 둘 다 약
`log n` 단계만 든다. 여기서 `log n`이라는 표현은 대략 `n`을 1에 이를 때까지 절반씩
줄일 수 있는 횟수를 뜻한다(천 개의 항목이면 약 10단계, 백만 개면 약 20단계) — `n`
자체보다 훨씬 저렴하다.

**형태: 완전 이진 트리.** 항목들이 *트리(tree)* — 각 항목(*노드(node)*)이 그 아래 최대
두 개의 항목, 즉 *자식(children)*을 둔 가지치기 도표 — 로 배열되어 있다고 그려 보자;
어떤 노드 위에 있는 항목은 그 *부모(parent)*이고; 부모가 없는 유일한 최상위 노드는
*루트(root)*다. *이진(binary)* 트리란 각 노드가 최대 두 개의 자식을 갖는다는 뜻이다.
*완전(complete)* 이진 트리는 여기에 채움 규칙을 더한다: 마지막 층을 제외한 모든 층
(트리의 모든 수평 행)이 완전히 채워져 있고, 마지막 행은 빈틈없이 왼쪽부터 채워진다.
이 채움 규칙이 바로 트리를 얕게 유지하도록 강제하는 것이다: `n`개의 노드가 이렇게
채워지면 트리는 약 `log n`개의 행 깊이밖에 되지 않는다. 새로 완전히 채워지는 행마다
노드 수가 대략 두 배가 되기 때문이다. 그 깊이가 바로 아래에서 설명할 연산들이 `log n`
비용이 드는 이유다 — 그것들은 루트에서 바닥까지, 또는 그 반대로 걷는데, 이는 길이
`log n`인 경로다.

**영리한 트릭: 포인터 없이 트리를 평평한 배열로 저장한다.** 트리라면 명시적인 링크 —
각 노드가 자식이 메모리 어디에 있는지 기억하는 것 — 가 필요하다고 예상할 수 있다. 힙에는
그런 것이 전혀 필요 없다. 트리가 *완전*하기 때문에, 트리를 위에서 아래로, 왼쪽에서
오른쪽으로 읽어 그 노드들을 평범한 배열(번호 매겨진 슬롯 `0`, `1`, `2`, …의 목록)에
넣을 수 있다. 루트는 슬롯 `0`에, 그 두 자식은 슬롯 `1`과 `2`에, 다음 행은 슬롯
`3, 4, 5, 6`에 들어가는 식이다. 마법 같은 부분은 이렇게 하면 가족 관계가 순수한 인덱스
[[arithmetic]]이 된다는 것이다: 인덱스 `i`에 앉아 있는 노드에 대해,

- **왼쪽 자식**은 인덱스 `2i + 1`에,
- **오른쪽 자식**은 인덱스 `2i + 2`에,
- **부모**는 인덱스 `(i − 1) // 2`에 있다. 여기서 `//`는 정수 나눗셈(나누고 나머지는
  버림)을 뜻한다.

일관성을 확인해 보자: 인덱스 `i`의 왼쪽 자식은 `2i + 1`이다; 여기에 부모 공식을
적용하면 `(2i + 1 − 1) // 2 = (2i) // 2 = i`가 나와 원래 자리로 돌아온다. 그러므로
"부모로 올라가기"나 "자식으로 내려가기"는 그저 인덱스를 곱하거나 나누는 것일 뿐이다 —
저장된 링크도, 메모리 추적도 없다. 이것이 힙이 빠르고 조밀한 *이유*다: 트리 구조
전체가 정수의 덧셈과 나눗셈 안에 암묵적으로 들어 있다.

**불변 조건: 힙 성질.** 최솟값이 항상 맨 앞에 있게 만드는 것은 언제나 유지되는 단
하나의 규칙, 즉 *힙 성질(heap property)*이다: **모든 부모의 값은 두 자식의 값보다
작거나 같다**(이것이 *최소 힙(min-heap)*이다; 비교를 "크거나 같다"로 뒤집으면 대신
가장 큰 값을 드러내는 *최대 힙(max-heap)*이 된다). 이것이 *지역적인* 약속이라는
점에 주목하라 — 각 부모를 자기 자식하고만 비교해 제약할 뿐, 먼 사촌들과는 비교하지
않는다. 하지만 모든 노드에서 지역적으로 "나는 내 자식보다 크지 않다"고 약속하는 것은
*전역적인* 결과를 강제한다: 부모가 없고 자기 자식들보다 작거나 같은 루트는, 그 자식들
역시 *그들의* 자식들보다 작거나 같으므로, 트리의 모든 노드보다 작거나 같아야 한다.
그래서 가장 작은 항목은 반드시 인덱스 `0`에 앉아 있어 즉시 읽을 수 있다. 힙은 나머지를
전혀 정렬하지 않는다 — 어디서나 이 부등식 하나만 강제할 뿐이며, 이는 전체 정렬보다
훨씬 적은 작업이면서도 최솟값을 꼭대기에 고정하기엔 충분하다.

**삽입 = 덧붙이고, 위로 걸러 올리기.** 항목을 추가하려면 첫 번째 빈 슬롯 — 채움 규칙상
바닥 행의 가장 왼쪽 열린 자리인 다음 배열 인덱스 — 에 놓는다. 이는 트리를 완전하게
유지하지만 힙 성질을 깰 수 있다. 새로 들어온 것이 그 부모보다 작을 수 있기 때문이다.
이를 *위로 걸러 올리기(sift up)*로 고친다: 새 항목을 부모(`(i − 1) // 2` 공식으로
찾는다)와 비교해, 더 작으면 서로 바꾼다; 항목의 새 위치에서 반복한다. 각 교환은 항목을
루트 쪽으로 한 행 들어 올리며, 트리는 겨우 `log n`개의 행 깊이이므로 최대 `log n`번의
교환만 필요하다. 왜 이것이 문제를 다른 곳으로 옮기는 게 아니라 불변 조건을 복원하는
것일까? 각 교환은 오직 *더 작은* 값을 *더 큰* 값 위로 옮길 뿐이며, 이는 정확히 그
성질이 원하는 방향이다. 그리고 들어 올린 항목이 이전에 그 자리에 있던 것보다 작으므로
다른 곳에서 성질을 위반할 수 없다. 항목이 더 이상 그 부모보다 작지 않은 순간 멈춘다 —
그 시점에는 모든 부모-자식 쌍이 다시 올바르다.

**최솟값 꺼내기 = 루트를 취하고, 다시 채운 뒤, 아래로 걸러 내리기.** 가장 작은 항목을
제거해 반환하려면 인덱스 `0`의 루트를 취한다 — 그것이 곧 최솟값이다. 이제 루트 슬롯은
비었지만, 완전 트리에 구멍을 남길 수는 없다. 그래서 *마지막* 원소(배열의 최종 슬롯)를
루트로 옮기고 배열을 하나 줄인다; 트리는 완전한 상태를 유지한다. 옮겨진 원소는 아마도
꼭대기에 있기엔 너무 클 테니, *아래로 걸러 내린다(sift down)*: 그 두 자식(인덱스
`2i + 1`과 `2i + 2`)을 살펴 더 작은 쪽을 찾고, 그 자식이 우리 원소보다 작으면 그것과
바꾼다; 새 위치에서 반복한다. 구체적으로 *더 작은* 자식 쪽으로 내려가는 이유는 그
자식이 둘 다의 새 부모가 되어야 하기 때문이다 — 그것은 형제와도 작거나 같아야 하는데,
더 작은 쪽이 그것을 만족시킨다. 각 단계는 한 행씩 내려가므로, 역시 최대 `log n`번의
교환이다. 원소가 두 자식보다 크지 않게 되면 멈추고, 성질이 복원된다.

**작동 예시.** 최소 힙을 하나 취해 값 `5, 3, 8, 1`을 차례로 밀어 넣는다. 배열을
`h`로 쓰고, 인덱스 `0`은 왼쪽에 둔다.

- `5` 삽입: `h = [5]`. 루트다; 걸러낼 것이 없다.
- `3` 삽입: 인덱스 `1`에 덧붙여 `h = [5, 3]`이 된다. 부모는 `(1 − 1) // 2 = 0`,
  값 `5`. `3 < 5`이므로 교환 → `h = [3, 5]`. 새 항목이 이제 인덱스 `0`(루트)에
  있으니 멈춘다.
- `8` 삽입: 인덱스 `2`에 덧붙여 `h = [3, 5, 8]`이 된다. 부모는 `(2 − 1) // 2 = 0`,
  값 `3`. `8 > 3`이므로 성질이 이미 성립한다; 멈춘다. `h = [3, 5, 8]`.
- `1` 삽입: 인덱스 `3`에 덧붙여 `h = [3, 5, 8, 1]`이 된다. 부모는
  `(3 − 1) // 2 = 1`, 값 `5`. `1 < 5`이므로 교환 → `h = [3, 1, 8, 5]`. 이제
  `1`은 인덱스 `1`에 있다; 그 부모는 `(1 − 1) // 2 = 0`, 값 `3`. `1 < 3`이므로
  교환 → `h = [1, 3, 8, 5]`. `1`이 루트에 도달했으니 멈춘다.

배열 `[1, 3, 8, 5]`는 정렬되어 있지 **않다** — `8`이 `5`보다 앞에 있다 — 하지만
가장 작은 값 `1`은 정확히 맨 앞에 있고, 모든 부모는 자식보다 작거나 같다(부모 `1`은
자식 `3`과 `8`보다 작거나 같고; 부모 `3`은 자식 `5`보다 작거나 같다). 이것이 전체
요점이다: 절반만 정렬되고, 최솟값은 드러나 있다.

이제 최솟값을 세 번 꺼내 본다.

- **꺼내기 1.** 루트 `1`이 답이다. 마지막 원소(인덱스 `3`의 `5`)를 루트로 옮기고
  줄인다: `h = [5, 3, 8]`. 인덱스 `0`에서 아래로 걸러 내린다: 자식은 인덱스
  `1`(`3`)과 인덱스 `2`(`8`)에 있고, 더 작은 쪽은 `3`이다. `5 > 3`이므로
  교환 → `h = [3, 5, 8]`. 원소(`5`)는 이제 인덱스 `1`에 있다; 그 자식들은
  인덱스 `3`과 `4`가 될 텐데 이는 끝을 넘었다 — 자식이 없으므로 멈춘다.
  **1**을 반환한다.
- **꺼내기 3.** 루트 `3`이 답이다. 마지막 원소(인덱스 `2`의 `8`)를 루트로 옮기고
  줄인다: `h = [8, 5]`. 인덱스 `0`에서 아래로 걸러 내린다: 유일한 자식은 인덱스
  `1`(`5`)이고, 인덱스 `2`는 끝을 넘었다. `8 > 5`이므로 교환 → `h = [5, 8]`.
  멈춘다. **3**을 반환한다.
- **꺼내기 5.** 루트 `5`가 답이다. 마지막 원소(인덱스 `1`의 `8`)를 루트로 옮기고
  줄인다: `h = [8]`. 아래로 걸러 내린다: 자식이 없다. **5**를 반환한다.

값은 `1`, 그다음 `3`, 그다음 `5` 순서로 나왔다 — 정렬된 순서다. 하지만 우리가 *치른
비용*을 주목하라: 각 삽입과 각 꺼내기는 루트에서 리프까지 길이 `log n`인 경로만
건드렸을 뿐, 모든 항목을 완전히 정렬한 적은 결코 없다. 힙은 오직 하나의 지역적 부등식만
유지하면서도 극값에 대한 정렬된 순서의 접근을 제공했다. 이것이 정확히 힙이 작업
스케줄러(항상 다음으로 우선순위가 가장 높은 작업을 실행), 스트림에 대한 상위-k 선택,
여러 정렬된 리스트의 병합, 그리고 방문하지 않은 가장 가까운 노드를 항상 먼저 확장하는
최단 경로 탐색을 뒷받침하는 이유다 — 모두 현재의 극값을 계속 반복해서 필요로 하지만
데이터 전체를 정렬할 필요는 결코 없는 경우들이다.
