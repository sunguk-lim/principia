# HTTP

## 요약

**HTTP**(HyperText Transfer Protocol)는 웹의 응용 계층 프로토콜이다. 이것은 **요청–응답
(request–response)** 프로토콜이다: 클라이언트가 이름 붙은 자원(resource)에 대해 무언가 해 달라는
자기완결적 메시지 하나를 보내고 — "`/index.html`을 *GET*해 줘", "이 폼을 `/orders`에 *POST*해 줘" —
서버는 자기완결적 답 하나를 돌려보낸다: 처리 결과를 말하는 숫자 **상태 코드(status code)**와 자원
그 자체. 두 메시지는 같은 방식으로 구조화된다: 첫 줄, `이름: 값` 형태의 **헤더(header)** 목록
(메타데이터), 빈 줄, 그리고 선택적인 **본문(body)**. HTTP 자체는 한 교환에서 다음 교환으로 아무
기억도 넘기지 않으며 — 즉 **무상태(stateless)**다 — 전달 작업은 전부 아래 계층에 위임한다:
바이트는 [[tcp]] 연결 위로 이동하고, TCP가 완전하고 순서 맞는 도착을 보장하므로 HTTP는 유실이나
재정렬을 전혀 생각하지 않는다.

## 상세 설명

### 무엇인가 — 신뢰성 있는 바이트 스트림 위의 두 가지 메시지 형태

[[tcp]]는 양 끝에 깨끗하고 신뢰성 있으며 순서가 보장되는 바이트 스트림을 건네준다. HTTP는 단지
*그 바이트들이 무엇을 뜻하는지*에 대한 합의다: 클라이언트는 **요청(request)**을 쓰고, 서버는
**응답(response)**을 쓰며, 각각은 고정된, 읽을 수 있는 형태를 가진다(여기서는 고전적 텍스트 형태인
HTTP/1.1로 보인다):

```
요청(request)                            응답(response)
─────────────────────────────           ─────────────────────────────
GET /index.html HTTP/1.1                 HTTP/1.1 200 OK
Host: example.com                        Content-Type: text/html
Accept: text/html                        Content-Length: 1256
                                         
(GET은 본문 없음)                         <html> … 1256 bytes … </html>
```

- **메서드(method)** — 동사: 클라이언트가 원하는 동작. `GET`(자원 읽기), `POST`(자원에 데이터
  제출), `PUT`(교체), `DELETE`(삭제), 그 외 몇 가지.
- **경로(path)** — 그 서버의 어느 자원인지 (`/index.html`).
- **상태 코드(status code)** — 서버의 세 자리 판정으로, 첫 자리로 묶인다: `2xx` 성공(`200 OK`),
  `3xx` 리다이렉션("옮겨졌으니 저기를 봐"), `4xx`는 *클라이언트*의 잘못(`404 Not Found`,
  `403 Forbidden`), `5xx`는 *서버*의 실패(`500 Internal Server Error`).
- **헤더(header)** — 양쪽 모두에 붙는 개방형 `이름: 값` 메타데이터: 클라이언트가 받아들이는 형식,
  본문의 타입과 길이, 캐싱 규칙, 쿠키, 인증 토큰. 헤더는 HTTP의 확장 지점이다: 새 기능은 새 메시지
  형태가 아니라 새 헤더로 도착한다.
- **본문(body)** — 실질 페이로드: HTML 페이지, JSON 응답, 업로드된 파일.

### 왜 동작하는가 — 무상태성, 그리고 역할 분담

**왜 무상태인가.** 각 요청은 서버가 답하는 데 필요한 *모든 것*(어느 자원인지, 자격 증명, 허용
형식)을 스스로 지녀야 한다 — 프로토콜은 서버가 요청 사이에 아무것도 기억하지 않아도 되게 만든다.
이것이 핵심적인 확장(scaling) 통찰이다: 똑같은 서버 천 대 중 어느 것이든 어떤 요청에도 답할 수
있고, 서버가 죽어도 프로토콜 상태는 잃을 것이 없으며, 캐시는 반복되는 `GET`에 원 서버를 전혀
거치지 않고 답할 수 있다. 애플리케이션이 연속성(로그인 세션, 장바구니)을 *정말* 필요로 하면 그
위에 얹는다 — 서버가 헤더로 토큰(쿠키)을 건네고, 클라이언트가 매 요청마다 그것을 다시 제시하여
각 교환을 자기완결적으로 유지한다.

**왜 [[tcp]] 위인가.** HTTP 메시지는 온전하고 순서가 맞아야만 의미가 있다 — 헤더 목록의 절반은
쓸모없고, 중간 조각이 빠진 본문은 손상된 것이다. [[tcp]]가 정확히 그 보장(완전하고, 순서 맞고,
중복 없는 바이트)을 제공하므로, HTTP의 설계는 *순수한 형식*일 수 있다: 자체 시퀀스 번호도,
재전송도, 확인 응답도 없다. 그러면 하나의 연결이 여러 요청–응답 교환을 연달아 실어 나를 수 있고
(**keep-alive**), 자원마다 새 연결 수립 비용을 아낀다. (더 새로운 와이어 버전들은 같은 요청–응답
*의미론* — 메서드, 상태 코드, 헤더 — 을 유지하면서 그 아래의 인코딩만 바꾼다: HTTP/2는 이진
프레임을 다중화하고, HTTP/3은 아예 TCP를 떠난다; HTTPS는 같은 HTTP를 암호화 계층에 통과시킨
것이다. 이것들은 와이어 형식의 진화로, 여기서는 부수적이다.)

### 구체 사례 — 이름에서 페이지까지, GET 하나의 전 과정

브라우저가 `http://example.com/index.html`을 가져온다:

1. **이름 → 주소.** URL은 서버를 호스트명으로 지목하므로, 클라이언트는 먼저 [[dns]]에
   `example.com` → `93.184.216.34` 해석을 요청한다.
2. **연결.** 클라이언트는 그 주소의 80번 포트(HTTP 기본값)로 [[tcp]] 연결을 연다.
3. **요청.** 위의 요청을 쓴다 — 메서드 `GET`, 경로 `/index.html`, `Host:` 헤더(이 주소에 있을 수
   있는 여러 사이트 중 어느 것을 뜻하는지), 그리고 `Accept: text/html`.
4. **응답.** 서버는 자원을 찾아 `HTTP/1.1 200 OK`를 돌려 쓰고, `Content-Type: text/html`과
   `Content-Length: 1256`을 선언하는 헤더, 빈 줄, 그리고 정확히 1256바이트의 본문을 쓴다.
   클라이언트는 메시지가 어디서 끝나는지 정확히 안다 — 헤더가 그렇게 말했기 때문이다.
5. **재사용 또는 종료.** keep-alive라면 같은 연결이 곧바로 다음 요청(예: 페이지의 스타일시트)을
   나른다; 아니면 닫힌다.

실패 분기도 같은 형태를 쓰며, 상태 줄만 다르다: 오타 난 경로는 `404 Not Found`(`4xx` — 없는 것을
요청한 클라이언트 잘못), 죽어 버린 핸들러는 `500 Internal Server Error`(`5xx` — 서버 자신의
잘못)를 받는다. 클라이언트 코드는 첫 자리 숫자만으로 분기한다 — 묶음이 존재하는 이유가 바로
그것이다.

## Prerequisites

- [[tcp]] — 모든 HTTP 교환이 올라타는 신뢰성 있고 순서 보장된 바이트 스트림; TCP가 전달 문제를
  이미 풀었기에 HTTP는 순수한 메시지 형식일 수 있다
- [[dns]] — URL의 호스트명이 클라이언트가 실제로 연결할 IP 주소가 되는 방법
