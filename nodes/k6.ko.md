# k6

## 요약

**k6**는 Grafana Labs가 만든 오픈소스 [[load-testing]] 도구다. 그 설계는 부하 테스트의 두 반쪽을
두 언어로 갈라 놓는다: **워크로드** — 시뮬레이션된 클라이언트 하나가 하는 일 — 는 작은
**JavaScript** 파일이고, 그 사본 수천 개를 동시에 돌리는 **부하 엔진**은 컴파일된 **Go** 바이너리
하나다. 시뮬레이션된 클라이언트 각각은 스크립트의 default 함수를 루프로 실행하는 **가상
사용자(virtual user, VU)**이고; **익스큐터(executor)**가 VU를 몇 개 돌릴지 또는 반복(iteration)이
얼마나 빨리 도착할지를 조형하며([[load-testing]]의 닫힌 모델과 열린 모델 둘 다); 모든 [[http]]
요청은 자동으로 내장 메트릭에 기록되고; **임계값(threshold)** — 그 메트릭들의
[[latency-percentile]]에 대한 "p(95) < 500 ms" 같은 통과/실패 규칙 — 이 프로세스의 종료 코드를
결정한다. 그래서 CI 파이프라인은 깨진 단위 테스트로 머지를 실패시키듯, 성능 회귀로도 머지를
실패시킬 수 있다.

## 상세 설명

### 무엇인가 — Go 엔진 위의 JS 워크로드

k6 테스트는 두 부분 — 설정과 행동 — 으로 이루어진 JavaScript 파일 하나다:

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [                                   // ramping closed model:
    { duration: '1m', target: 100 },          //   ramp 0 → 100 VUs
    { duration: '3m', target: 100 },          //   hold
    { duration: '1m', target: 0 },            //   ramp down
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],         // tail latency gate (ms)
    http_req_failed:   ['rate<0.01'],         // error-rate gate
  },
};

export default function () {                  // one VU iteration
  const res = http.get('https://api.example.com/items');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);                                   // think time
}
```

`k6 run script.js`를 실행하면 Go 엔진이 시작되어, options가 요구하는 만큼의 VU에서 `default`
함수를 동시에 실행하고, 집계 리포트를 출력한 뒤 — 각 메트릭의 평균, 중앙값, 그리고
[[latency-percentile]] p90/p95 — **임계값이 하나라도 실패했으면 0이 아닌 코드로 종료한다**. 그
종료 코드가 핵심이다: `k6 run`은 추가 장치 없이 그대로 CI 잡에 성능 게이트로 들어간다.

### 왜 이런 아키텍처인가 — 선택 하나하나의 이유

**워크로드에 왜 JavaScript인가.** 워크로드는 행동이다 — 로그인하고, 응답을 파싱하고, 무작위
항목을 골라, 게시한다 — 그러니 진짜 프로그래밍 언어가 필요하고, 테스트 대상 서비스를 만드는 웹
개발자들에게 친숙한 언어면 더 좋다. k6는 바이너리 안에 Go로 작성된 *자체* JavaScript
[[interpreter]](goja 엔진, 현재는 Grafana의 포크인 *Sobek*으로 유지됨)를 내장한다: 스크립트는
Node.js나 브라우저가 아니라 엔진 자신이 해석한다 — 이벤트 루프도, `npm` 런타임도, 외부 의존성도
없다; JS는 *게스트* 언어이고 모든 `http.get` 호출은 Go 호스트가 실행한다.

**VU가 왜 싼가 — OS [[thread]]가 아니라 그린 스레드.** 고전적인 사용자당-스레드 설계(시뮬레이션
사용자 하나 = OS [[thread]] 하나)는 금방 벽에 부딪힌다: [[thread]] 하나마다 메가바이트급 스택과
스케줄링을 위한 커널 [[context-switch]](문맥 교환)이 들므로, 사용자 수천 명은 기가바이트의 스택과 허덕이는 스케줄러를
뜻한다. k6는 대신 각 VU를 **고루틴(goroutine)** — Go의 그린 스레드 — 으로 돌린다: 몇 킬로바이트의
자라나는 스택을 갖고, Go 런타임이 *사용자 공간에서* 스케줄하며, 수천수만 개의 고루틴을 CPU 코어당
대략 하나의 OS [[thread]] 위에 다중화한다. [[http]] 응답을 기다리며 막혀 있는 VU는 거의 비용이
없다 — 런타임이 그 코어에서 그냥 다른 고루틴을 돌린다. "노트북에서 VU 수천 개"의 비결 전부가
이것이다. 그러면서도 각 VU는 **자기만의 격리된 [[interpreter]] 인스턴스**(자기 전역 변수, 자기
상태 — VU들은 기본적으로 아무것도 공유하지 않는다)를 가지므로, 반복들이 서로를 오염시킬 수 없다.

**임계값과 체크가 왜 분리되어 있는가.** **체크(check)**는 요청 단위 단언(`status is 200`)으로,
결과를 *기록*하되 절대 실행을 중단시키지 않는다 — 무거운 부하 아래에서 *일부* 실패는 예상되는
일이고 그 자체가 데이터다. **임계값(threshold)**은 집계된 메트릭에 대한 실행 수준의 판정이다.
그래서 흐름은: 체크와 요청이 메트릭을 채우고 → 메트릭이 실행 전체에 걸쳐 집계되고 → 임계값이
집계를 판정한다. 메트릭은 네 타입이다 — Counter(누적 사건 수), Gauge(최신 값), Rate(참인 비율,
예: `http_req_failed`), Trend([[latency-percentile]]을 유지하는 분포, 예: `http_req_duration`) —
그리고 임계값은 각 타입의 언어로 말한다: Rate에는 `rate<0.01`, Trend에는 `p(95)<500`.

**익스큐터 — [[load-testing]]의 두 모델을 명시적으로.** 위의 `stages`는 *닫힌* 모델이다: VU 풀이
있고, 각 VU가 보내고-기다리고-생각하는 루프를 돌며, 서버가 느려지면 스스로 물러선다. k6는 *열린*
모델 익스큐터도 함께 제공한다 — `constant-arrival-rate` / `ramping-arrival-rate`는 이전 반복이
끝났는지와 무관하게 고정된 일정으로 반복을 시작한다(꺼내 쓸 VU를 미리 할당해 두고서). 용량이나
꼬리 지연 질문에 필요한 것이 바로 이것이며, 그 이유는 정확히 [[load-testing]]이 설명하는 조율된
누락(coordinated omission) 때문이다. 익스큐터를 고르는 일이 *곧* 워크로드 모델을 고르는 일이다.

### 구체 사례 — 실행 하나 읽기

위 스크립트를 용량이 ~90 req/s인 서비스에 돌린다. 100-VU 유지 구간 동안 각 VU는 대략 초당 한 번
루프를 돌고(생각 시간 1초 + 응답 시간), ~95 req/s를 가한다 — 무릎을 살짝 넘긴 부하다. 실행 종료
리포트(발췌):

```
✓ status is 200 ........ 96% — 27,360 of 28,500 checks
http_req_duration ...... avg=210ms p(90)=460ms p(95)=780ms
http_req_failed ........ 4.0%  — 1,140 of 28,500
THRESHOLDS
  http_req_duration p(95)<500 ✗ (780ms)
  http_req_failed   rate<0.01 ✗ (0.04)
→ exit code 99
```

[[load-testing]]의 언어로 읽으면: 가해진 부하가 포화 무릎을 살짝 지나 있으므로 꼬리가 먼저
폭발했다 — *평균*은 차분해 보이는 210 ms인데 p(95)는 780 ms다(임계값을 평균이 아니라
[[latency-percentile]]에 건 이유가 정확히 이것이다) — 그리고 요청의 4%가 아예 실패했다([[http]]
`5xx`와 타임아웃). 두 임계값 모두 실패; 0이 아닌 종료 코드가 CI 잡을 실패시키고; 수정(용량 증설
또는 트래픽 목표 하향)은 사용자가 780 ms를 보기 전에 일어난다. 질문이 "느려지든 말든 *정확히*
120 req/s에서는 어떻게 동작하는가?"였다면, 같은 `default` 함수를 `constant-arrival-rate` 익스큐터
아래에서 다시 돌리면 된다 — 같은 워크로드, 다른 모델.

## Prerequisites

- [[load-testing]] — k6가 구현하는 분과: 워크로드 + 부하 모델 + 임계값; 익스큐터가 닫힌 모델과
  열린 모델을 둘 다 실현한다
- [[http]] — VU 반복이 발행하는 것이자 내장 메트릭이 측정하는 것(상태 코드, 요청 소요 시간)
- [[latency-percentile]] — 임계값(`p(95)<500`)과 실행 종료 리포트의 언어; Trend 메트릭은 이것을
  유지하려고 존재한다
- [[thread]] — VU가 싼 이유를 설명하는 대비: 사용자당 OS 스레드 하나 대 사용자 공간에서 스케줄되는
  작은 스택의 고루틴 그린 스레드
- [[interpreter]] — 각 VU는 자기만의 내장 Go-호스팅 JS 인터프리터(Node.js 아님)에서 스크립트를
  실행하며, 다른 모든 VU로부터 격리된다
- [[context-switch]] — 사용자당-스레드를 비싸게 만드는 커널 매개 비용; 고루틴 스케줄링은 사용자
  공간에서 전환함으로써 이를 피한다
