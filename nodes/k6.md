# k6

## Summary

**k6** is an open-source [[load-testing]] tool built by Grafana Labs. Its design splits the two
halves of a load test between two languages: the **workload** — what one simulated client does —
is a small **JavaScript** file, while the **load engine** that runs thousands of copies of it
concurrently is a single compiled **Go** binary. Each simulated client is a **virtual user (VU)**
executing the script's default function in a loop; **executors** shape how many VUs run or how
fast iterations arrive (both the closed and open models of [[load-testing]]); every [[http]]
request automatically feeds built-in metrics; and **thresholds** — pass/fail rules like
"p(95) < 500 ms" over those metrics' [[latency-percentile]]s — decide the process's exit code, so
a CI pipeline can fail a merge on a performance regression exactly as it fails one on a broken
unit test.

## Grounded explanation

### What it is — a JS workload on a Go engine

A k6 test is one JavaScript file with two parts — configuration and behavior:

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [                                   // ramping closed model:
    { duration: '1m', target: 100 },          //   ramp 0 → 100 VUs
    { duration: '3m', target: 100 },          //   hold
    { duration: '1m', target: 0 },            //   ramp down
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],         // tail latency gate (ms)
    http_req_failed:   ['rate<0.01'],         // error-rate gate
  },
};

export default function () {                  // one VU iteration
  const res = http.get('https://api.example.com/items');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);                                   // think time
}
```

Running `k6 run script.js` starts the Go engine, which executes the `default` function
concurrently in as many VUs as the options demand and prints an aggregate report — every metric
with its mean, median, and the [[latency-percentile]]s p90/p95 — then exits **non-zero if any
threshold failed**. That exit code is the point: `k6 run` drops into a CI job as a performance
gate with no extra machinery.

### Why this architecture — the why behind each choice

**Why JavaScript for the workload.** A workload is behavior — log in, parse the response, pick a
random item, post — and that wants a real programming language, familiar to the web developers
whose services are under test. k6 embeds its *own* JavaScript [[interpreter]], written in Go
(the goja engine, today maintained as Grafana's fork *Sobek*), inside the binary: the script is
interpreted by the engine itself, not by Node.js or a browser — so there is no event loop, no
`npm` runtime, no external dependency; the JS is a *guest* language whose every `http.get` call is
executed by the Go host.

**Why VUs are cheap — green threads, not OS [[thread]]s.** The classic thread-per-user design
(each simulated user = one OS [[thread]]) hits a wall fast: each [[thread]] costs a
megabyte-scale stack and a kernel [[context-switch]] to schedule, so thousands of users means
gigabytes of stacks and a scheduler thrashing. k6 instead runs each VU as a **goroutine** — Go's
green thread: a few-kilobyte growable stack, scheduled *in user space* by the Go runtime, which
multiplexes many thousands of goroutines onto roughly one OS [[thread]] per CPU core. A VU that
is blocked waiting on an [[http]] response costs almost nothing — the runtime just runs other
goroutines on that core. That is the whole trick behind "thousands of VUs on a laptop." Each VU
still gets its **own isolated [[interpreter]] instance** (own globals, own state — VUs share
nothing by default), which is why iterations can't corrupt each other.

**Why thresholds and checks are separate.** A **check** is a per-request assertion
(`status is 200`) that *records* its result but never aborts the run — under heavy load *some*
failures are expected and are themselves data. A **threshold** is the run-level verdict over
aggregated metrics. So the flow is: checks and requests feed metrics → metrics aggregate over the
whole run → thresholds judge the aggregate. Metrics come in four types — Counter (total events),
Gauge (latest value), Rate (fraction true, e.g. `http_req_failed`), Trend (a distribution keeping
[[latency-percentile]]s, e.g. `http_req_duration`) — and thresholds speak each type's language:
`rate<0.01` for a Rate, `p(95)<500` for a Trend.

**Executors — both [[load-testing]] models, explicitly.** The `stages` above are a *closed* model:
a VU pool, each VU looping send-wait-think, self-throttling when the server slows. k6 also ships
*open*-model executors — `constant-arrival-rate` / `ramping-arrival-rate` start iterations on a
fixed schedule regardless of whether earlier ones finished (pre-allocating VUs to draw from), which
is what a capacity or tail-latency question needs, for exactly the coordinated-omission reason
[[load-testing]] explains. Choosing an executor *is* choosing the workload model.

### Worked instance — reading one run

The script above, against a service whose capacity is ~90 req/s. During the 100-VU hold, each VU
loops roughly once per second (1 s think time + response time), offering ~95 req/s — just past the
knee. End-of-run report (abridged):

```
✓ status is 200 ........ 96% — 27,360 of 28,500 checks
http_req_duration ...... avg=210ms p(90)=460ms p(95)=780ms
http_req_failed ........ 4.0%  — 1,140 of 28,500
THRESHOLDS
  http_req_duration p(95)<500 ✗ (780ms)
  http_req_failed   rate<0.01 ✗ (0.04)
→ exit code 99
```

The reading, in [[load-testing]] terms: the offered load sits slightly past the saturation knee, so
the tail has exploded first — p(95) at 780 ms while the *average* is a calm-looking 210 ms
(exactly why the threshold was on a [[latency-percentile]], not the mean) — and 4% of requests
failed outright ([[http]] `5xx`s and timeouts). Both thresholds fail; the non-zero exit fails the
CI job; the fix (more capacity, or a lower traffic target) happens before users ever see the
780 ms. Had the question been "how does it behave at *exactly* 120 req/s regardless of slowdown?",
the same `default` function would be re-run under a `constant-arrival-rate` executor instead —
same workload, other model.

## Prerequisites

- [[load-testing]] — the discipline k6 implements: workload + load model + thresholds; its
  executors realize both the closed and open models
- [[http]] — what a VU iteration issues, and what the built-in metrics measure (status codes,
  request duration)
- [[latency-percentile]] — the language of thresholds (`p(95)<500`) and of the end-of-run report;
  Trend metrics exist to keep them
- [[thread]] — the contrast that explains VU cheapness: goroutine green threads with tiny
  user-space-scheduled stacks vs one OS thread per user
- [[interpreter]] — each VU runs the script in its own embedded Go-hosted JS interpreter (no
  Node.js), isolated from every other VU
- [[context-switch]] — the kernel-mediated cost that makes thread-per-user expensive; goroutine
  scheduling avoids it by switching in user space
