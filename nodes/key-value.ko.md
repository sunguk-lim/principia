# 키-값 매핑

## 요약

**키-값 매핑(key–value mapping)**은 데이터를 쌍 — *키(key)*와 거기 붙은 *값(value)*
— 으로 저장하여, 값이 어디 있는지 알아야 하는 대신 그 키의 이름을 대는 것만으로 값을
가져오고, 바꾸고, 제거할 수 있게 한다. 전화번호부가 일상적인 예다: 사람(키)을 찾아
그 번호(값)를 얻으며, 그것이 실제로 어느 물리적 페이지에 놓였는지는 알지도 못하고 신경
쓰지도 않는다. 정의하는 규칙은 **키가 고유하다**는 것이다: 각 키는 최대 하나의 값만
가리키므로, "키 `k`에 대한 값"은 항상 단 하나의 모호하지 않은 답이다. 이것은 *추상
인터페이스*다 — 키로 주소를 매기는 세 연산 *가져오기(get)*, *설정(set)*, *삭제
(delete)* — 데이터를 저장하는 특정 방식이 아니다; `hash-map`, 균형 트리, `trie`는
모두 이 같은 키-값 인터페이스를 제공하는 서로 다른 구체적인 기계들이다.

## 상세 설명

**대상: 서로 다른 키를 갖는 쌍들의 집합.** 키-값 매핑은 *순서쌍* `(k, v)` — 키 `k`가
그 값 `v`에 묶인 것 — 의 [[set]]으로, 이것을 단순한 쌍들의 집합이 아니라 *매핑
(mapping)*으로 만드는 제약 하나를 따른다: **어떤 두 쌍도 키를 공유하지 않는다.** 키가
서로 다르므로, 키들은 그 자체로 하나의 [[set]](*키공간(keyspace)*)을 이루며, 키
하나를 대는 것은 정확히 하나의 쌍을 선택한다. 이 단 하나의 제약이 전체 아이디어다:
"`k`에 대한 값"이라는 표현이 하나의 값만을 가리키지, 결코 둘을 가리키지 않음을
보장한다. (이 제약을 없애면 *멀티맵(multimap)*을 얻는다. 여기서는 키 하나가 여러
값을 지닐 수 있으며, 이는 다른 구조다.) 모든 연산이 "`k`가 이미 키인가, 그렇다면
어느 쌍인가?"를 묻는 것으로 시작하므로 키는 [[set]] 소속 검사와 동등성을 지원해야
한다; 값에는 그런 요구사항이 없어 자유롭게 반복될 수 있다(서로 다른 두 사람이 같은
전화번호를 공유할 수 있다).

**이것이 기여하는 바: 연관 접근.** 데이터에 다다르는 두 방식을 비교해 보자. 배열은
*위치적(positional)* 접근을 준다: 어떤 항목을 가져오려면 그것이 인덱스 `7`에 있음을
알아야 한다 — 주소는 당신이 추적할 책임이 있는 위치다. 키-값 매핑은 대신 *연관
(associative)*(내용으로 주소가 매겨지는) 접근을 준다: 주소는 **곧** 키 자체이며,
이미 손에 쥐고 있는 의미 있는 데이터 — 사용자 이름, 단어, 계좌 id — 다. `"alice"`의
*값*을 요청할 뿐, "Alice가 어느 슬롯에 있나?"를 묻지 않는다. 이것이 이 구조의 기여이자
어디에나 존재하는 이유다: 실제 조회는 거의 항상 "이 식별자가 주어지면, 거기 붙은 것은
무엇인가?"이며, 매핑은 바로 그 질문에 직접 답한다.

**인터페이스 — 세 연산, 모두 키로 주소가 매겨짐.** 매핑은 다음을 노출한다:

- **set(k, v)** — 값 `v`를 키 `k`에 묶는다. `k`가 아직 키공간에 없으면 쌍
  `(k, v)`를 추가한다; `k`가 *이미 있다면*(소속 검사가 예라고 답한다면) 그 값을
  `v`로 **덮어쓴다**. 고유성 불변 조건은 바로 이 덮어쓰기*에 의해* 유지된다 —
  기존 키를 설정하는 것은 복제가 아니라 대체이므로 키공간은 계속 [[set]]으로
  남는다.
- **get(k)** — `k`에 묶인 값을 반환하거나, `k`가 키공간에 없으면 "없음"을 보고한다.
  이것이 연관 접근이 존재하는 이유인 읽기 연산이다.
- **delete(k)** — 키가 `k`인 쌍을 제거해 키공간을 하나 줄인다.

모든 연산은 키를 대며 먼저 키공간에 대한 [[set]] 소속 검사를 참조한다; 위치를
참조하는 것은 없다. 이것이 이 인터페이스를 *추상적*으로 만드는 것이다 — 소속 여부가
*어떻게* 결정되는지, 쌍이 *어디* 있는지는 아무것도 말하지 않고, 오직 세 연산이
*무엇을* 뜻하는지만 말한다.

**"추상적"이 중요한 이유 — 하나의 인터페이스, 여러 기계.** 위의 어떤 것도 키에 대한
쌍을 어떻게 찾는지 말하지 않는다. 서로 다른 구현들은 이를 다르게 답하며 그에 따라
트레이드오프를 만든다: `hash-map`은 키로부터 저장 위치를 계산해 평균 `O(1)` 접근을
주지만 키 순서는 없다; 균형 탐색 트리는 키를 정렬된 채로 유지해 `O(log n)` 접근을
*순서 있는* 순회와 함께 준다; `trie`는 키를 문자 단위로 저장하며 공통 접두사를
공유한다. 이들이 서로 다른 노드인 것은 정확히 그 *메커니즘*이 다르기 때문이다 — 하지만
바깥에서 보면 각각은 그저 키로 하는 *가져오기 / 설정 / 삭제*일 뿐이다. 인터페이스를
어느 특정 기계와 별개로 이름 붙이는 것, 그것이 어느 구조가 그 비용을 치를지 정하기
*전에* "여기서는 키-값 저장소를 쓰라"고 말할 수 있게 해 주는 것이다.

**작동 예시.** 전화번호부를 키-값 매핑 `B`로 모델링하되, 다음 쌍들의 집합에서
시작한다

```
B = { ("alice", "555-1234"), ("bob", "555-7777") }
```

키공간은 [[set]] `{"alice", "bob"}`이다.

1. **get("bob")** → 소속 검사가 `"bob"`이 키라고 답한다; 그 쌍은
   `("bob", "555-7777")`이므로 결과는 `"555-7777"`이다. 위치가 아니라 사람의
   이름을 댔다.
2. **set("alice", "555-9999")** → `"alice"`는 이미 키이므로 이는 **덮어쓰기**다:
   쌍 `("alice", "555-1234")`가 `("alice", "555-9999")`가 된다. 키공간은
   변하지 않는다 — 여전히 `{"alice", "bob"}`이다 — *새* 키가 도입되지 않았기
   때문이다. 고유성이 유지되었다: `"alice"` 쌍이 두 개가 되지 않았다.
3. **set("carol", "555-0000")** → `"carol"`은 키공간에 *없으므로* 이는 쌍을
   **추가**한다. 이제
   `B = { ("alice","555-9999"), ("bob","555-7777"), ("carol","555-0000") }`이고
   키공간은 `{"alice", "bob", "carol"}`로 늘어난다.
4. **delete("bob")** → 키가 `"bob"`인 쌍을 제거한다; 키공간은
   `{"alice", "carol"}`로 줄어들고 이제 `get("bob")`은 "없음"을 보고한다.

어느 단계에서도 인덱스, 슬롯, 순서를 언급하지 않았다 — 모든 동작은 순전히 키와
키공간에 대한 [[set]] 소속 검사만으로 이루어졌다. 그것이 키-값 매핑의 전부다: 고유한
키를 가진 쌍들의 집합으로, 키의 내용으로 접근한다.

**이것이 등장하는 곳.** 이것은 모든 언어의 딕셔너리 / 연관 배열(파이썬의 `dict`,
자바의 `Map`, JS 객체) 뒤에 있는 모델이며, `redis` 같은 키-값 데이터베이스와 캐시
뒤에, 그리고 셀 수 없이 많은 일회성 조회("사용자 id → 세션", "단어 → 개수") 뒤에
있는 모델이다. 이들은 부수적인 사례들일 뿐이며, 지속적인 아이디어는 위에서 설명한
고유하게 키가 매겨진, 내용으로 주소가 매겨지는 매핑이다.
