# KV 캐시 양자화

## 요약

[[kv-cache]] — 지나온 모든 토큰의 key와 value를 저장한 것 — 는 보통 16비트
부동소수점(FP16)으로 보관되며, 긴 컨텍스트나 큰 배치에서는 메모리상 가장 큰
것일 뿐 아니라, **매** 디코딩 스텝마다 모델이 메모리에서 다시 읽어와야 하는
대상이기도 하다. KV 캐시 양자화는 캐시된 `K`와 `V` 값을 FP16 대신 저정밀도
정수(INT8, 심지어 INT4)로 저장함으로써 캐시를 줄인다. 방법은 평범한
[[quantization]]과 같다: 값마다 작은 정수 코드를 하나씩 두고 공유되는
**스케일 `s`**를 함께 두었다가, 어텐션에 그 값이 필요한 순간에 다시 곱해
복원한다(`x̂ = q × s`). INT8은 캐시를 절반으로(2배) 줄이고, INT4는 4분의
1로(4배) 줄인다 — 그리고 디코딩은 캐시를 *연산*하는 것이 아니라 *이동*시키는
것이 병목이기 때문에, 절반의 바이트만 읽으면 그만큼 각 스텝이 빨라진다.
한 가지 눈에 잘 띄지 않는 함정: **key**에는 소수의 극단적으로 큰 "이상치
(outlier)" 채널이 있어서 하나의 공유 스케일을 쓰면 망가지므로, 실제로는
key를 **채널별로**, value를 **토큰별로** 양자화한다 — 캐시 전체에 하나의
스케일을 쓰는 것이 아니라.

## 상세 설명

**비용이 어디 있는가.** [[kv-cache]]에서 디코딩은 전체 시퀀스에 대해
`2 × n_tokens × n_layers × n_heads × d_head`개의 숫자를 저장하며, 긴
컨텍스트나 큰 배치에서 이 캐시가 추론 비용을 **지배**한다는 점을 떠올리자.
사실 비용은 두 가지다. (1) *메모리*: 캐시는 모델 자체의 가중치보다도 커질 수
있다 — 예를 들어 시퀀스 32개, 각 8192 토큰, 레이어 32개, 헤드 32개,
`d_head = 128`, 값당 2바이트(FP16)인 배치는
`2 × 8192 × 32 × 32 × 128 × 32 × 2바이트 ≈ 137 GB`로, 가속기 하나에 가중치와
나란히 담기에는 너무 크다. (2) *대역폭*: [[kv-cache]]에서 각 디코딩 스텝은
새 토큰 **하나**만 계산하지만, 그것에 어텐션하기 위해 **캐시 전체**를 메모리에서
다시 읽어와야 한다. 그러므로 디코딩은 *메모리 대역폭에 의해 제한(memory-bound)*
된다 — 산술 연산은 사소하고, 시간은 그 바이트들을 스트리밍하는 데 든다. 바이트
수를 절반으로 줄이면 메모리 사용량과 스텝당 읽기 시간도 거의 절반으로 줄어든다.
이것이 전체 동기다.

**아이디어: 캐시 내용에 [[quantization]]을 적용한다.** 캐시된 각 key/value를
FP16 숫자로 저장하는 대신, [[quantization]]과 정확히 같은 방식으로 저비트 정수
**코드**와 공유 **스케일**로 저장한다: 코드 `q`는 실제 값 `q × s`를 나타내며,
클리핑으로 인한 손실이 없는 스케일은 `s = max(|x|) / q_max`이고, `b`비트에
대해 `q_max = 2^(b−1) − 1`이다(INT8: `q_max = 127`; INT4: `q_max = 7`). 캐시
쓰기는 `q = round(x / s)`가 되고, 어텐션 안에서 매 스텝 일어나는 캐시
읽기는 `x̂ = q × s`가 된다. FP16→INT8은 각 값을 16비트에서 8비트로
줄이고(2배 작아짐), FP16→INT4는 4비트로 줄인다(4배 작아짐). 대가는, 역시
[[quantization]]에서 그대로 온 것으로, 유한한 반올림 오차
`|x̂ − x| ≤ s/2`다: 어텐션에 들어가는 key와 value가 이제 약간 흔들린다.
이것이 전체 거래다 — `K`/`V`에 작고 유한한 오차를 감수하는 대신 캐시 저장과
스트리밍이 2배–4배 줄어든다.

**눈에 잘 띄지 않는 부분: key에는 이상치가 있으므로 세분성(granularity)이
중요하다.** 캐시 전체에 스케일 하나만 쓸 수 있다면 그렇게 할 것이다 — 저장할
숫자가 하나뿐이니까. 하지만 [[quantization]]에서의 세분성 경고를
떠올려보자: 이상치 하나가 `M = max(|x|)`를 부풀리고 따라서 `s`도 부풀리며,
`s`가 커지면 *다른 모든 값*이 거칠어진다(어쩌다 있는 큰 값 하나가 작은 값들을
전부 코드 `0`으로 반올림시켜 지워버릴 수 있다). 학습된 트랜스포머의 **key**
벡터에는 정확히 이런 병리 현상이 있다: key 벡터 안에서 *특정 몇 개의 좌표*
(모든 토큰에 걸쳐 같은 좌표 — 즉 하나의 "채널")가 지속적으로 거대한 크기를
가지고, 나머지는 작다. 그런 이상치들로부터 만들어진 텐서 전체 단일 스케일
하나는 수많은 작은 좌표들을 0으로 짓눌러 버릴 것이다. 해법은 이상치가
있는 위치에 맞춰 세분성을 더 세밀하게 나누는 것이다:

- **key: 채널별로.** 이상치는 *좌표*를 기준으로 정렬되어 있으므로, **각
  좌표(채널)에 자신만의 스케일**을 주고, 캐시된 토큰들에 걸쳐 그 좌표에
  대해서만 계산한다. 그러면 이상치 채널은 큰 스케일을 갖되 *자기 자신만*
  거칠어지고, 정상적인 채널들은 작은 스케일을 유지해 정밀함을 지킨다.
- **value: 토큰별로.** value 벡터는 key와 같은 고정 채널 이상치 구조를
  보이지 않으므로 **토큰 단위**로 양자화한다 — 토큰 하나의 value 벡터
  전체가 스케일 하나를 공유하며, 이는 캐시 레이아웃과도 잘 맞는다(토큰의
  `V`는 토큰이 도착할 때 한꺼번에 도착하기 때문이다).

일부 방법(예: KVQuant)은 더 나아가 가장 나쁜 이상치 채널 몇 개는 FP16 그대로
남겨두고 나머지만 양자화한다 — 약간의 저장 공간을 대가로 가장 해로운 값들을
제거하는 것이다. 이 모든 것을 관통하는 원리는 [[quantization]]의 교훈이다:
스케일 경계를 이상치가 *없는* 곳에 두어, 큰 값 하나가 이웃들을 거칠게
끌고 가지 못하게 하라는 것이다.

**계산 예시.** 명확한 이상치 좌표를 가진 key 벡터 하나와 value 벡터
하나를 **INT8**(`q_max = 127`)로 양자화해 보자.

*key 벡터* `k = [0.5, −0.8, 12.0, 0.3]` — 좌표 3이 이상치다(이웃들이
±0.5 근처인데 12.0이다).

- **텐서별(잘못된 방법) — 실패를 확인하기 위해.** 벡터 전체에서 스케일
  하나를: `M = 12.0`, `s = 12.0 / 127 ≈ 0.0945`. 코드 `q = round(k/s)`:
  `0.5/0.0945 = 5.3 → 5`; `−0.8/0.0945 = −8.5 → −8`; `12.0/0.0945 = 127 → 127`;
  `0.3/0.0945 = 3.2 → 3`. 역양자화: `[0.472, −0.756, 12.00, 0.284]`. 여기서
  작은 값들이 살아남는 것은 INT8이 그래도 꽤 세밀하기 때문일 뿐이다 — 하지만
  *오차 예산*은 이상치가 정한다: `s/2 ≈ 0.047`이므로, 작은 값 `0.3`은 그
  값의 약 **5%**에 해당하는 오차 `≈ 0.016`을 갖는다. INT4로 떨어뜨리면
  (`q_max = 7`, `s = 12.0/7 ≈ 1.714`) [[quantization]]에서 말한 재앙이
  덮친다: `round(0.5/1.714)=0`, `round(0.3/1.714)=0`,
  `round(−0.8/1.714)=0` — 네 좌표 중 셋이 `0`으로 붕괴하여
  `[0, 0, 7, 0]` → `[0, 0, 12.0, 0]`이 된다. 이상치가 벡터 전체를 집어삼킨
  것이다.

- **채널별(올바른 방법).** 각 좌표가 자신만의 스케일을 갖는다(실제
  사용에서는 캐시된 모든 토큰에 걸쳐 그 좌표에 대해 계산하지만, 여기서는
  설명을 위해 값 하나 기준으로 계산한다). 작은 좌표들은 이제 작은 스케일을
  갖는다 — 예를 들어 크기가 `0.5`인 좌표 1은 `s_1 = 0.5/127 ≈ 0.00394`를
  가지므로, `0.5`는 코드 `127`로 매핑되고 `0.500`으로 복원되어, 오차는
  `≈ 0.002`(`< s_1/2 ≈ 0.002`)에 그친다 — 이상치에 휩쓸리는 대신. 이상치
  좌표는 자신의 큰 스케일(`12.0/127 ≈ 0.0945`)을 그대로 유지하며 `12.00`으로
  복원된다. 어떤 좌표도 다른 좌표의 크기 때문에 거칠어지지 않는다. *이
  대비가 바로 key를 채널별로 다루는 이유다.*

*value 벡터* `v = [0.2, −1.3, 3.1, 0.05]` — 극단적인 이상치가 없으므로
**토큰별로**(벡터 전체에 스케일 하나) 양자화한다. `M = 3.1`,
`s = 3.1/127 ≈ 0.0244`. 코드: `round(0.2/0.0244)=8`,
`round(−1.3/0.0244)=−53`, `round(3.1/0.0244)=127`, `round(0.05/0.0244)=2`.
역양자화 `v̂ = [0.195, −1.293, 3.100, 0.0488]`, 모든 오차가
`s/2 ≈ 0.0122` 미만이다. `v`에 이상치가 없으므로 공유되는(토큰별) 스케일
하나만으로 이미 충분하다 — 이것이 정확히 value가 key처럼 채널별 처리를
필요로 하지 않는 이유다.

**대가는 무엇이고, 얻는 것은 무엇인가.** 저장량은 비트 비율만큼 줄어든다:
이 key/value 쌍은 FP16에서는 `8개 숫자 × 16비트 = 128비트`이고, INT8에서는
`8 × 8 = 64비트`에 스케일(스케일 오버헤드를 빼면 대략 2배)이 더해지며,
INT4에서는 `8 × 4 = 32비트`다(4배). 캐시 전체로 보면 이는 컨텍스트가
메모리에 들어가느냐 마느냐의 차이이자, 각 디코딩 스텝이 137 GB를 읽느냐
~68 GB(INT8) / ~34 GB(INT4)를 읽느냐의 차이다 — 디코딩이 메모리 대역폭에
제한되므로 이는 곧 디코딩 속도에 정비례한다. 대가는 어텐션에 들어가는
`K`/`V`에 실리는 값당 반올림 오차 `≤ s/2`와, 스케일이 많아지면서 생기는
약간의 부기(bookkeeping) 비용이다(스케일이 많다는 것은 비트가 늘어난다는
뜻이며, 이는 [[quantization]]에서와 같은 비트 대 오차의 거래가 스케일
자신에게도 적용되는 것이다). 채널별 key와 토큰별 value를 선택하는 것이
바로 이 오차를 충분히 작게 유지해주는 방법이다 — 대체로 INT8은 거의
손실이 없고 잘 만든 INT4도 실용적이다 — 그래서 2배–4배의 이득이 거의 공짜로
따라온다.
