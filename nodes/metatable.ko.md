# 메타테이블

## 요약

유일한 자료 구조가 테이블 — [[key-value]] 쌍을 담는 [[hash-map]] — 인 언어에서, **메타테이블(metatable)**은 첫 번째 테이블에 매달아 놓은 두 번째 테이블로, *첫 번째 테이블에 대한 연산이 무엇을 뜻하는지를 바꾼다*. 그 항목들은 특수한 이벤트 이름(`__index`는 "키가 없었다", `__add`는 "`+` 연산자가 적용되었다" 등)을 키로 하고, 값으로는 핸들러 함수나 폴백(fallback) 테이블을 갖는다. 주 테이블에서 촉발 조건에 해당하는 연산이 일어나면, 런타임은 그 메타테이블에서 일치하는 항목을 찾아보고, 발견하면 기본 동작 대신 그것을 사용한다. 메타테이블은 그저 테이블일 뿐이고 그 내용물도 [[hash-map]]으로 조회되는 평범한 [[key-value]] 항목이기 때문에, 이 단일 메커니즘 하나로 연산자 오버로딩, 기본값, 읽기/쓰기 가로채기, 그리고 — `__index`가 다른 테이블을 가리키게 하여 — 프로토타입 방식의 상속까지, 별도의 클래스 시스템 없이 전부 제공한다.

## 상세 설명

**중심 대상.** 배경에서 시작하자: 테이블은 [[key-value]] 쌍을 저장하는 [[hash-map]]이며 이 언어의 만능 구조 역할을 한다(배열, 레코드, 객체, 모듈이 모두 테이블이다). 기본적으로 테이블에 대한 연산의 의미는 고정되어 있다 — `t[k]`는 `k`를 조회해 그 값 또는 `nil`을 돌려주고, `a + b`는 숫자에 대해서만 정의된다. **메타테이블**은 다른 테이블에 붙여 그 의미들을 *재정의하거나 확장하는* 테이블이다. 요령은 균일성이다: 메타테이블 자체의 내용도 그저 [[key-value]] 쌍이고, 각 키는 런타임이 알고 있는 특정 *이벤트* 이름이며, 각 값은 그 이벤트가 발생했을 때 할 일이다. 따라서 "동작을 커스터마이즈한다"는 것은 "테이블에 항목을 하나 넣는다"로 환원되고, 그 커스터마이즈를 디스패치하는 것은 메타테이블에 대한 [[hash-map]] 조회로 환원된다.

**왜 동작하는가 — 하나의 메커니즘, 여러 기능.** 가장 중요한 이벤트는 `__index`로, *없는 키에 대한 읽기(missing-key read)*에서 발생한다. `t[k]`를 읽으면 먼저 `t`에서 통상적인 [[hash-map]] 조회를 하고, 적중하면 평소처럼 값을 돌려준다. **미스(miss)**가 나면, 단순히 `nil`을 내놓는 대신 런타임은 `t`의 메타테이블에서 `__index` 항목을 찾아본다: 그것이 테이블이면 조회를 *그곳에서* 다시 시도하고(위임), 함수이면 그 함수를 호출해 결과를 계산한다. 이 폴백 하나가 [[key-value]] 미스를 *상속*으로 바꾸어 놓는다 — 자기 항목이 거의 없는 객체 테이블이 나머지를 공유 "부모" 테이블에 위임할 수 있다. 다른 이벤트들은 같은 아이디어를 연산자 등으로 일반화한다: `__add`는 테이블에 `+`가 적용될 때 발생하고(*연산자 오버로딩*), `__newindex`는 쓰기를 가로채고, `__call`은 테이블을 호출 가능하게 만드는 식이다. 이들 모두 같은 방식으로 해소된다 — 런타임은 기본 규칙으로 처리할 수 없는 연산을 만나면 메타테이블에서 이벤트 이름을 [[hash-map]] 조회하고 거기서 찾은 것에 맡긴다.

**구체적인 실례.** 메서드 상속(`__index`)과 오버로딩된 연산자(`__add`) 양쪽에 메타테이블을 써 보자:

```
Account = {}                    -- a "class" table holding shared methods
Account.__index = Account       -- misses on an instance delegate to Account
function Account.deposit(self, x) self.balance = self.balance + x end

obj = {balance = 100}           -- an instance: its own table
setmetatable(obj, Account)      -- attach Account as obj's metatable

obj.deposit(obj, 50)            -- obj has no "deposit" key → __index → found in Account
print(obj.balance)              -- 150
```

`obj.deposit`을 읽으면 먼저 `obj`에서 [[hash-map]] 조회를 하고 *미스*가 난다(obj에는 `balance`밖에 없다). 그러면 런타임은 obj의 메타테이블에서 `__index` [[key-value]] 항목을 읽어 `Account` 테이블을 찾고, 조회를 그곳에서 다시 시도한다 — 거기에 `deposit`이 살고 있다. 즉 `obj`는 아무 복사 없이 메서드를 "상속"했다: 순수한 [[key-value]] 위임이다. 이제 연산자를 오버로딩해 보자:

```
Vec = {}
Vec.__add = function(a, b) return setmetatable({a[1]+b[1], a[2]+b[2]}, Vec) end

v1 = setmetatable({1, 2}, Vec)
v2 = setmetatable({3, 4}, Vec)
v3 = v1 + v2                    -- '+' on tables is undefined by default → __add fires
print(v3[1], v3[2])            -- 4  6
```

`v1 + v2`는 테이블에 대해 내장된 의미가 없으므로, 런타임은 메타테이블에서 `__add`를 조회해 호출한다. 이 예가 퇴화하지 않은(non-degenerate) 이유는 이 메커니즘이 담당하는 *두 방향 모두*를 연습하기 때문이다 — 없는 키의 조회가 다른 테이블로 라우팅되는 것(`__index` 상속)과, 기본 의미가 없는 연산자가 핸들러로 라우팅되는 것(`__add` 오버로딩) — 그리고 둘 다 평범한 [[key-value]] 항목들에 대한 동일한 "메타테이블에서 이벤트를 조회한다" 규칙임을 보여준다.
