# MongoDB

## 요약

**MongoDB**는 **분산 문서 데이터베이스**다 — 그리고 PostgreSQL과 마찬가지로,
이것을 독자적인 개념으로 다루는 요점은 어느 단일 서브시스템이 아니다. 그것들은
모두 아래의 선행 노드로 이미 존재한다. 요점은 **조합(composition)**이다. 데이터
모델은 [[document-model]]이다: 레코드는 스키마가 유연한 문서(**BSON**, 바이너리
JSON으로 인코딩)로서 *컬렉션(collection)*으로 묶이며, 관련 데이터를 정규화하는
대신 내장(embedding)한다. 저장 엔진인 **WiredTiger**는 컬렉션과 인덱스를
[[b-tree]]에 보관하고, 동시 연산을 [[mvcc]] 스냅숏으로 격리하며, 쓰기를
[[write-ahead-logging]] **저널(journal)**로 내구성 있게 만든다. 질의는 보조
[[database-index]]를 통해 문서에 도달하고, v4.0부터는 문서 하나의 원자성으로
부족할 때 다중 문서 ACID [[transaction]]을 쓸 수 있다. 가용성은 **레플리카
셋(replica set)**이다: 논리적 연산 로그(**oplog**)를 통한 리더 기반
[[replication]]과, 수 초 단위로 측정되는 과반수 투표 [[leader-election]]에 의한
장애 조치. 수평 확장은 [[sharding]]이다: 컬렉션이 샤드 키에 따라 청크로 나뉘어
여러 레플리카 셋에 걸쳐 배치되고, 프런트엔드(`mongos`)가 라우팅한다. *MongoDB*란
바로 이 특정한 묶음이다 — B-tree 저장 위의 문서 모델, 그 아래의 MVCC + 저널,
그 곁의 레플리카 셋, 그 위의 샤딩 — 각 계층의 보장이 정확히 다음 계층이
가정하는 것이 되도록 조립된 것.

## 상세 설명

### 왜 MongoDB는 부분들의 합이 아니라 독자적인 노드인가

아래의 모든 선행 개념은 많은 시스템이 공유하는 일반적인 메커니즘이다. "MongoDB"
노드가 가르치는 것은 **통합(integration)** — 각 설계 갈림길에서 이 시스템이
어느 가지를 택하는지, 그리고 그 선택들이 왜 서로를 강화하는지다:

- PostgreSQL이 관계형 테이블과 조인을 핵심에 두는 곳에서, MongoDB는
  [[document-model]]의 내장 레코드를 둔다 — 한 번의 페치로 읽는 트리 모양의
  데이터가 흔한 경우라는 데 거는 것이다.
- 그 내기는 아래로 파급된다: 레코드 전체가 *하나의* 문서에 산다는 것은 단일
  문서 쓰기가 이미 의미 있는 원자적 단위라는 뜻이고, 그래서 MongoDB는 여러 해
  동안 문서 단위 원자성만으로 운영되다가 다중 문서 [[transaction]]을
  늦게(v4.0), 규칙이 아니라 예외로서 추가했다.
- 옆으로도 파급된다: [[sharding]]은 각 문서를 통째로 하나의 샤드에 배치할 수
  있으므로, 지배적인 읽기 — 키로 문서 하나 가져오기 — 는 샤드를 결코 가로지르지
  않는다; 그리고 [[replication]]은 oplog를 통해 문서 전체 단위의 연산을 깔끔하게
  실어 나른다.

*같은* 부품들의 다른 조합(예컨대 보조 인덱스 없는 해시 분할 키-값 레코드, 또는
MVCC를 가진 관계형 엔진)은 다른 데이터베이스다. MongoDB는 *이* 조합이다.

### 부품들, 그리고 각각이 맡는 역할

- **데이터 모델 — [[document-model]].** 데이터는 문서들의 컬렉션이다: 중첩되고
  스키마가 유연한 필드-값 쌍의 트리로, 정규화되는 대신 내장된다. 구체적인
  인코딩은 **BSON**이다 — 추가 타입(날짜, ObjectId, 바이너리)과 빠른 순회를
  위한 길이 접두 필드를 가진 바이너리 JSON — 이는 모델의 구현 세부이지 별도의
  아이디어가 아니다. 모든 문서는 고유한 `_id`, 즉 기본 키를 지닌다.

- **저장 엔진 — [[b-tree]] + [[mvcc]] + [[write-ahead-logging]]을 조합하는
  WiredTiger.** WiredTiger는 MongoDB의 기본 저장 엔진이다 — 새로운 메커니즘이
  아니라 기존 세 가지의 패키지다. 각 컬렉션과 각 인덱스는 [[b-tree]]다(문서는
  `_id`를 키로 하는 컬렉션의 트리에 저장된다). 동시 연산은 [[mvcc]]로부터
  **스냅숏 격리(snapshot isolation)**를 얻는다: 갱신은 문서의 새 버전을 쓰고
  독자는 자신의 스냅숏 위에서 계속한다 — 독자는 결코 기록자를 막지 않으며,
  충돌 입도는 테이블 수준이 아니라 문서 수준이다. 내구성은 **저널**, 고전적인
  [[write-ahead-logging]] 로그다: 변경은 순차 저널에 덧붙여지고 fsync되며,
  B-tree 페이지 자체는 체크포인트에서 게으르게 플러시된다; 크래시 복구는 마지막
  체크포인트 이후의 저널을 재생한다.

- **접근 경로 — [[database-index]].** `_id`를 지정하지 않는 질의는 컬렉션을
  스캔하게 될 것이다; 보조 [[database-index]](그 자체로 B-tree이며, 어떤 필드의
  값을 그 값을 가진 문서로 사상한다)가 O(log N) 조회를 회복시킨다 — 내장 필드와
  배열 *안으로* 들어가는 인덱스(`"author.name"`, 멀티키 인덱스)를 포함해서,
  고전적 메커니즘에 가해진 문서 모델식 변주다. 언제나처럼 각 인덱스는 모든
  쓰기에 세금을 물린다.

- **작업 단위 — [[transaction]].** *단일* 문서에 대한 쓰기는 — 아무리 깊게
  중첩되었더라도 — 그 자체로 원자적이다: 문서는 하나의 B-tree 값, 하나의 MVCC
  버전, 하나의 저널 레코드다. [[document-model]]이 관계형 스키마라면 여러
  테이블로 쪼갰을 것을 내장하기 때문에, 이 단일 문서 원자성이 이미 대부분의
  워크로드를 커버한다 — 모델의 선택이 *곧* 동시성 제어의 선택이다. 여러 문서가
  함께 변해야 할 때(두 계좌 문서 사이의 이체)는, 다중 문서 ACID
  [[transaction]](v4.0+, 샤드 간은 v4.2+)이 WiredTiger 스냅숏 위에서
  커밋-또는-롤백을 제공한다.

- **가용성 — 레플리카 셋: [[replication]] + [[leader-election]].** **레플리카
  셋**은 MongoDB의 배포 단위다: 하나의 **프라이머리**가 모든 쓰기를 받고,
  **세컨더리**들이 리더 기반 [[replication]]으로 이를 재생한다. 복제 로그는
  **oplog** — *논리적* 연산들의 캡드 컬렉션("컬렉션 `orders`에서 문서 `_id=…`의
  필드 `status`를 설정하라") — 이다. oplog는 WiredTiger 저널이 **아니다**:
  저널은 한 노드의 저장 엔진을 크래시 복구하기 위한 *물리적*
  [[write-ahead-logging]] 기록이고, oplog는 다른 노드들이 재생하는 *논리적*
  변경 스트림이다. 따라서 하나의 쓰기는 서로 다른 두 보장을 위해 **두** 로그
  모두에 착지한다. **쓰기 우려(write concern)** 손잡이(`w:1` 대
  `w:"majority"`)는 클라이언트에 확인 응답하기 전에 몇 개의 레플리카가 oplog
  항목을 보유해야 하는지를 정한다. 프라이머리가 죽으면 세컨더리들이 과반수 투표
  [[leader-election]](텀을 가진 Raft류 프로토콜; oplog가 낡은 후보는 거부된다)을
  치르고 새 프라이머리가 수 초 안에 재개한다.

- **수평 확장 — [[sharding]].** 하나의 레플리카 셋이 데이터를 담거나 쓰기를
  흡수할 수 없을 때, 컬렉션은 **샤드 키(shard key)**에 따라 **청크(chunk)**
  (연속적인 키 범위 — 또는 키의 해시 범위로, MongoDB는 분할 함수의 범위/해시
  쌍을 정확히 그대로 제공한다)로 샤딩되고, 각 청크는 하나의 **샤드**가 소유한다.
  각 샤드는 그 자체로 완전한 레플리카 셋이다 — 샤딩과 복제는 직교적으로
  조합된다. 라우터 프로세스 **mongos**가 청크 맵(구성 서버에 영속화됨)을 보유한다:
  샤드 키를 지정하는 질의는 하나의 샤드로 가고; 나머지는 흩뿌렸다
  모은다(scatter/gather). **밸런서(balancer)**가 샤드가 고르지 않게 자라면
  청크를 이주시킨다.

### 동작 예시 — 쓰기 하나가 모든 부품을 끝까지 통과한다

승차 호출 앱이 각 주문을 샤딩된 `orders` 컬렉션의 문서 하나로 저장한다(샤드 키
`city`, 해시; 각 샤드는 3-멤버 레플리카 셋; `status`에 보조 [[database-index]]).
서울에서 기사가 주문 `"o-42"`를 수락하고, 앱은 `w:"majority"`로 다음을 실행한다:

```js
db.orders.updateOne({ _id: "o-42", city: "Seoul" },
                    { $set: { status: "accepted", driver: "d-7" } })
```

1. **[[sharding]]이 라우팅한다.** 질의가 샤드 키를 지정하므로 `mongos`는
   `"Seoul"`을 해시하고, 청크 맵에서 이 해시 범위가 **샤드 B**의 것임을 찾아
   갱신을 샤드 B의 레플리카 셋으로 전달한다 — 접촉한 샤드는 하나, 건드리지 않은
   샤드는 둘.
2. **[[replication]]이 받는다.** 샤드 B 안에서 쓰기는 **프라이머리**만 할 수
   있다; `mongos`는 갱신을 거기로 전달한다.
3. **[[document-model]] + [[transaction]]이 변경의 범위를 정한다.** 주문 —
   탑승자, 경로, 요금, 상태 — 은 *하나의* 내장 문서이므로 이 갱신은 **단일 문서
   원자적 쓰기**다: 두 `$set` 필드는 함께 반영되거나 전혀 반영되지 않는다. 다중
   문서 트랜잭션은 필요 없다; 데이터 모델이 흡수했다.
4. **WiredTiger가 적용한다: [[b-tree]] + [[mvcc]].** 프라이머리는 컬렉션의
   [[b-tree]]를 따라 문서까지 내려가고(몇 번의 페이지 읽기), [[mvcc]]에 따라
   `status: "accepted"`를 가진 **새 버전**을 쓴다 — 더 오래된 스냅숏 위에서
   주문들을 순회하는 대시보드 질의는 여전히 `"assigned"`를 보며, 막히지 않는다.
   `status` [[database-index]] B-tree가 갱신된다(문서가 `"assigned"` 키에서
   `"accepted"` 키로 옮겨진다).
5. **[[write-ahead-logging]]이 내구성을 만든다 — 두 번, 두 가지 이유로.** 변경은
   WiredTiger의 **저널**(물리적 WAL, fsync됨; B-tree 페이지는 다음 체크포인트에서
   게으르게 플러시)에 덧붙여지고, 논리적 **oplog** 항목("orders: `_id: o-42`의
   status/driver 설정")으로 기록된다.
6. **과반수 확인 응답.** 세컨더리들이 oplog 항목을 끌어와 적용한다; 한
   세컨더리가 확인하면 — 3 중 2 멤버가 보유 — 프라이머리가 확인 응답하여
   `w:"majority"`를 충족한다. 다음 순간 프라이머리의 머신이 죽어도, 확인 응답된
   것은 아무것도 잃지 않는다.
7. **[[leader-election]]이 장애를 흡수한다.** 실제로 죽었다고 하자: 두
   세컨더리가 하트비트 타임아웃을 겪고, 텀 번호가 매겨진 과반수 투표를
   치르며(6단계의 oplog 항목을 보유한 쪽이 자격이 있다; 낡은 멤버는 거부될
   것이다), 승자가 프라이머리로 재개한다. `mongos`는 앱의 다음 쓰기를 새
   프라이머리에 재시도한다. 앱이 본 것은 수 초의 비가용성과 0의 데이터 손실이다.

**구조**는 B-tree 안의 BSON 문서 하나, 그 MVCC 버전 사슬, 그리고 그 인덱스
항목들이다; **알고리즘**은 *샤드 키로 라우팅 → 프라이머리 → 원자적 문서 갱신 →
저널 + oplog → 과반수 복제 → (필요 시 장애 조치)*다; **기질(substrate)**은 샤드당
세 대 곱하기 N개의 샤드로, 각각 메모리에 더러운 B-tree 페이지와 디스크에 두 개의
로그를 가진다. 그 한 번의 추적된 갱신 — 각 선행 개념이 정확히 자기 일 하나씩을
하는 — 이 *곧* MongoDB다: 어느 한 부품이 아니라, 통합이.

## 선행 개념

- [[document-model]] — MongoDB의 데이터 모델: 컬렉션 안의 스키마 유연한 내장
  BSON 문서; 단일 문서 원자성이 대부분의 워크로드를, 단일 샤드 배치가 대부분의
  읽기를 커버하게 만드는 선택.
- [[b-tree]] — WiredTiger의 저장 구조: 모든 컬렉션과 인덱스는 팬아웃이 큰 균형
  트리이므로, 점 조회는 몇 번의 페이지 읽기면 된다.
- [[database-index]] — 문서 필드(내장 및 배열 필드 포함)에 대한 보조 접근 경로;
  모든 쓰기에 추가 작업이라는 대가를 치르고 O(log N) 필터를 얻는다.
- [[mvcc]] — WiredTiger의 격리: 갱신은 독자의 스냅숏에 대비해 새 문서 버전을
  쓰므로, 독자는 결코 기록자를 막지 않는다 — 문서 수준 입도로.
- [[write-ahead-logging]] — 두 번 나타나는 내구성 메커니즘: WiredTiger
  **저널**(물리적, 한 노드를 크래시 복구)과, 같은 로그-후-적용 원리에 따라,
  복제가 실어 나르는 oplog.
- [[transaction]] — ACID 작업 단위: 기본적으로 암묵적이고 단일 문서(문서 모델의
  배당금)이며, 여러 문서가 함께 커밋해야 할 때는 v4.0부터 명시적 다중 문서
  트랜잭션.
- [[replication]] — 레플리카 셋의 엔진: 논리적 oplog를 통한 리더 기반 복제와,
  지연 시간을 장애 조치 시 내구성과 맞바꾸는 쓰기 우려 손잡이.
- [[leader-election]] — 자동 장애 조치: 과반수 투표, 텀 번호가 매겨진
  선거(Raft류)가 최신 상태의 세컨더리를 수 초 안에 승격시켜, 사람 없이 단일
  기록자 불변식을 지킨다.
- [[sharding]] — 수평 확장: 컬렉션이 샤드 키(범위 또는 해시)에 따라 청크로
  나뉘어 레플리카 셋들에 걸쳐 분할되고, mongos가 라우팅하며, 밸런서가 재균형한다.
