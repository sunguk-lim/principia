# NCCL

## 요약

**NCCL**(NVIDIA Collective Communications Library)은 다중 GPU [[collective-operation]]을
구현하는 **소프트웨어 라이브러리**다 — 그 대표 예가 [[all-reduce]]로, 모든 GPU가 하나의 값
(자신의 그래디언트)을 제공하면 그 값들이 합산되고 동일한 총합이 모든 GPU에 다시 전달된다.
NCCL은 하나의 전선(wire)도 아니고 더 빠른 전선의 버전도 아니다. 그것은 *누가 어떤 바이트를
누구에게, 어떤 순서로 보낼지*를 결정하는 **알고리즘 및 오케스트레이션 계층**이며, 이렇게
결정된 트래픽을 이용 가능한 가장 빠른 인터커넥트 위로 흘려보낸다 — 한 박스 안 GPU들 사이라면
[[nvlink]], 서로 다른 머신들 사이라면 네트워크 링크가 그것이다. NCCL의 대표적 기여는
**링 올리듀스(ring all-reduce)** 알고리즘으로, 모든 링크가 고르게 부하를 받으며 병렬로
동작하도록 올리듀스를 수행하는 방법이며, 이를 통해 데이터를 결합하는 비용이 참여 GPU 수와
거의 무관해진다.

## 상세 설명

### NCCL이란 무엇이고, 어느 계층을 차지하는가

[[nvlink]] 노드는 문제의 형태로 끝을 맺었다: 모델이 여러 GPU에 걸쳐 분할되면, 그 GPU들은
자신들의 조각을 계속해서 다시 결합해야 하며, CPU를 우회하는 넓은 전선이 있어야 이 재결합이
머신 전체를 스로틀링하지 않는다. 하지만 전선은 두 종단점 사이에서 바이트를 옮길 뿐, "이
여덟 개의 그래디언트를 합산해서 모두에게 총합을 주라"는 개념을 전혀 알지 못한다. 무언가가
그것을 *결정*해야 한다 — 집단 연산(collective operation)을 점대점(point-to-point) 송수신의
정밀한 스케줄로 쪼개고, 올바른 순서로 발행하고, 도착하는 숫자들을 결합해야 한다. 그 무언가가
바로 **NCCL**이다.

따라서 NCCL과 [[nvlink]]는 **대안 관계가 아니라 계층 관계**다. [[nvlink]]는 물리적
전송계층이다 — 원시 바이트를 실어 나르는 전선. NCCL은 CPU에서 실행되는 라이브러리로,
전체 GPU에 걸친 [[all-reduce]] 같은 요청이 주어지면 데이터 이동을 계획하고, 실제로 로컬
GPU 메모리에서 값을 읽고 전선을 건너 이웃에게 바이트를 밀어 넣고 도착한 것을 더하는 작은
GPU 프로그램(보조 *커널* — 짧은 루틴)들을 실행시킨다. CPU 자체는 대용량 데이터를 결코
건드리지 않는다. CPU는 **디스패처**로서 실행(launch) 및 동기화 명령만 작성한다. 바이트는
전선을 통해 GPU에서 GPU로 흐른다. 이 구분을 붙잡아 둘 유용한 방법은 이렇다: NVLink 혼자는
*그저 바이트*일 뿐이며 그 의미를 알지 못한다. NCCL은 그 바이트가 여덟 개의 그래디언트이며
하나의 합으로 합쳐져야 함을 알고, 그렇게 만드는 송수신을 오케스트레이션하는 존재다.

이러한 분리 덕분에 NCCL은 이식성도 갖는다. "그래디언트를 결합하라"는 *동일한* 요청은
GPU들이 [[nvlink]]로 배선된 한 서버 안에 있든, 보통의 호스트 버스(흔히 PCIe로, 한 자릿수
느림)만을 공유하든, 아니면 InfiniBand 같은 데이터센터 네트워크로 연결된 *서로 다른 머신*에
있든 변경 없이 실행된다. NCCL은 시작 시점에 하드웨어를 탐색하여 각 GPU 쌍이 도달할 수 있는
가장 빠른 전송계층을 선택하고, 그 위에서 동일한 알고리즘을 실행한다. 학습 코드는 "그래디언트를
올리듀스하라"고 말할 뿐이며, NCCL은 가능할 때 그것을 조용히 [[nvlink]] 위로 라우팅한다 —
프로그램은 전혀 알아채지 못하고, 그저 더 빨라지거나 느려질 뿐이다.

### 순진한 올리듀스가 왜 전선을 낭비하는가

NCCL에게 결정적인 질문은 [[all-reduce]]를 *어떻게* 잘 수행할 것인가이다. [[all-reduce]]에서
보았듯이, *의미상으로는* 리듀스한 뒤 브로드캐스트하는 것이다: 모든 GPU의 값을 하나의 결과로
결합한 다음, 그 결과를 모두에게 전달한다. 가장 명백한 구현은 이를 그대로 실행에 옮긴다: 한
GPU를 수집자(gatherer)로 정하고, 다른 모든 GPU가 자신의 데이터를 그곳으로 보내게 하고, 거기서
합산한 다음, 총합을 모두에게 다시 보낸다.

이는 정확하지만 하드웨어를 낭비한다. 모든 바이트가 그 한 수집자의 단일 링크로 몰리므로 그
링크가 병목이 되는 동안 나머지 *모든* 다른 링크는 놀고 있다. GPU가 많고 그래디언트가 크면
전체 연산이 하나의 전선 위로 직렬화된다 — [[nvlink]]가 벗어나고자 했던 바로 그 단일 파이프
병목이, 이번에는 빠른 전선임에도 나쁜 *알고리즘* 때문에 재도입되는 것이다. 전송계층의 링크
중 하나만 바쁘다면 그 빠른 전송계층은 낭비된다. 진짜 공학적 문제는 따라서 다음과 같다:
**모든** 링크가 **동시에** 데이터를 나르도록, 그리고 어느 것도 병목이 되지 않도록 전송을
스케줄링하는 것.

### 링 올리듀스: 알고리즘

NCCL의 답은 **링 올리듀스(ring all-reduce)**다. 참여하는 `N`개의 GPU를 논리적 **링(ring)**으로
배치한다 — `GPU 0 → GPU 1 → GPU 2 → … → GPU (N−1) → GPU 0` — 여기서 각 GPU는 정확히 하나의
*후속(successor)* 대상에게 보내고 하나의 *선행(predecessor)*으로부터 받는다. 각 GPU의 데이터를
`N`개의 동일한 **청크(chunk)**로 나누되, 링의 위치마다 하나씩 배정한다. 그러면 연산은 두
단계로 진행된다.

**단계 1 — [[reduce-scatter]].** 이 단계가 끝나면 각 GPU는 전체 결과가 아니라 **하나**의
청크(GPU마다 다른 청크)에 대한 *완전한 합*을 보유하게 된다. 이는 `N−1`단계가 걸린다. 각
단계마다 모든 GPU는 동시에 하나의 청크를 후속 GPU로 보내고 선행 GPU로부터 하나의 청크를
받아, 받은 청크를 자신이 이미 보유한 대응 청크에 **더한다**. GPU들이 엇갈려 시작하기 때문에
— 각자 다른 청크 인덱스를 보내는 것부터 시작 — 부분합은 이동하면서 누적된다: 하나의 청크는
매 홉(hop)마다 GPU 하나의 기여분을 더 얻는다. `N−1`번의 홉 후, 각 청크는 모든 `N`개의 GPU를
방문하고 각 GPU에서 합산되었으므로, 그 청크의 누적이 최종적으로 머무는 GPU는 **완전히
합산된** 값을 보유하게 된다. 핵심 불변식은 이렇다: *매 단계마다 `N`개의 링크 전부가 청크를
나르고 있고 `N`개의 GPU 전부가 더하고 있다* — 어떤 링크도 놀지 않고, 어떤 것도 한 노드로
몰리지 않는다.

**단계 2 — [[all-gather]].** 이제 완전히 합산된 청크들은 GPU 하나당 하나씩 흩어져 있고,
모두가 *전부*를 필요로 한다. 이는 [[all-reduce]]의 브로드캐스트 절반으로, 같은 링을 따라
또 다른 `N−1`단계로 이루어진다. 각 GPU는 자신이 소유한 완성된 청크를 후속 GPU로 보내고,
그 GPU는 이를 저장한 뒤 앞으로 전달한다. `N−1`번의 홉 후 완성된 청크 각각이 모든 GPU를
순환했다. 여기서는 덧셈이 일어나지 않는다 — 청크들은 이미 완성되어 있고, 단지 복사되어
돌아갈 뿐이다. 끝에 가면 **모든 GPU가 완전히 합산된 청크 전부**를 보유하게 된다 — 즉 합산된
전체 결과 — 이것이 정확히 [[all-reduce]]의 결과다: 동일하게 결합된 값이 모든 GPU에 놓이는 것.

### 왜 대역폭 최적인가

두 가지 속성이 링 올리듀스를 효율적인 선택으로 만들며, 둘 다 "모든 링크를 바쁘게 유지하라"는
목표로 거슬러 올라간다.

첫째, **고른 부하 분산과 병렬성**. 두 단계 모두의 모든 단계에서, 각 GPU는 하나의 청크를
보내고 하나의 청크를 받으며, 모든 링크가 동시에 작동한다. 중앙 수집자가 없으므로 어떤 단일
링크도 병목이 되지 않는다 — 작업이 링 전체에 균일하게 분산된다.

둘째, 그리고 이것이 이 방식이 *확장*되는 이유인데, 각 GPU가 옮기는 바이트 수를 세어 보자.
한 GPU의 전체 데이터 크기를 `S`라 하면 각 청크는 `S/N`이다. 각 GPU는 리듀스-스캐터의
`N−1`단계와 올게더의 `N−1`단계에 걸쳐 단계마다 하나의 청크를 보낸다 — 즉 크기 `S/N`인
청크를 `2 × (N−1)`개 보내는 셈이다. 이는 GPU당 `2 × (N−1)/N × S` 바이트다. `N`이 커질수록
`(N−1)/N` 계수는 1에 가까워지므로, 각 GPU는 최대 약 `2S` — *GPU가 몇 개나 참여하든 자신의
데이터 양의 약 두 배*만 옮기게 된다. 이것이 정당화가 필요한 "마법처럼 보이는" 비직관적
성과다: 순진한 방식은 수집자가 대략 `N × S` 바이트(클러스터와 함께 증가)를 옮기게 만드는
반면, 링은 GPU당 트래픽을 `N`과 무관하게 `2S` 근처로 제한한다. 이는 데이터가 `N`개의
청크로 잘게 나뉘고 작업이 한 노드에 쌓이는 대신 링 전체에 걸쳐 공유되기 때문이다. 이를
느린 호스트 버스가 아니라 [[nvlink]]의 초당 수백 기가바이트급 링크 위에서 실행하는 것과
결합하면, 데이터 병렬 학습이 *매 스텝마다* 수행해야 하는 그래디언트 결합은 더 이상 실행을
스로틀링하는 요인이 되지 않는다.

### 구체적 사례: 4개 GPU가 그래디언트를 결합하는 경우

**`N = 4`개의 GPU**를 상정하며, 각각 네 숫자로 이루어진 그래디언트 벡터를 보유한다고
하자(GPU당 청크 하나씩, 즉 여기서는 청크 = 숫자 하나로, 모든 덧셈이 눈에 보이도록 작게
유지했다). 청크를 위치별로 `a,b,c,d`라 부르자:

- `GPU0 = [a0, b0, c0, d0] = [1, 2, 3, 4]`
- `GPU1 = [a1, b1, c1, d1] = [5, 6, 7, 8]`
- `GPU2 = [a2, b2, c2, d2] = [9, 10, 11, 12]`
- `GPU3 = [a3, b3, c3, d3] = [13, 14, 15, 16]`

올바른 올리듀스 결과는 **모든** GPU에서의 위치별 합이다: `a = 1+5+9+13 = 28`,
`b = 2+6+10+14 = 32`, `c = 3+7+11+15 = 36`, `d = 4+8+12+16 = 40`, 즉 모든 GPU가 결국
`[28, 32, 36, 40]`에 도달해야 한다. 링은 `0 → 1 → 2 → 3 → 0`이다. 총 단계 수는
`2 × (4−1) = 6`이다 — 리듀스-스캐터 세 번, 올게더 세 번. GPU1에 완전히 합산된 채로
안착하도록 예정된 청크 `a`를 따라가 보자.

**리듀스-스캐터, 1단계.** GPU0가 `a0 = 1`을 GPU1로 보낸다. GPU1은 이를 자신의
`a1 = 5`에 더해 `a = 1+5 = 6`을 얻는다. (동시에 GPU1은 `b1`을 GPU2로, GPU2는 `c2`를
GPU3로, GPU3는 `d3`를 GPU0로 보낸다 — 모든 링크가 바쁘고, 모든 GPU가 덧셈을 수행한다.)

**리듀스-스캐터, 2단계.** GPU1은 진행 중인 `a = 6`을 GPU2로 넘긴다. GPU2는 자신의
`a2 = 9`를 더해 `a = 6+9 = 15`를 얻는다.

**리듀스-스캐터, 3단계.** GPU2는 `a = 15`를 GPU3로 보낸다. GPU3는 자신의 `a3 = 13`을
더해 `a = 15+13 = 28`을 얻는다. 청크 `a`는 이제 네 GPU를 모두 방문했고 각 지점에서
합산되었다. 엇갈린 스케줄에 따라 그것은 알고리즘이 의도한 위치에 안착했고, GPU3는 인계
과정에서 한 홉을 더 전달하여 **GPU1이 완성된 `a = 28`을 소유**하게 된다 — 위에서 손으로
계산한 `28`과 정확히 일치한다. 같은 엇갈린 과정에 의해 동시에 GPU2는 완성된 `b = 32`를,
GPU3는 완성된 `c = 36`을, GPU0는 완성된 `d = 40`을 보유하게 된다. 이제 각 GPU는 정확히
**하나**의 완성된 청크를 소유한다 — 리듀스-스캐터의 불변식이다.

**올게더, 4~6단계.** 이제 이 네 개의 완성된 숫자를 같은 링을 따라 순환시켜 모두가 넷
전부를 얻도록 한다. 4단계: 각 소유자가 자신의 완성된 청크를 후속 GPU로 보낸다(GPU1은
`a = 28`을, GPU2는 `b = 32`를 넘기는 식으로). 수신자는 이를 저장한다. 5단계와 6단계는
각 청크를 한 홉씩 더 전달한다. 세 번의 홉 후, `a = 28`, `b = 32`, `c = 36`, `d = 40`이
각각 네 GPU 모두에 도달했다. 이제 모든 GPU가 `[28, 32, 36, 40]` — 동일하게 합산된
그래디언트 — 를 보유한다.

이 사례는 비퇴화적이다: 네 GPU 모두가 참여하고, 모든 청크 인덱스가 사용되며, 두 단계
모두 전체 `N−1 = 3`단계를 실행하고(어느 단계도 0으로 축소되지 않는다), 덧셈은 어느 항도
시작 값에 머무르지 않고 실제로 홉을 거쳐 누적된다. [[nvlink]] 위에서 실행하면, 네 링크
각각이 매 단계마다 병렬로 하나의 청크를 나른다 — 어느 것도 놀지 않고, 어느 것도 병목이
되지 않는다 — 이것이 정확히 이 방식을 효율적으로 만드는 고른 부하 분산 속성이다.

### 결론

NCCL은 다중 GPU 집단 연산을 위한 **라이브러리 및 알고리즘 계층**이다. 그 핵심 임무는
[[all-reduce]] 같은 요청을 균등하게 균형 잡힌 송수신 및 덧셈의 구체적 스케줄로 바꾼 다음
그 스케줄을 빠른 전송계층 위에서 실행하는 것이다. 대표적 기법인 **링 올리듀스**는
인터커넥트의 모든 링크를 동시에 바쁘게 유지하고 클러스터 크기와 무관하게 GPU당 트래픽을
자신의 데이터 양의 약 두 배로 제한한다 — 그래서 GPU가 늘어나도 그래디언트 결합 비용이
더 비싸지지 않는다. NCCL은 *무엇을 할지*를 제공하고, [[nvlink]]는 *그것이 실행되는 전선*을
제공한다. 함께 — "NVLink 위의 NCCL" — 이들은 데이터 병렬 학습이 매 스텝 반복하는
그래디언트 결합을 충분히 빠르게 만들어, 다중 GPU 머신이 통신 대기로 멈추지 않고 계속
바쁘게 돌아가도록 한다.
