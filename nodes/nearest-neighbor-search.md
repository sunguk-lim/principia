# Nearest-Neighbor Search

## Summary

**Nearest-neighbor search** answers one question over a stored collection: *given a query, which stored items are most similar to it?* Each item is held as an [[embedding]] — a vector whose position encodes meaning — and "most similar" is scored by [[cosine-similarity]], how nearly two vectors point the same way. The search returns the $k$ stored vectors whose similarity to the query is highest: the *k nearest neighbors*. It is the retrieval primitive that turns a pile of embeddings into search-by-meaning. The catch is cost: scoring every stored vector is correct but slow, so at scale one builds an **index** that finds nearly the same answer while comparing the query against only a tiny fraction of the collection.

## Grounded explanation

Begin with what the search is *for*. Suppose every sentence or item you care about has already been turned into an [[embedding]]: a dense vector — an ordered list of a few hundred to a couple thousand real numbers — produced by a trained network so that things with similar meaning land at nearby points in the vector space. You hold a large *collection* of these, say $N$ of them, one per stored item. Now a query arrives — itself a sentence — and you embed it the same way, producing a *query vector*. The task is to find the stored items whose meaning is closest to the query's, and because meaning has been turned into position, "closest in meaning" becomes "closest in the space." This is **nearest-neighbor search**: the central object is the collection of stored vectors plus a query, and the contribution is a ranked answer — the $k$ stored items most similar to the query — where $k$ is a small number you choose (the top 5, the top 10).

To rank, we need a single number saying how similar two vectors are, and the standard choice is [[cosine-similarity]]: the measure of how nearly two vectors point in the same direction, equal to $+1$ for perfectly aligned vectors, $0$ for perpendicular (unrelated) ones, and $-1$ for opposing ones — and, crucially, independent of how long either vector is. Independence from length is what makes it the right scorer here: two items about the same topic should count as similar whether their vectors came out long or short. So "the nearest neighbors of the query" means, precisely, *the stored vectors with the highest cosine similarity to the query vector.* The phrase "nearest" comes from thinking geometrically — a high cosine similarity is a small angle, hence a near direction — but the operational definition is just: rank by that score, keep the top $k$.

**The obvious method, and why it eventually fails.** The direct way to do this is **exact** nearest-neighbor search: walk through all $N$ stored vectors, compute the cosine similarity of each one to the query, and sort to take the top $k$. This is correct — it cannot miss a true neighbor, because it literally looked at every candidate. Its cost is the problem. Each query touches all $N$ vectors, so the work grows *linearly* with the collection — written $O(N)$, meaning "proportional to $N$." With a thousand stored vectors that is nothing; with ten million, every single query must score ten million vectors, and if many queries arrive per second the machine cannot keep up. The key tension of the whole topic lives here: searching by meaning at scale means you cannot afford to re-score the entire collection on every query.

**The insight that resolves it.** Notice what exact search wastes. Most stored vectors are nowhere near the query — they point in wildly different directions — and yet exact search dutifully scores every one of them, every time. If we could *rule out* the obviously-distant vectors without scoring them, we would only pay for the few plausible candidates. That is the idea behind **approximate nearest-neighbor** search, usually abbreviated **ANN**. Before any queries arrive, you do one-time work over the collection to build an **index**: an auxiliary data structure that organizes the stored vectors by their layout in the space, so that at query time it can *prune* — skip whole regions of the collection — and hand back a small candidate set to score. The query then costs *sub-linear* time: it grows much slower than $N$ (often like $\log N$, the number of times you can halve $N$ — which for ten million is only about 23). The word **approximate** names the price: because the index examined only a slice of the collection, it can occasionally miss a true top-$k$ neighbor that happened to sit in a pruned region.

This sets up the defining trade-off, which is *tunable*. **Recall** is the fraction of the true nearest neighbors the approximate search actually returns — recall $1.0$ means it found them all, recall $0.95$ means it missed one in twenty. Index parameters let you slide along a curve: search more candidates and recall climbs toward exact while queries slow down; search fewer and queries get faster while recall drops. The whole bargain of ANN is to accept a tiny, controlled loss of accuracy in exchange for orders-of-magnitude speed — a worthwhile trade precisely because, in meaning-based retrieval, the difference between the true 5th-best match and the 6th-best is usually immaterial, while the difference between a 1-millisecond and a 1-second query is decisive.

**How an index prunes, concretely.** Two families dominate, and both turn on the same trick of *not looking everywhere*. One family **clusters** the collection: group the stored vectors into, say, a few thousand cells, each represented by a single average vector. At query time you score only the handful of cell-averages, pick the few cells whose average is most similar to the query, and then score only the vectors inside those cells — perhaps a few thousand instead of ten million. Everything in the unvisited cells is pruned untouched; you might miss a neighbor sitting just across a cell boundary, which is exactly where recall leaks. The other family builds a **navigable graph**: link each stored vector to a few of its nearest fellows, so the collection becomes a network you can walk. A query enters at some node and repeatedly hops to whichever neighbor-of-the-current-node is closer to the query, the way you would home in on an address by always stepping toward it. Within a logarithmic number of hops you arrive in the query's neighborhood, having examined only the nodes along your path — not the whole graph. Both families pay the same way: a one-time cost to build the structure, extra memory to store it, and a small chance of missing a true neighbor in return for query work that scales like $\log N$ instead of $N$.

**Worked instance.** Take a store of $N = 10{,}000{,}000$ sentence [[embedding]]s, and the query *"a small cat."* First embed the query into a vector $q$. **Exact search**: score $q$ against all ten million stored vectors by [[cosine-similarity]] and sort. Suppose the stored sentence *"a kitten on the rug"* has embedding $r$ with cosine similarity $0.91$ to $q$, the highest of any stored vector; *"a small dog naps"* scores $0.78$; *"quarterly revenue rose 4%"* scores $0.02$. Exact search ranks them and returns *"a kitten on the rug"* as the top-1 neighbor — having performed all ten million comparisons. **ANN with a navigable-graph index**: enter the graph at some node, and at each step hop to the linked vector with higher cosine similarity to $q$. Starting far away you might pass through a node at similarity $0.20$, hop to one at $0.55$, then $0.83$, then arrive at $r$ at $0.91$, where no linked neighbor scores higher and the walk stops. About $\log_2(10{,}000{,}000)\approx 23$ hops, each checking only a few links — on the order of a hundred comparisons total, versus ten million. The answer is the same — *"a kitten on the rug"* — reached by checking roughly $0.001\%$ as many vectors. The approximation shows its teeth only in the rare case where the true best vector was reachable solely through a node the walk never visited; then ANN returns the close-but-second-best instead, the recall cost of never having looked everywhere.

So nearest-neighbor search is the bridge from representation to retrieval. An [[embedding]] makes meaning into a position and [[cosine-similarity]] makes closeness into a number; nearest-neighbor search is the operation that, given a query position, *finds* the nearest stored positions — exactly when the collection is small, approximately and far faster when it is large. The structural fact to carry away is the cost progression: exact search is $O(N)$ and unmissable; an ANN index trades a sliver of recall for sub-linear query time, and that trade is what makes search-by-meaning practical over millions of vectors.
