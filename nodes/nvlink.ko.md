# NVLink

## 요약

**NVLink**는 GPU들을 **서로 직접** 연결하는 (그리고 일부 패키지에서는 GPU를 CPU에 직접
연결하는) 전용의 고대역폭·저지연 전선으로, 이를 통해 한 GPU의 메모리에 있는 데이터가 GPU를
호스트 컴퓨터에 연결하는 데 보통 쓰이는 느린 범용 버스를 우회하지 않고 다른 GPU로 이동할 수
있다. 이것이 존재하는 이유는 [[cpu-vs-gpu]] 이야기에 내재된 한계 때문이다: 단일 GPU는
자체 온보드 메모리로부터 수천 개의 산술 레인을 먹임으로써 **처리량**에서 승리하지만, 그
메모리와 레인 수는 *유한*하다. 하나의 GPU에 담기에 너무 큰 모델은 여러 GPU에 나뉘어야 하는데
— 이는 한 칩의 처리량 베팅을 여러 칩의 베팅으로 바꾸는 것이며, 칩들이 자신의 작업 조각을
충분히 빠르게 **교환**할 수 있어야만 이득이 된다. 이 교환을 보통의 호스트 버스(초당 수십
기가바이트) 위에서 실행하면 그것이 병목이 된다: 값비싼 레인들이 데이터를 기다리며 놀게 된다.
NVLink는 이 파이프를 한 자릿수(초당 수백 기가바이트) 넓혀서, 교환이 더 이상 제약이 되지
않고 GPU들이 계속 바쁘게 유지되도록 한다. 랙 규모에서는 NVLink 스위치가 수십 개의 GPU를 하나의
패브릭으로 엮어 거의 하나의 거대한 GPU처럼 동작하게 만든다.

## 상세 설명

### 여러 GPU를 강제하는 한계

[[cpu-vs-gpu]] 노드는 GPU의 베팅을 확립했다: 몇 개의 지연-최적화 코어 대신, 각각 사이클당
한 번의 곱셈이나 덧셈을 하는 수천 개의 단순한 산술 **레인**으로 칩을 채우고, 이를 **고대역폭
온보드 메모리**로부터 먹이며, 대량의 상주 스레드 뒤로 느린 메모리 단계를 숨긴다. 이 베팅은
규칙적이고 데이터-병렬적인 작업에서 **처리량** — 초당 유용한 작업의 총량 — 을 두고 승리한다.

하지만 이 베팅은 물리적 용량에 의해 제한된다. GPU 하나는 고정된 양의 온보드 메모리(수십
기가바이트)와 고정된 레인 수를 갖는다. 큰 신경망 — 그 가중치에 더해 학습 스텝 동안 생성되는
중간 값들 — 은 GPU 하나의 메모리에 담기에 너무 크거나, GPU 하나의 레인으로 받아들일 수 있는
시간 안에 끝내기에 너무 느릴 수 있다. 유일한 해결책은 **작업을 여러 GPU에 나누는** 것이다:
각 GPU에 모델의 한 조각(또는 데이터의 한 조각)을 주고 병렬로 실행시킨다. 이는 GPU의 처리량
확장을 *칩 하나*에서 *여러 칩*으로 확장한다 — 원리상 GPU 여덟 개는 여덟 배의 작업을 한다.

### 작업을 나누는 것이 왜 통신 문제를 만드는가

"원리상"이라는 말은 함정을 숨긴다. 조각들은 독립적이지 않다. 올바른 결과를 만들려면 GPU들은
끊임없이 서로 데이터를 **교환**해야 한다. 세 용어가 이를 구체화한다(각각은 GPU가 보유하는
숫자 덩어리일 뿐이다):

- **활성화(activations)** — 네트워크를 통해 데이터가 흐르면서 계산되는 중간 값들. GPU 0이
  모델의 앞 절반을, GPU 1이 뒤 절반을 보유한다면, GPU 0의 출력 활성화는 계속하기 위해 GPU
  1에게 *넘겨져야* 한다.
- **그래디언트(gradients)** — 모델을 어떻게 조정할지 알려주는, 학습 중에 계산되는 보정
  신호. 각 GPU가 다른 학습 예제를 본다면, 각각은 *동일한* 공유 가중치에 대해 *다른* 그래디언트를
  계산하며, 모든 GPU가 자신의 사본을 동일하게 갱신하도록 그 그래디언트들이 **결합**(합산 후
  다시 공유)되어야 한다.
- **샤딩된 텐서(sharded tensors)** — 여러 GPU에 의도적으로 분산된 하나의 큰 배열 조각들.
  배열 전체를 사용하려면 소유자들로부터 조각들을 모아야 한다.

따라서 모델을 나누는 것은 병렬 연산을 사주지만 **반복되는 청구서**를 발생시킨다: 매 스텝마다
숫자의 큰 덩어리가 한 GPU의 메모리에서 다른 GPU의 메모리로 이동해야 한다. 여러 GPU에 걸친
베팅이 실제로 단일 GPU 기준선을 이기는지 여부는 전적으로 그 이동이 얼마나 빠른가에 달려
있다 — 아직 가질 수 없는 데이터를 기다리는 동안 GPU의 수천 개 레인은 아무것도 하지 않기
때문이다. 놀고 있는 레인은 정확히 GPU가 제공하기 위해 구매된 그 처리량이 버려지는 것이다.

### 병목: 보통의 호스트 버스

데이터는 보통 GPU를 어떻게 빠져나가는가? GPU는 호스트 컴퓨터에 범용 확장 버스로 연결된
주변 장치 카드다 — 디스크와 네트워크 카드를 CPU에 연결하는 것과 같은 종류의 버스다.
(일반적인 이름은 PCIe이며, 세부 사항은 별개의 주제다. 여기서 중요한 것은 그 역할과
속도다.) 이 버스는 CPU와 *그것의* 주변 장치들 사이에서 데이터를 옮기도록 설계된 것이지,
*두 GPU 사이의* 빠른 고속도로가 되도록 설계된 것이 아니다.

이 버스를 통해 GPU A에서 GPU B로 블록을 보내려면, 기본적인 경우 바이트는 A의 메모리에서
위로 올라가 버스를 건너 호스트의 메인 메모리로 갔다가, 다시 버스를 건너 B의 메모리로
내려간다 — CPU가 전송을 중계한다. 두 GPU가 호스트 복사 없이 버스를 건너 서로에게 직접
바이트를 넘기는 더 나은 배치조차도 여전히 **버스의 대역폭에 의해 제한**된다: 실제로는 초당
대략 30~60 기가바이트 정도, 즉 초당 수십 기가바이트 수준이다.

이것을 단일 GPU가 자신의 *자체* 온보드 메모리를 읽는 속도와 비교해 보라 — 초당 **수천**
기가바이트 단위로 측정된다. 작업이 두 GPU에 걸치는 순간, 그 사이의 링크는 시스템 전체에서
가장 느린 부분이 되며, 그것도 큰 폭으로 그렇다. 반복되는 교환 청구서가 가장 좁은 파이프
위에서 지불되므로 교환이 지배하게 된다: GPU들은 서로를 기다리는 데 계산하는 것보다 더 많은
시간을 쓴다. 처리량-최적화된 레인들로 가득한 다중 GPU 머신은 버스 속도로 스로틀링된다.

### NVLink: 호스트 버스를 우회하는 전용 전선

NVLink는 이 병목에 대한 답이다. 이는 GPU 간 트래픽만을 나르기 위해 *오직 그 목적으로*
존재하며 *범용 호스트 버스를 완전히 우회하는*, GPU들 사이에 직접 배선된 전용 구리
링크인 **별도의 물리적 인터커넥트**다. 두 속성이 이를 해결책으로 만든다:

- **높은 대역폭.** NVLink 연결은 초당 수백 기가바이트로 동작한다 — 일반적인 데이터센터
  GPU에서 약 **900 GB/s**로, 호스트 버스의 초당 수십 기가바이트보다 대략 **한 자릿수**
  높다. 제약이었던 파이프가 더 이상 제약이 아닐 때까지 넓어진 것이다.
- **저지연과 CPU 우회.** CPU는 데이터 경로에 있지 않다. 시작 시점에 링크가 구성되고 나면,
  GPU 0에서 실행되는 스레드가 물리적으로 GPU 1의 메모리에 있는 주소를 읽을 수 있고, GPU의
  메모리 시스템이 *그 단일 읽기를 자동으로 NVLink 위로 라우팅한다* — 코드상으로는 로컬
  메모리를 읽는 것과 다를 바가 없어 보인다. 하드웨어는 주소별로 바이트가 로컬인지 다른
  GPU에 있는지를 결정한다. CPU의 역할은 *설정과 오케스트레이션*("GPU들에게 교환하라고
  지시")으로 축소되며, 결코 바이트 자체를 *옮기지* 않는다.

핵심 통찰은 [[cpu-vs-gpu]]에서 나온 것과 같은 처리량 논리를, 이번에는 칩 *내부*의 메모리가
아니라 칩 *사이*의 전선에 적용한 것이다: GPU는 방대한 대역폭과 다수의 진행 중 스레드를
가짐으로써 느린 개별 메모리 페치를 견딘다. NVLink는 **GPU 간** 링크에 그와 동일한 방대한
대역폭을 부여하여, GPU 사이의 교환이 로컬 메모리 지연이 이미 숨겨졌던 것과 같은 방식으로
숨겨질 수 있게 한다 — 모든 레인을 멈추게 하는 노출된 정체로 서 있는 대신 말이다.

### 구체적 사례: 매 스텝 그래디언트를 결합하는 8개 GPU

구체적이고 비퇴화적인 경우를 살펴보자: **하나의 서버 안에 있는 8개 GPU가 하나의 모델을
학습**한다. 각 GPU는 모델 가중치의 자기 사본을 보유하고 서로 다른 학습 예제 배치를
처리한다. 각 스텝 후 모든 GPU는 그래디언트를 계산한다 — 가중치와 같은 형태로, 예를 들어
**2기가바이트**의 숫자 블록이라 하자 — 하지만 여덟 개의 *서로 다른* 그래디언트다, 각자
다른 데이터를 보았기 때문이다. 학습이 올바르려면 여덟 그래디언트 모두가 **합산**되어 그
합이 다시 모든 GPU에 전달되어야 모든 사본이 동일하게 갱신된다. 이는 전체-대-전체 교환을
강제한다: 모든 GPU의 2GB가 다른 모든 GPU에 도달해야 한다. 이는 비퇴화적이다 — 여덟 개
모두 참여하고, 전체 2GB가 이동하며(어떤 항도 붕괴하지 않는다), 이것이 매 스텝마다, 한
번의 실행에서 수천 번 반복된다.

**호스트 버스를 통할 때.** 링크는 예컨대 **60 GB/s** 정도에서 상한이 걸린다. GPU 한
대의 2GB를 이를 통해 옮기는 데는 약 `2 ÷ 60 ≈ 0.033초 = 33ms`가 걸리고, 결합에는 각
GPU가 자신의 그래디언트를 내보내면서 동시에 다른 것들을 받아야 하므로 — 교환은 **스텝당
수십 밀리초** 규모가 된다. 실제 그래디언트 *계산*이 GPU에서 예컨대 ~20ms 걸렸다면, 머신은
매 스텝의 *절반 이상*을 레인이 놀면서 전선을 기다리는 데 쓰는 셈이다. 8-GPU 머신은
8-GPU 몫의 처리량에 훨씬 못 미치는 것을 제공한다. 좁은 파이프 위에서 지불되는 교환
청구서가 지배하는 것이다.

**NVLink를 통할 때.** 링크는 **~900 GB/s**로 동작한다 — 여기서는 약 **15배** 더 빠르다.
동일한 2GB가 이제 `2 ÷ 900 ≈ 0.0022초 ≈ 2.2ms`만에 건너가고, 전체 그래디언트 결합은
**몇 밀리초** 안에 끝난다. 같은 ~20ms의 계산 대비, 교환은 이제 스텝의 대부분이 아니라
작은 부분일 뿐이다. 레인들은 계속 바쁘게 유지되고, 머신은 실제로 자신이 만들어진 목적인
8-GPU 처리량에 근접한다. 동일한 학습 코드, 동일한 수학 — 오직 전선만 바뀌었고, 그 전선이
다중 GPU 베팅이 성공했는지를 결정했다.

### 서버 하나에서 랙 하나로

같은 아이디어가 단일 박스를 넘어 확장된다. 한 서버 안에서 NVLink는 소수의 GPU를 함께
배선하며, 종종 작은 스위치 칩을 통해 *어느* GPU든 *다른* 어느 GPU에든(이웃만이 아니라)
전체 NVLink 속도로 도달할 수 있게 한다. NVIDIA는 이를 두 방향으로 밀어붙인다.
**NVLink-C2C**("chip-to-chip")는 한 모듈에 패키징된 *CPU와 GPU 사이에* NVLink급
링크를 실행하며, 역시 호스트 버스의 초당 수십 기가바이트 대비 ~900 GB/s로, 두 칩이
메모리에 대한 일관된 뷰를 공유한다 — CPU가 GPU의 메모리를 주소 지정할 수 있고 그
반대도 가능하여, 둘이 하나의 논리적 노드처럼 동작한다. **랙 규모 NVLink**(예: NVL72
설계)는 이 패브릭을 단일 서버의 GPU들을 넘어 랙 전체에 걸친 *수십 개*로 확장하며,
NVLink 스위치 뱅크를 통해 연결되어, 72개의 GPU가 하나의 고대역폭 패브릭을 공유하고
거의 하나의 거대한 GPU처럼 동작한다.

이것이 중요한 이유는 이 노드를 시작하게 만든 것과 같으며, 이제 증폭되었을 뿐이다:
모델이 클수록 더 많은 GPU에 나뉘어야 하고, 패브릭이 병목이 되지 않고 나를 수 있는 전체
교환 트래픽도 더 많아진다. NVLink의 한 자릿수 대역폭 우위가 다중 GPU 머신이 보통의
호스트 버스 속도로 되돌아가지 않도록 지켜준다. (*별도의* 머신들 사이에서 GPU를 연결하는
것은 다른, 네트워크 기반 경로를 사용한다 — 별개의 주제다; NVLink는 박스 안, 이제는
랙 안의 패브릭이다.)

### 결론

단일 GPU의 메모리와 레인은 유한하므로, 큰 모델은 여러 GPU에 나뉜다 — [[cpu-vs-gpu]]의
처리량 베팅을 칩 하나에서 여러 칩으로 확장하는 것이다. 하지만 나뉜 작업은 계속해서
재결합되어야 하며, 그 재결합이 느린 범용 호스트 버스 위에서 실행되면 교환이 지배하고
레인이 논다. NVLink는 GPU 사이(그리고 C2C를 통해 CPU와 GPU 사이)를 연결하는 전용의,
~10배 넓고, CPU를 우회하는 전선으로, 교환이 제약이 되는 것을 제거한다 — 여러 개의 별개
GPU를 중요한 작업에서 마치 하나의 큰 GPU처럼 행동하게 만든다.
