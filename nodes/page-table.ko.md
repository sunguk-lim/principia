# 페이지 테이블

## 요약

**페이지 테이블**(page table)은 프로세스별 조회 구조로, 각 가상 [[page]]에 대해 현재 어느 물리
프레임이 그것을 담고 있는지를 기록한다 — CPU의 주소 하드웨어가 가상 주소를 물리 주소로 바꾸기
위해 *모든* 메모리 접근마다 참고하는 "번역 장부"다. [[page]]는 이미 각 가상 주소를 **페이지
번호**(어느 4KB 블록인지)와 **오프셋**(그 안에서 얼마나 깊이 있는지)으로 나누었으며, 페이지
테이블은 정확히 페이지 번호-프레임 기록이 사는 곳이고, 오프셋은 손대지 않은 채로 통과한다.
각 프로세스는 **자신만의** 페이지 테이블을 가지며, 이것이 바로 한 프로세스의 주소 공간을
다른 것으로부터 사적으로 만드는 것이다: 동일한 가상 주소가 각 프로세스에서 서로 다른 물리
프레임으로 변환되거나, 아예 아무것도 변환되지 않는다. 각 엔트리는 프레임뿐만 아니라 **권한
비트**(존재함, 읽기 가능, 쓰기 가능, 사용자 접근 가능)도 담고 있어서, 매핑되지 않은 엔트리를
건드리거나 그 권한을 위반하는 접근은 페이지 폴트(page fault)로서 커널에 트랩된다. 현대 주소 공간 전체를
덮는 단일 평면 테이블은 천문학적으로 클 것이지만 그 공간 중 거의 전부는 사용되지 않으므로,
실제 페이지 테이블은 **다단계**다 — 실제로 매핑된 영역에 대해서만 가지를 저장하는 트리 —
그리고 **TLB**라는 작은 하드웨어 캐시가 최근 변환들을 기억하여 모든 접근마다 조회를 반복할
필요가 없게 해 준다.

## 상세 설명

### 페이지 테이블이란 무엇이며, 왜 존재해야 하는가

[[page]]는 한 가지를 짓지 않은 채 남겨 두었다. 그것은 메모리가 고정 4KB 블록으로 잘려 있다는
것, 가상 페이지 전체가 물리 **프레임**(실제 RAM의 4KB 블록) 전체에 매핑된다는 것, 그리고 그러므로
가상 주소를 변환한다는 것은 오직 그것의 **페이지 번호** — 어느 4KB 블록에 속하는지 — 만을
변환하는 것을 의미하며, 그 **오프셋** — 그 블록 안에서 얼마나 깊이 있는지 — 은 변경 없이
복사된다는 것을 확립했다. 그것이 의도적으로 말하지 않은 것은 *페이지 번호-프레임 기록이 실제로
어디에 사는가*였다. 그 저장소가 바로 페이지 테이블이다.

정확히 정의하자. **페이지 테이블**은 커널이 만들고 소유하는 데이터 구조로, 각 가상 페이지
번호를 현재 그 페이지를 담고 있는 물리 프레임에 매핑한다. 그것의 한 행 — 하나의 **페이지 테이블
엔트리**(PTE) — 는 정확히 하나의 질문에 답한다: "가상 페이지 *X*는 물리 프레임 *Y*에 산다(그리고
여기 당신이 그것으로 할 수 있는 일이 있다)." 주소 변환을 수행하는 하드웨어 유닛인 **MMU**(메모리
관리 유닛, CPU의 일부)는 *모든 단일* 메모리 접근 — 모든 명령어 페치, 모든 포인터 역참조 — 마다
이 구조를 읽어 프로그램이 사용한 가상 주소를 RAM 칩이 이해하는 물리 주소로 바꾼다. 커널은 장부를
쓰고, MMU는 그것을 전속력으로 읽는다.

왜 이런 것이 애초에 존재해야 하는가? [[page]]가 설명한 변환은 마법이 아니기 때문이다 — 누군가는
그 매핑을 *기억해야* 한다. 페이지 번호는(오프셋과 달리, 조회가 필요 없는) 산술만으로 프레임
번호로 바뀔 수 없다. 페이지를 프레임에 배정하는 것은 임의적이고 시간에 따라 바뀌므로, 저장된
데이터에서 조회되어야 한다. 페이지 테이블이 바로 그 저장된 데이터다. 그것은 [[page]]가 계속
언급했던 "지도"를 구체적으로 실현한 것이다.

### 왜 각 프로세스가 자신만의 것을 가지는가 — 사생활 보호는 여기서 따라 나온다

페이지 테이블은 **프로세스별**이다: 모든 프로세스는 자신만의 별도의 장부를 가진다. 이 단 하나의
사실이 사적인 주소 공간을 제공하는 것이다. 프로세스 A와 프로세스 B 모두 가상 주소 0x400000을
사용할 수 있지만, A의 페이지 테이블은 그 페이지를 한 물리 프레임으로 보내고 B의 것은 완전히
다른 프레임으로 보낸다 — 그래서 어느 쪽도 다른 쪽의 메모리를 지칭하거나 건드릴 수 없다. 커널은
"지금 사용할 페이지 테이블"을 가리키는 특별한 CPU 레지스터를 유지한다. 스케줄러가 A에서 B로
전환할 때, 그것은 이 레지스터가 B의 테이블을 가리키도록 다시 로드하며, 그 순간부터 바로 그
동일한 가상 주소가 다른 곳으로 해석된다. 그러므로 사생활 보호는 나중에 덧붙여진 별도의 메커니즘이
아니다 — 그것은 MMU가 *프로세스별로 다른 장부*를 참고하는 것의 직접적인 귀결이다.

### 엔트리가 담고 있는 것: 프레임 더하기 권한 비트

페이지 테이블 엔트리는 프레임 번호 이상이다. "어느 물리 프레임인지"와 함께, 그것은 접근을
통제하는 몇 가지 **권한 및 상태 비트**를 담고 있다:

- **존재** 비트 — 이 페이지가 지금 실제로 RAM의 프레임에 의해 뒷받침되고 있는가?
- **쓰기 가능** 비트 — 이 페이지에 쓸 수 있는가, 아니면 읽기만 가능한가?
- **사용자** 비트 — 평범한(커널이 아닌) 프로그램이 이 페이지를 조금이라도 건드릴 수 있는가?

매 접근마다 MMU는 변환을 완료하기 *전에* 이것들을 확인한다. 존재 비트가 꺼져 있거나(아직
매핑된 프레임이 없음), 접근이 어떤 권한을 위반하면 — 읽기 전용 페이지에 대한 쓰기, 또는 사용자
프로그램이 커널 전용 페이지에 접근하려는 시도 — MMU는 완료할 수 없다. 그것은 명령어를 멈추고
**페이지 폴트**를 일으킨다: 커널에게 무엇을 할지 결정하도록(프레임을 찾거나 만들거나, 문제가
되는 프로세스를 종료시키거나) 제어권을 넘기는 트랩이다. 폴트는 페이지 테이블의 집행 경계다 —
저장된 권한이 실제로 작동하는 순간이다.

### 왜 다단계인가: 테이블은 희소해야 한다

여기 핵심적인 설계 문제와, 페이지 테이블이 지금과 같은 모양으로 되어 있는 이유가 있다. 64비트
기계는 거대한 가상 공간을 이름 지을 수 있다(리눅스는 기본적으로 프로세스마다 그 비트 중 48개를
사용한다 — 256TB). 4KB 페이지에서, 이는 256TB ÷ 4KB ≈ 640억 페이지다. **평면**(flat) 페이지
테이블 — 가능한 페이지마다 하나의 엔트리를, 페이지 번호로 인덱싱된 단일 배열로 배치한 것 — 은
프로세스*마다* 640억 개의 엔트리를 필요로 할 것이다. 엔트리당 8바이트라면 이는 몇 메가바이트만
사용할지도 모르는 프로세스를 기술하기 위해 0.5테라바이트의 테이블이 필요하다는 뜻이다. 수백 개의
프로세스에 곱하면 절망적이다. 평면 테이블은 [[page]] 노드에서 바이트 단위 매핑이 불가능했던 것과
같은 이유로 불가능하다: 장부가 그것이 기술하는 것을 압도한다.

탈출구는 그 공간이 **희소하다**는 것이다: 실제 프로세스는 몇 개의 작은 영역만을 매핑한다 —
약간의 코드, 약간의 데이터, 스택 하나 — 그리고 광대한 중간 부분은 결코 건드려지지 않는다. 우리는
실제로 사용 중인 영역에만 저장 공간을 쓰는 구조를 원한다. 그 답이 **다단계**(트리 구조) 페이지
테이블이다. 하나의 거대한 배열 대신, 페이지 번호의 비트들이 여러 그룹으로 나뉘고, 각 그룹은 트리의
한 레벨을 인덱싱한다. 최상위 레벨 테이블은 주소 공간의 *굵은* 조각마다 하나의 엔트리를 가진다.
그 엔트리는 "이 전체 조각은 매핑되지 않았다"고 말하고 멈추거나(그 조각에 대한 하위 테이블이
존재하지 않는다), 그 조각을 더 세분화하는 다음 레벨 테이블을 가리킨다. 이것이 계속된다. 변환을
위해 MMU는 최상위에서 시작하여(레지스터가 현재 프로세스의 최상위 레벨 테이블 주소를 담고 있다)
**아래로 내려가며**, 각 레벨에서 하나의 비트 그룹을 사용하여 다음 테이블을 고르고, 프레임 번호를
가진 리프 엔트리에 도달할 때까지 계속한다.

이득은 정확히 우리가 원했던 희소성이다: 프로세스가 결코 사용하지 않는 어떤 굵은 조각에 대해서도,
단일한 최상위 레벨 엔트리만 비어 있음으로 표시되고 그 조각에 대한 하위 테이블은 *전혀* 할당되지
않는다. 사용되지 않는 트리의 전체 가지가 수십억 개 대신 엔트리 하나만을 소비한다. 이 트리는
프로세스가 실제로 사는 곳에만 세부 사항을 저장한다. (x86-64 리눅스에서는 이 트리가 기본적으로
네 레벨 깊이다. 그 개수는 세부 사항일 뿐이며, 핵심은 희소한 트리라는 것이다.)

이 희소한 트리에는 한 가지 비용이 있다: MMU는 이제 단일 주소를 변환하기 위해 메모리에서 여러
테이블 — 레벨당 하나 — 을 읽어야 한다. 모든 접근마다 이를 하는 것은 지독하게 느릴 것이다. 그래서
하드웨어는 가장 최근의 가상-페이지-대-프레임 결과들의 작고 빠른 캐시인 **TLB**(translation
lookaside buffer)를 유지한다. 변환이 TLB에 있을 때 — 프로그램이 같은 페이지를 계속 반복해서
재사용하기 때문에 흔한 경우 — MMU는 전체 순회를 건너뛰고 캐시된 프레임을 곧바로 사용한다. 페이지
테이블은 권위 있는 완전한 장부이고, TLB는 지금 사용 중인 몇몇 페이지에 대한 포스트잇 메모다.

### 실전 사례: 하나의 테이블을 통한 두 번의 변환

최종 레벨 페이지 테이블에 다음 두 엔트리(프레임 번호와 권한이 표시됨)를 가진 프로세스와, [[page]]
노드가 주소를 나눈 것과 정확히 동일하게 오프셋이 하위 12비트(하위 16진수 세 자리)인 4KB 페이지를
생각해 보자:

- 엔트리 **0x401** → 프레임 **0x12**, 존재함, 읽기 가능, 쓰기 가능
- 엔트리 **0x999** → *(엔트리 없음 — 이 조각은 결코 매핑된 적이 없다)*

**변환 1 — 히트.** 프로그램이 가상 주소 **0x401234**에 접근한다. [[page]]처럼 나누면: 하위
16진수 세 자리가 오프셋 **0x234**이고, 그 위 전체가 페이지 번호 **0x401**이다. MMU는 트리를
따라 내려가 리프 엔트리 0x401에 도달하고, 그것이 **존재함**을 발견하며, 프레임 **0x12**를 읽고,
권한을 확인한다 — 프로그램이 읽고 있다고 하면, 엔트리가 이를 허용한다. 이제 물리 주소를 조립하자.
프레임의 RAM 베이스는 프레임 번호를 12비트 위로 시프트한 것이다(프레임은 4KB 간격이므로): 프레임
0x12는 물리 주소 0x12000에서 시작한다. 변경되지 않은 오프셋을 그 위에 붙인다: 0x12000 + 0x234 =
**물리 주소 0x12234**. [[page]]의 항등식으로 검산해 보자, 페이지 번호 × 4096 + 오프셋: 가상
주소 0x401234 = 0x401 × 0x1000 + 0x234, 그리고 물리 주소는 프레임 0x12 × 0x1000 + 0x234다 —
페이지 번호는 0x401에서 0x12로 바뀌었고, 오프셋 0x234는 그대로 통과했다. 그것이 페이지 테이블의
임무 전체를 한 줄로 요약한 것이다: 페이지 번호를 프레임 번호로 바꾸고, 오프셋은 유지한다.

**변환 2 — 폴트.** 이제 같은 프로그램이 가상 주소 **0x999000** — 페이지 번호 **0x999**,
오프셋 **0x000** — 에 접근한다. MMU는 트리를 순회하지만, 0x999를 포함하는 조각은 결코 매핑된
적이 없다: 엔트리가 존재하지 않는다. MMU는 프레임을 만들어낼 수 없으므로, 명령어를 멈추고
커널로 **페이지 폴트**를 일으킨다. 여기서부터는 페이지 테이블이 아니라 커널의 결정이다: 0x999가
프로세스가 사용할 수 있는 영역에 속한다면, 커널은 새 프레임을 할당하고 엔트리를 채운 뒤 명령어를
재시작할 수 있다(이 첫-접촉-시-할당은 *디맨드 페이징*이며, 별개의 주제다). 만약 0x999가 유효한
영역 어디에도 속하지 않는 엉뚱한 주소라면, 커널은 세그멘테이션 폴트로 프로세스를 종료시킨다.
페이지 테이블의 역할은 정확히 "유효한 엔트리 없음 → 커널로 트랩"에서 끝난다 — 그것은 조회를
*할 수 있을 때는 답하고* *할 수 없을 때는 폴트를 신호하는* 구조다.

두 변환 사이의 대비가 핵심이다. 동일한 방식으로 순회되는 동일한 단일 테이블이, 한쪽 접근은
나노초 만에 물리 주소로 바꾸고 다른 쪽은 커널 트랩으로 바꾼다 — 그리고 어느 쪽이 일어날지는
전적으로 조회된 엔트리가 존재하고 접근을 허용하는지에 달려 있다. 그것이 페이지 테이블이 *무엇인지*다:
그 존재, 내용, 권한 비트가 매 접근마다 가상 페이지가 실제로 어디에 사는지, 또는 그것을 건드리는
것이 애초에 허용되는지를 결정하는, 프로세스별 장부다.
