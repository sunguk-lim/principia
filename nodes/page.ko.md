# 페이지

## 요약

**페이지**(page)는 메모리가 관리되는 단위인 고정 크기 블록으로, 거의 항상 **4KB**(4096바이트)다.
[[virtual-memory]]는 각 프로세스에게 커널이 물리 RAM의 실제 위치와 연결해야 하는 사적인 가상 주소
범위를 제공한다. 이 연결을 바이트 단위로 추적하는 대신, 시스템은 *양쪽* 모두를 동일한 크기의
블록으로 자른다. 가상 주소 공간의 4KB 너비 조각은 **페이지**이고, 물리 RAM의 동일한 4KB 너비
조각은 **프레임**이다. 커널은 그 다음 전체 페이지를 전체 프레임에 매핑하고 오직 그것만을 기록한다
— "이 가상 페이지는 저 물리 프레임에 산다" — 바이트마다 하나씩 기록하는 대신. 그 이유는 순전한
경제성이다: 바이트 단위 장부는 메모리의 모든 단일 바이트에 대해 매핑 기록을 요구할 것이며, 이는
불가능할 만큼 크다. 모든 페이지가 정확히 4KB이기 때문에, 어떤 가상 주소든 **페이지 번호**(어느
페이지에 속하는지)와 **오프셋**(그 페이지 안에서 얼마나 깊이 있는지)으로 깔끔하게 나뉘며, 오직
페이지-프레임 관계만 저장하면 된다 — 오프셋은 변환 과정을 손대지 않은 채로 통과한다.

## 상세 설명

### 페이지가 어디서 왔는가

[[virtual-memory]]가 이미 확립한 것에서 시작하자. 각 프로세스는 자신만의 사적인 **가상 주소**
범위 — 메모리를 이름 짓는 데 사용하는 숫자 — 를 부여받으며, 모든 접근마다 하드웨어는 가상 주소를
**물리 주소**, 즉 RAM 안의 실제 위치로 바꿔야 한다. 이는 가상 위치에서 물리 위치로의 *지도*를
요구한다. virtual-memory가 의도적으로 별도의 노드에 남겨 둔 열린 질문은: 그 지도는 어떤 세밀함
수준에서 작동하는가?

순진한 답은 "바이트마다"이다 — 개별 가상 바이트마다 그것이 대응하는 물리 바이트를 저장하는 것.
이는 가망이 없다. 현대의 기계는 수십억 바이트의 RAM을 가지고 있고, 가상 공간은 그보다 더 크다.
바이트당 하나의 엔트리를 가진 지도는 그것이 기술하는 메모리만큼 크거나 그보다 더 클 것이며,
다른 어떤 것을 위한 공간도 남기지 않을 것이다. 지도는 그것이 통제하는 메모리보다 *훨씬* 작아야
한다. 그러므로 모든 바이트를 지칭할 여유가 없다.

페이지는 이 문제에 대한 답이다. 바이트를 매핑하는 대신, 시스템은 메모리를 **고정 크기 블록**으로
관리하고, 한 번에 하나의 블록 전체를 매핑한다.

### 페이지란 무엇인가, 그리고 그 짝인 프레임

용어를 정확히 정의하자.

- **페이지**는 **가상** 주소 공간의 고정 크기, 연속된 블록이다 — 관례적으로 4KB, 즉 4096바이트.
  전체 가상 공간은 이 동일한 블록들로, 연이어서 잘린다: 첫 페이지는 가상 바이트 0에서 4095까지를,
  다음 페이지는 4096에서 8191까지를 덮는 식이다.
- **프레임**(또는 *물리 페이지*)은 동일한 크기, 4KB의 블록이지만 **물리 RAM**에서 잘라낸
  것이다. 실제 RAM은 가상 공간이 페이지로 잘리는 것과 같은 방식으로 프레임으로 잘린다.

이 둘은 의도적으로 *동일한 크기*를 가진다: 그것이 페이지 전체가 아무런 여백이나 부족함 없이
프레임 전체에 정확히 들어맞게 해 주는 이유다. 그래서 커널의 지도는 각 가상 페이지에 대해 현재
어느 물리 프레임이 그것을 담고 있는지를 기록한다 — 바이트마다가 아니라 페이지마다 하나의 기록.
페이지는 **매핑의 단위**다: 시스템이 재배치하거나, 계산에 넣거나, 하나의 나눌 수 없는 조각으로
내주는 최소 메모리 양이다.

### 왜 고정 크기 블록이 장부를 줄이는가

여기 핵심적인 보상이 숫자로 표현되어 있다. 4KB 페이지를 쓰면, 이제 매핑 기록 하나가 바이트 하나
대신 4096바이트의 메모리를 덮는다. 이는 지도가 유지해야 하는 기록 수의 4096배 감소다 — 지도는
페이지가 넓어진 것과 정확히 같은 배수로 줄어든다. 지도가 작게 유지되는 것은 블록이 크기 *때문*이다.
고정 블록 크기를 선택하는 이유 전체는 지도를 감당할 수 있게 만들기 위해서다.

하지만 고정 크기 블록은 더 작은 지도보다 더 미묘한 것을 사 준다. 그것이 진짜 마법이다: 그것들은
가상 주소를 *순전한 산술만으로 나눌 수 있게* 만든다. 블록 안쪽 부분에는 아무런 조회도 필요하지
않다. 모든 페이지가 정확히 4096바이트이고 블록들이 0부터 연이어 배치되어 있기 때문에, 어떤
바이트의 위치든 완전히 두 조각으로 기술된다:

- 그것의 **페이지 번호** — 어느 4KB 블록에 속하는지, 즉 주소를 4096으로 나눈 값; 그리고
- 그것의 **오프셋** — 그 블록 안에서 얼마나 깊이 있는지, 즉 4096으로 나눈 나머지, 0부터 4095까지의
  값.

함께, (페이지 번호, 오프셋)은 바이트를 정확히 지칭한다: 바이트 = 페이지 번호 × 4096 + 오프셋.
4096이 2¹²이므로, 이 나눗셈과 나머지는 하드웨어가 계산해야 하는 진짜 산술이 아니다 — 그것들은
그저 *비트를 자르는* 것일 뿐이다. 주소의 **하위 12비트**가 오프셋이다(2¹² = 4096개의 서로 다른
위치가 12비트에 들어맞기 때문이다). 하위 12비트 위에 있는 모든 비트가 페이지 번호다. 그러므로
주소를 변환한다는 것은 오직 페이지 번호만을 변환하는 것을 의미한다 — "가상 페이지 X는 물리
프레임 Y에 있다"를 조회하고, 오프셋은 변경 없이 그대로 복사하는 것 — 4KB 블록 *안에서의* 바이트
위치는 그 블록이 가상 공간에 있든 물리 프레임에 있든 동일하기 때문이다. 지도는 페이지 번호를
처리하고, 오프셋은 지도가 전혀 필요 없다. 이것이 바로 virtual-memory가 자신의 추적에서 사용한
페이지 번호/오프셋 분할이 작동하는 이유다: 이 분할은 블록이 2의 거듭제곱 크기라는 것의 자유로운
귀결이다.

(페이지-프레임 기록을 실제로 저장하는 구조 — 커널이 프로세스마다 만드는 *페이지 테이블* — 와,
프로세스가 처음 건드릴 때까지 대부분의 페이지를 뒷받침하지 않은 채로 두는 요령 — *디맨드 페이징* —
은 각각 별개의 개념이며 페이지 자체는 아니다. 여기서 페이지는 단지 이 둘 모두를 가능하게 만드는
고정 크기 단위일 뿐이다.)

### 실전 사례, 1부: 할당은 전체 페이지 단위로 반올림된다

구체적인 요청을 살펴보자. 어떤 프로그램이 **10KB**의 메모리 — 10240바이트 — 를 요청한다. 메모리는
오직 전체 페이지 단위로만 내주어지므로, 커널은 정확히 10240바이트를 줄 수 없다. 요청을 덮을 만큼
충분한 *전체 4KB 페이지*를 주어야 한다. 나눠 보면: 10240 ÷ 4096 = 2.5. 두 페이지는 8192바이트만
덮으므로 부족하다. 그래서 커널은 **3페이지**로 **올림**한다:

- 페이지 1 — 4096바이트, 완전히 사용됨.
- 페이지 2 — 4096바이트, 완전히 사용됨. (여기까지 8192바이트가 덮였다.)
- 페이지 3 — 실제로 필요한 것은 10240 − 8192 = **2048바이트**뿐이지만, 4096바이트 페이지 전체가
  이 할당에 배정된다.

그러므로 10KB 요청은 3페이지 = 12288바이트의 주소 공간을 소비하며, 그중 12288 − 10240 =
**2048바이트가 마지막 페이지에서 예약되었지만 사용되지 않는다.** 이 낭비된 꼬리 부분을 **내부
단편화**(internal fragmentation)라고 부른다 — 할당이 전체 페이지 단위로 양자화되어 있고 요청이
좀처럼 정확한 페이지 경계에 맞아떨어지지 않기 때문에 할당된 페이지 *안에서* 사라지는 메모리다.
이는 고정 크기 블록으로 메모리를 관리하는 것의 직접적이고 피할 수 없는 비용이다: 지도를 4096배
줄여 준 바로 그 고정 크기가 모든 할당을 올림하도록 강제하여, 평균적으로 마지막 페이지의 약 절반을
낭비하게 만든다. 이 사례는 의도적으로 *사소하지 않게* 구성되었다는 점에 유의하라 — 10KB는
4KB의 배수가 아니므로 올림과 나머지가 실제로 나타난다. 깔끔한 8KB 요청이었다면 단편화가 완전히
가려졌을 것이다.

### 실전 사례, 2부: 실제 주소를 나누기

이제 비트를 자르는 과정을 직접 보기 위해 실제 가상 주소를 두 부분으로 나눠 보자. 4KB 페이지에서
가상 주소 **0x00401234**를 가지고 시작한다.

오프셋은 주소의 **하위 12비트**다. 16진수에서는 자릿수 하나가 4비트이므로, 12비트는 정확히
**하위 3자리**다. 0x00401234에서 그것을 읽어 보면: 하위 3자리는 **0x234**다. 그러므로 오프셋 =
0x234 = 10진수로 564다 — 이 바이트는 자신의 페이지 안에서 564바이트 지점에 있으며, 564는 모든
오프셋이 그래야 하듯 4096보다 넉넉히 작다.

페이지 번호는 그 하위 12비트 *위에 있는* 모든 것이다 — 하위 3자리를 떼어내고 나머지를 유지하면:
0x00401234 → **0x401**. 정의하는 항등식으로 검산해 보자, 페이지 번호 × 4096 + 오프셋: 0x401 =
10진수로 1025이고, 1025 × 4096 + 564 = 4,198,400 + 564 = 4,198,964, 이는 정확히 0x00401234다.
분할이 원래 주소를 재현하므로 옳다.

그러므로 읽어 보면: 주소 0x00401234는 **가상 페이지 0x401**의, 그 안에서 **오프셋 0x234**에
산다. 실제 바이트를 찾기 위해 시스템은 지도에서 오직 페이지 0x401만을 조회하여 어느 물리 프레임이
그것을 담고 있는지 알아낸다 — 이를테면 프레임 0x9C2 — 그리고 변경되지 않은 오프셋 0x234를 그
위에 붙여, 물리 주소 0x9C2234를 얻는다. 4KB 페이지 전체가 하나의 블록으로 이동했고, 오프셋
0x234는 양쪽에서 동일한 바이트를 골랐다. 오직 페이지를 조회하고, 오프셋을 유지하는 이 하나의
동작 — 메모리가 고정 4KB 페이지로 잘려 있기 때문에만 감당할 수 있는 동작 — 이 바로 페이지가
개념으로서 존재하는 이유다.
