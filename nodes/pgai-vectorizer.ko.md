# pgai Vectorizer

## 요약

**pgai Vectorizer**는 Postgres를 위한 **선언적 자동 임베딩 파이프라인**이다.
어떤 모델을 쓸지, 텍스트를 어떻게 청크로 나눌지 등, 특정 원본 테이블의 텍스트
컬럼을 임베딩해야 한다고 *한 번* 선언하면, Vectorizer는 그 이후로 쓰기 애플리케이션이
아무것도 하지 않아도 [[embedding]]을 원본 데이터와 **자동으로, 영원히** 동기화된
상태로 유지한다. 이는 함께 작동하는 두 개의 선행 개념으로 구성된다: 원본 테이블의
[[database-trigger]]가 모든 변경(INSERT/UPDATE/DELETE)을 **작업 큐**에 기록하고,
**백그라운드 워커**가 그 큐를 비운다 — 변경된 각 행의 텍스트를 청크로 나누고,
임베딩 모델을 호출하며, 결과 벡터를 [[pgvector]] `vector`인 컬럼을 가진 별도의
목적지 테이블에 기록한다. 핵심 아이디어는 **분리(decoupling)**다: 임베딩 작업은
행을 변경한 트랜잭션 *바깥에서* 일어나므로, 느리거나 속도 제한에 걸리거나 실패하는
모델 호출이 사용자의 쓰기를 결코 막거나 롤백시킬 수 없다 — 그러면서도 큐 항목이
트랜잭션적으로 생성되었기 때문에 어떤 변경도 조용히 누락되지 않고, 모든 낡은 행은
*결국* 재임베딩된다.

## 상세 설명

### 이것이 해결하는 문제 — 임베딩이 동기화에서 벗어난다

테이블을 의미로 검색하려면 각 행의 텍스트를 [[embedding]]으로 바꿔서 [[pgvector]]
컬럼에 저장해야 한다. 순진한 방법은 쓰기 시점에 임베딩하는 것이다: 행을 삽입하거나
업데이트할 때마다 임베딩 모델도 호출하고 벡터를 저장한다. 이는 매우 다른 두 작업을
결합시킨다. 데이터베이스 쓰기는 빠르고, 로컬이며, 트랜잭션적이다; 임베딩 호출은
모델 제공자에게 보내는 **느린 네트워크 요청**으로, 비용이 들고, 속도 제한이
있으며, 실패할 수 있다. 이를 인라인으로 하면 모델의 지연과 실패가 *쓰기 자체의*
지연과 실패가 되어버린다 — 시간이 초과되는 모델이 평범한 `INSERT`를 중단시킨다.
그리고 나중에 행의 텍스트가 업데이트되면, 저장된 벡터는 이제 **낡은
(stale)** 상태다: 옛 텍스트를 나타내므로, 유사도 검색이 조용히 잘못된 매치를
반환한다. 매 쓰기를 모델 호출의 인질로 잡지 않으면서 변화하는 테이블에 대해
벡터를 충실하게 유지하는 것 — 이것이 Vectorizer가 존재하는 이유인 문제다.

### 메커니즘 — 트리거가 큐에 넣고, 워커가 임베딩한다

Vectorizer는 두 선행 개념에 작업을 나누고 그 사이에 큐를 둠으로써 이 긴장을
해소한다.

1. **트랜잭션적으로 변경을 포착 — [[database-trigger]].** `documents(body)`에
   벡터라이저를 만들면, pgai는 `documents`에 [[database-trigger]]를 설치한다.
   모든 INSERT/UPDATE/DELETE마다 이 트리거는 마커 — "행 *N*이 (재)임베딩 필요" —
   를 **큐 테이블**에 삽입한다. [[database-trigger]]는 *발동시킨 트랜잭션
   안에서* 실행되므로, 큐 항목은 행 변경이 커밋될 **경우에 한해서만** 생성된다:
   변경과 그 "나를 재임베딩해줘"라는 메모는 원자적이다. 이것이 정확히
   [[database-trigger]]가 설명하는 변경 기반 작업 큐 패턴이며, 아무것도 누락되지
   않고 롤백된 변경에 대해 아무것도 큐에 들어가지 않음을 보장하는 요소다.

2. **트랜잭션 밖에서 느린 작업을 수행 — 백그라운드 워커.** 별도의 **워커
   프로세스**가 자신만의 스케줄로(사용자의 트랜잭션 안이 아니라) 실행된다. 큐를
   폴링하며, 대기 중인 각 행에 대해: 텍스트를 가져오고, 임베딩하기에 알맞은
   크기의 구절로 **청크**로 나누고, 임베딩 모델을 호출하여 각 청크를
   [[embedding]]으로 바꾼 뒤, 그 벡터들을 — [[pgvector]] `vector` 컬럼을 가진,
   청크당 한 행이며 원본 행으로 다시 연결되는 별개의 테이블인 — **목적지
   테이블**에 기록한다. 그런 다음 큐 항목을 지운다. 모델 호출이 실패하면 워커는
   그저 항목을 그대로 두거나(또는 나중에 재시도한다); 원본 테이블은 손대지
   않으며 사용자의 쓰기는 이미 오래전에 커밋되었다.

3. **하나로 보이도록 제시 — 뷰.** pgai는 또한 원본 행들을 목적지 테이블의 청크
   임베딩과 조인하는 **뷰**를 만들어, 쿼리가 원본 컬럼과 벡터를 마치 하나의
   테이블처럼 함께 읽고 그것들에 대해 [[pgvector]] 유사도 검색을 실행할 수 있게
   한다.

### 왜 이런 형태인가 — 핵심 아이디어

이 아키텍처는 **데이터 수정과 임베딩의 분리**의 직접적인 결과다.

- **쓰기는 빠르고 신뢰할 수 있는 상태를 유지한다.** 쓰기 경로에 추가되는 유일한
  비용은 큐에 대한 트리거 삽입 하나뿐이다 — 저렴하고 로컬이다. 모델의 지연과
  실패는 전적으로 워커 안에 머물며, 결코 트랜잭션에 걸리지 않는다.
- **동기화는 보장되지만 지연이 있다(eventual).** 트랜잭션적 포착
  ([[database-trigger]]를 통한)은 커밋된 모든 변경이 정확히 한 번 큐에 들어감을
  의미하고, 워커는 실제 재임베딩이 *곧* 일어나되 즉시는 아니라는 것을 의미한다.
  따라서 [[embedding]]은 원본과 **최종적으로 일관(eventually consistent)**하다 —
  변경 직후 잠깐 낡아 있다가 곧 바로잡힌다 — 이는 검색에 있어 몇 초의 지연은
  보이지 않지만 막힌 쓰기는 그렇지 않은 만큼 올바른 트레이드오프다.
- **선언적이지 손으로 연결하지 않는다.** *무엇*을 원하는지(이 컬럼을 이 모델로,
  이렇게 청크로 나누어 임베딩하라) 한 번 말하면, 트리거, 큐, 워커, 목적지
  테이블, 뷰가 여러분을 위해 생성되고 유지된다. 손으로 하는 것과 비교하면:
  트리거, 큐, 워커 루프, 청크 로직, 목적지 스키마, [[pgvector]] 인덱스를 직접
  작성하고 테이블이 진화함에 따라 계속 올바르게 유지해야 할 것이다.

### 실제 사례 — 변경되는 문서 하나

`documents(body)`에 벡터라이저를 선언한다(임베딩 모델과 청크 방식은 한 번만
지정). 이제 행 하나의 생애를 지켜보자.

1. 클라이언트가 `INSERT INTO documents (body) VALUES ('...long article...')`를
   실행하고 커밋한다. [[database-trigger]]가 그 트랜잭션 안에서 발동하여
   "doc 42 → pending"을 큐에 기록한다. 클라이언트의 INSERT는 즉시 반환된다;
   임계 경로에서 모델은 호출되지 않았다.
2. 잠시 후 **백그라운드 워커**가 깨어나 "doc 42 pending"을 보고, 글을 읽어,
   (예를 들어) 6개의 청크로 나눈 뒤, 임베딩 모델을 6번 호출하여 6개의
   [[embedding]]을 얻고, 목적지 테이블에 6개의 행을 삽입한다 — 각각 doc 42에
   연결된 [[pgvector]] `vector`다 — 그런 다음 큐 항목을 제거한다. 이제 doc
   42는 의미로 검색 가능하다.
3. 이후 누군가 글을 수정한다: `UPDATE documents SET body = '...revised...'
   WHERE id = 42`. [[database-trigger]]가 다시 발동하여 doc 42를 다시 큐에
   넣는다. 워커는 다시 청크로 나누고 재임베딩하여, doc 42의 낡은 벡터를 새
   것으로 **교체**한다. 유사도 검색은 이제 수정된 텍스트를 반영한다 —
   자동으로, 임베딩이 존재한다는 것을 아는 애플리케이션 코드 없이도.

그 루프 — *트리거가 변경을 트랜잭션적으로 포착하고, 워커가 대역 외에서
재임베딩하며, [[pgvector]]가 벡터를 저장하고 서빙한다* — 가 모든 행에 대해
영원히 실행되는 것, 그것이 Vectorizer의 전부다.

## 선행 개념

- [[database-trigger]] — 동기화 포착 메커니즘: 원본 테이블의 트리거가 커밋된
  각 INSERT/UPDATE/DELETE를 *발동시킨 트랜잭션 안에서* 작업 큐에 기록하므로,
  변경은 정확히 한 번 큐에 들어가고 롤백된 쓰기에 대해서는 결코 들어가지
  않는다.
- [[embedding]] — 백그라운드 워커가 각 텍스트 청크로부터 만들어내고 최신
  상태로 유지해야 하는 것: 원본 텍스트가 바뀔 때마다 다시 계산되는, 유사도
  검색이 의존하는 밀집 의미 벡터.
- [[pgvector]] — 벡터가 저장되고 검색되는 곳: 목적지 테이블의 컬럼이
  [[pgvector]] `vector`이므로, 유지 관리된 [[embedding]]은 즉시 그 거리
  연산자와 ANN 인덱스로 사용 가능하다.
