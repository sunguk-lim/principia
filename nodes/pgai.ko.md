# pgai

## 요약

**pgai**는 (Timescale이 만든) 확장 모음으로, PostgreSQL을 — 주로
**검색-증강 생성(retrieval-augmented generation)**과 **의미 검색(semantic
search)**을 위한 — AI 애플리케이션 구축 플랫폼으로 바꾼다. *데이터베이스 엔진
자체*처럼, "pgai" 노드의 핵심은 어느 하나의 기능이 아니다 — 각각은 이미 아래에
선행 개념으로 존재한다. 핵심은 **조합**이다: pgai는 세 가지 능력을 함께 묶어
서로를 강화하도록 만든다. [[pgvector]]는 데이터베이스에 `vector` 컬럼 타입, 거리
연산자, ANN 인덱스를 제공하여, 임베딩이 관계형 데이터 옆에 놓이고 SQL에서 의미로
검색되게 한다. [[pgai-vectorizer]]는 그 임베딩들을 원본 행과 **자동으로 동기화된
상태로** 유지하여, 검색 가능한 벡터가 자신이 나타내는 텍스트에서 결코 벗어나지
(drift) 않게 한다. [[llm-from-sql]]은 생성형 모델과 임베딩 모델을 **SQL 함수로**
노출하여, 추론이 외부 서비스가 아니라 쿼리 안에서 실행되게 한다. 이들을 함께
놓으면, [[retrieval-augmented-generation]]의 검색-후-생성 루프 전체가 하나의
PostgreSQL 인스턴스 안에서 실행될 수 있다 — 동기화할 별도의 벡터 데이터베이스도,
맞춤형 임베딩 파이프라인도, 모델 호출을 오케스트레이션하는 애플리케이션 측 코드도
필요 없다.

## 상세 설명

### pgai가 왜 독자적인 노드이지 부분들의 합에 불과하지 않은가

각 선행 개념은 이미 독자적으로 성립한다: [[pgvector]]는 벡터 저장과 검색이고,
[[pgai-vectorizer]]는 자동 임베딩 파이프라인이며, [[llm-from-sql]]은 SQL 함수로
구현된 모델 추론이고, [[retrieval-augmented-generation]]은 검색-후-생성
아키텍처다. 그렇다면 "pgai" 노드는 이 넷이 가르치지 않는 무엇을 가르치는가?
**통합**이다 — 이 특정한 조각들을 하나의 데이터베이스 안에 조립하면, 보통은 서너
개의 별도 서비스에 흩어져 있던 시스템을 단일 PostgreSQL 배포로 응축시킨다는
사실이다. 전통적인 RAG 스택은 다음과 같다: 원본 데이터를 위한 관계형
데이터베이스, 임베딩을 위한 *별도의* 벡터 데이터베이스, 둘을 동기화 상태로
유지하기 위한 *별도의* 임베딩 파이프라인, 그리고 검색과 모델 호출을
오케스트레이션하는 *애플리케이션 코드*. pgai의 기여는 이 모든 것이 Postgres의
기능이 된다는 점이다: 벡터는 같은 테이블에 놓이고([[pgvector]]), 동기화는 선언적이고
스스로 유지되는 파이프라인이며([[pgai-vectorizer]]), 임베딩과 생성 호출 모두 SQL이다
([[llm-from-sql]]). 그 가치는 부분들이 서로 맞물리는 방식에 있다 —
[[pgai-vectorizer]]는 정확히 [[pgvector]]가 인덱싱하는 임베딩을 만들어내고,
[[llm-from-sql]]의 생성 호출은 정확히 [[pgvector]]가 반환하는 이웃들을 소비한다 —
그래서 [[retrieval-augmented-generation]]은 데이터베이스 밖의 아무것도 필요로
하지 않는다.

### 각 조각과 그 역할

- **벡터 저장과 검색 — [[pgvector]].** 기반(substrate)이다. `vector` 컬럼 타입을
  추가하여 임베딩이 행에 저장되게 하고, 거리 연산자를 추가하여 유사도가 SQL 비교가
  되게 하며, ANN 인덱스를 추가하여 최근접 이웃 검색이 빠르게 이루어지게 한다.
  이것은 *벡터가 어디에 살고 어떻게 검색되는지*에 관한 것이다.

- **벡터를 최신 상태로 유지하기 — [[pgai-vectorizer]].** 유지보수 계층이다. 텍스트
  컬럼에 벡터라이저를 선언하면, 행이 변경될 때마다 [[pgvector]] 임베딩이 자동으로
  생성되고 재생성된다 — 트리거가 모든 변경을 트랜잭션적으로 포착하고, 백그라운드
  워커가 대역 외(out of band)에서 재임베딩한다. 이것은 *검색 가능한 벡터가 낡지
  않게 막는 요소*이며, 임베딩 파이프라인을 직접 작성하지 않고도 pgai를 사용할 수
  있는 이유다.

- **쿼리 안에서의 모델 추론 — [[llm-from-sql]].** 연산 계층이다. 임베딩 호출
  (벡터라이저와 임시 임베딩에 사용됨)과 생성 호출(최종 답변을 만드는 데 사용됨)을
  SQL 함수로 노출한다. 이것은 데이터베이스를 벗어나지 않고 *모델을 호출하는
  방법*이다.

- **애플리케이션의 형태 — [[retrieval-augmented-generation]].** 다른 세 요소가
  섬기는 아키텍처다: 가장 관련성 높은 몇 개의 조각을 검색한 뒤, 그것들에 조건화된
  답을 생성한다. pgai는 RAG를 발명하지 않는다; RAG를 SQL로 조립할 수 있는 것으로
  만든다.

### 실제 사례 — 문서 테이블에 대한 RAG 어시스턴트, 처음부터 끝까지

`documents` 테이블에 대한 질의응답 어시스턴트를 전적으로 Postgres 안에서
구축하며, 각 선행 개념이 자신의 역할을 하는 것을 지켜보자.

1. **수집(계속 [[pgai-vectorizer]]가 처리).** `documents(body)`에 벡터라이저를
   선언했다. 글이 삽입되거나 수정되면, 그 트리거가 이를 큐에 넣고 워커가 각각을
   청크로 나누고 임베딩 모델을 통해 임베딩하며, 청크 임베딩을 [[pgvector]] 타입의
   목적지 테이블에 기록한다. 여러분 쪽에서 실행하는 수집 스크립트는 없다; 코퍼스의
   벡터는 그저 텍스트와 동기화된 상태를 유지할 뿐이다.

2. **질문이 도착한다.** 사용자가 *"우리 환불 정책이 뭐야?"*라고 묻는다. 먼저 질문을
   임베딩한다 — [[llm-from-sql]]을 통한 임베딩 호출 — 쿼리 벡터 `$q`를 만든다.

3. **검색(via [[pgvector]]).** SQL 쿼리가 청크 벡터를 `$q`에 대한 코사인 거리로
   순위 매기고 상위 5개를 취한다:
   `SELECT chunk FROM documents_embeddings ORDER BY embedding <=> $q LIMIT 5`.
   이것들이 의미상 가장 관련 있는 다섯 구절이다 — ANN 인덱스 스캔으로 실행되는
   [[retrieval-augmented-generation]]의 검색 절반이다.

4. **생성(via [[llm-from-sql]]).** 검색된 다섯 청크가 하나의 프롬프트로
   연결된다 — *"다음 구절들을 사용하여 답하라: … 질문: 우리 환불 정책이 뭐야?"* —
   그리고 생성형 모델 호출에 전달된다. 모델은 검색된 텍스트에 근거한 답을
   반환한다.

5. **전체가 [[retrieval-augmented-generation]]이다.** 2~4단계는 정확히
   검색-후-생성이며, 1단계는 검색 가능한 집합을 원본에 충실하게 유지했다. 모든
   단계는 하나의 PostgreSQL 데이터베이스에 대한 SQL 문장이었다: 벡터는
   [[pgai-vectorizer]]가 유지 관리했고, [[pgvector]]가 검색했으며, 임베딩과 생성
   모두 [[llm-from-sql]] 호출이었다. 원래는 네 개의 협력 시스템이었을 것이 하나가
   된다.

**층위 맞추기.** **구조**는 `documents` 테이블과 뷰로 조인된 그 동반
[[pgvector]] 임베딩이다. **알고리즘**은 *벡터라이저가 임베딩을 동기화 상태로
유지 → 질문을 임베딩 → [[pgvector]] 최근접 이웃 검색 → [[llm-from-sql]] 생성*
이다 — 즉 모든 화살표가 SQL 호출인 [[retrieval-augmented-generation]]이다.
**기저**는 단일 Postgres 인스턴스다: 원본 행들, 벡터 컬럼과 그 ANN 인덱스,
벡터라이저의 큐와 워커, 그리고 모델 호출 함수들이 모두 하나의 엔진 안에 있다.
그 처음부터 끝까지의 조립 — 어느 한 확장이 아니라 — 이 바로 pgai다.

## 선행 개념

- [[pgvector]] — 저장과 검색 기반: 임베딩이 테이블에 살고 SQL에서 의미로
  검색되게 하는 `vector` 컬럼 타입, 거리 연산자, ANN 인덱스.
- [[pgai-vectorizer]] — 그 [[pgvector]] 임베딩을 원본 행과 자동으로 동기화
  상태로 유지하는 유지보수 계층으로, pgai가 손으로 만든 임베딩 파이프라인 없이도
  작동하게 한다.
- [[llm-from-sql]] — 연산 계층: 인덱싱과 최종 답변 모두를 위해, 데이터베이스를
  벗어나지 않고 호출되는 SQL 함수로 노출된 임베딩 및 생성 모델 호출.
- [[retrieval-augmented-generation]] — pgai가 나머지 셋으로부터 조립하는
  애플리케이션 아키텍처: 관련 있는 조각을 검색한 뒤, 그것들에 조건화된 답을
  생성한다. 여기서는 PostgreSQL 안에서 처음부터 끝까지 실행된다.
