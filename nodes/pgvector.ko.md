# pgvector

## 요약

**pgvector**는 [[postgresql]]에게 벡터를 저장하고 검색하는 법을 가르치는
확장이다. 데이터베이스에 세 가지를 추가한다: 최상위급 `vector` **컬럼 타입**
(실수의 고정 길이 목록), 두 벡터가 얼마나 가까운지 채점하는 **거리 연산자**
집합, 그리고 그 연산자 위에 구축된 **근사 최근접 이웃(ANN) 인덱스** 타입이다.
이것들을 합치면 평범한 관계형 테이블이 벡터 저장소로 바뀐다: 각 행의
[[embedding]]을 일반 컬럼 *옆에* `vector` 컬럼으로 유지하고, 평범한 SQL 쿼리로
[[nearest-neighbor-search]]를 실행한다 — `ORDER BY embedding <거리> $query LIMIT
k`. 별도의 전문 저장소가 아니라 [[postgresql]] 안에서 이렇게 하는 핵심 이유는,
그러면 벡터가 엔진의 트랜잭션, 조인, 필터를 공유하게 된다는 데 있다: 하나의
쿼리가 관계형 컬럼에 대한 `WHERE`와 벡터 컬럼에 대한 유사도 정렬을 결합할 수
있고, 벡터는 자신이 속한 행과 원자적으로 삽입, 업데이트, 롤백된다.

## 상세 설명

### pgvector가 추가하는 세 가지

이것이 기반으로 삼는 검색 스택을 떠올려 보자. [[embedding]]은 *위치*가 의미를
인코딩하는 밀집 벡터이고; [[cosine-similarity]]는 그런 두 벡터가 얼마나 같은
방향을 가리키는지 채점하며; [[nearest-neighbor-search]]는 *"쿼리 벡터가
주어졌을 때, 저장된 벡터 중 가장 유사한 `k`개를 반환하라"*는 연산으로, 컬렉션
전체를 채점하는 대신 대부분을 가지치기하는 **ANN 인덱스**로 대규모에서도
빠르게 만들어진다. 목적에 특화된 벡터 데이터베이스는 정확히 이것만을 위해
전용된 저장소다. pgvector의 기여는 이 같은 능력을 **범용 관계형
데이터베이스에 대한 확장으로서** 제공하는 것이다 — 그래서 별도의 시스템이
필요 없다. 세 가지를 설치한다.

1. **`vector` 컬럼 타입.** `CREATE TABLE documents (id bigserial, body text,
   embedding vector(1536))`은 1536차원 [[embedding]]을 담는 컬럼을 선언한다.
   차원은 컬럼별로 고정되며, 벡터는 `id`나 `body`와 정확히 똑같이
   [[postgresql]]에 의해 저장되고, 트랜잭션 처리되고, 백업되면서 다른 값과
   똑같이 행 안에 자리한다.

2. **거리 연산자.** pgvector는 두 벡터를 받아 거리(작을수록 가까움)를 반환하는
   중위 연산자를 추가한다: **코사인 거리**를 위한 `<=>`, 유클리드(L2) 거리를
   위한 `<->`, (음의) 내적을 위한 `<#>`. 코사인 거리는 선행 개념을 직접
   표현한 것이다: `1 − `[[cosine-similarity]]로 정의되므로, *가장 유사함*
   (코사인 유사도가 `+1`에 가까움)은 *가장 작은 코사인 거리*(`0`에 가까움)를
   의미한다. 이것이 유사도 순위를 평범한 SQL `ORDER BY`로 쓸 수 있게 하는
   요소다.

3. **ANN 인덱스 타입.** pgvector는 인덱스 타입들 — **HNSW**(탐색 가능한 그래프
   인덱스)와 **IVFFlat**(클러스터링 인덱스) — 을 제공하는데, 이는
   [[nearest-neighbor-search]]가 설명하는 두 ANN 계열을 pgvector가 구현한
   것이다. 각각은 특화된 [[database-index]]다: B-트리 인덱스처럼 엔진이
   유지하는 보조 구조로 쿼리가 테이블 전체를 스캔하지 않게 하지만, 스칼라
   키로 행을 정렬하는 대신 공간상의 배치로 벡터를 조직하여 쿼리가 몇 개의
   후보로 가지치기할 수 있게 한다. 결정적으로 이는 [[postgresql]]의 기존
   인덱스 메커니즘에 연결되므로, 비용 기반 쿼리 계획이 B-트리를 선택하는
   것과 정확히 같은 방식으로 이를 **선택**할 수 있다.

### 왜 벡터를 관계형 엔진 안에 두는가 — 핵심 아이디어

독립된 벡터 데이터베이스에서 [[nearest-neighbor-search]]를 실행하고 행은
[[postgresql]]에 유지할 *수도* 있다. pgvector가 존재하는 이유는 그 둘을
**나누지 않았을 때** 얻는 것에 있다.

- **하나의 쿼리로 필터와 유사도를 함께.** 벡터가 컬럼이기 때문에, 하나의 SQL
  문장이 관계형 컬럼에 대한 제약*과* 벡터 거리에 의한 순위를 동시에 지정할
  수 있다: `SELECT id, body FROM documents WHERE lang = 'en' ORDER BY
  embedding <=> $q LIMIT 5`. 분리된 시스템에서는 이웃을 과다 조회한 뒤 나중에
  필터링하거나, 취약한 필터링된 미러를 유지해야 할 것이다; 여기서는 플래너가
  한 번의 패스로 둘 다 처리한다.
- **공짜로 얻는 트랜잭션적 일관성.** 벡터는 그 행과 같은 트랜잭션 안에서
  쓰이고, 업데이트되고, 롤백된다([[postgresql]]이 이미 모든 행에 부여하는
  ACID 보장). 동기화해야 할 두 번째 저장소도 없고, 행은 존재하는데 벡터는
  없는 시간대도 없다 — 둘은 문자 그대로 같은 행이다.
- **조인.** 이웃 결과는 그저 행의 집합이므로, 스키마의 다른 어떤
  테이블(저자, 권한, 타임스탬프)과도 평범한 SQL로 조인될 수 있다.

pgvector가 [[nearest-neighbor-search]]로부터 물려받는 비용은 같은 ANN
트레이드오프다: 근사 인덱스는 *거의* 참인 상위 `k`를 반환하며, 약간의 재현율을
서브선형 쿼리 시간과 맞바꾸고, 구축 시간, 추가 저장공간, 쓰기당 인덱스 유지
비용이 든다(`vector`의 모든 삽입이나 업데이트는 어떤 [[database-index]]든
쓰기를 느리게 만드는 것과 마찬가지로 인덱스도 업데이트해야 한다).

### 실제 사례 — 문서 테이블에 대한 의미 검색

전적으로 SQL로 코퍼스를 저장하고 의미로 질의한다.

```sql
CREATE EXTENSION vector;
CREATE TABLE documents (id bigserial PRIMARY KEY, body text, embedding vector(1536));
-- 각 행의 `embedding`은 어떤 임베딩 모델이 `body`로부터 만들어낸 1536차원 벡터다
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);   -- 코사인 거리에 대한 ANN 인덱스

-- 쿼리: 질문 벡터 $q와 의미상 가장 유사한 5개의 문서
SELECT id, body
FROM documents
ORDER BY embedding <=> $q      -- 코사인 거리: 작을수록 = 더 유사함
LIMIT 5;
```

쿼리를 추적해 보자. `$q`는 질문의 [[embedding]]이다. `ORDER BY embedding <=>
$q`는 `$q`에 대한 **코사인 거리**, 즉 `1 − `[[cosine-similarity]]로 정렬된
행을 요청하므로, 벡터가 `$q`와 가장 잘 정렬된 행이 첫 번째로 정렬된다. 인덱스가
없다면 이는 정확한 스캔이 될 것이다 — 모든 행에 대해 거리를 계산하며,
`O(N)`, 느리지만 정확한 방법이다. HNSW 인덱스가 있으면 [[postgresql]]의
플래너는 대신 탐색 가능한 그래프를 걸을 수 있다: 어느 노드에서 진입하여
`$q`에 더 가까운 벡터 쪽으로 반복해서 도약하며, 대략 `log N`개의 벡터만
건드리고 근사적으로 상위 5개를 반환한다 — [[nearest-neighbor-search]]가
정의하는 것과 같은 속도-대-재현율 거래로, 이제 Postgres 인덱스 스캔으로
표현된다. `LIMIT 5`가 `k`다. 결과는 다섯 개의 평범한 행이므로, 전체를
`WHERE`나 `JOIN`으로 감싸서 의미 검색을 어떤 관계형 조건과도 결합할 수 있다.
그 결합 — 벡터 검색이 RDBMS 안의 *그저 또 다른 연산자와 인덱스*라는 것 — 이
pgvector가 기여하는 전부다.

## 선행 개념

- [[postgresql]] — pgvector가 확장하는 관계형 엔진; `vector` 타입은 새로운
  컬럼 타입이고, ANN 인덱스는 Postgres 자체의 인덱스 및 쿼리 계획 메커니즘에
  연결되므로, 벡터는 다른 모든 데이터와 같은 트랜잭션, 저장소, 조인을 탄다.
- [[embedding]] — `vector` 컬럼이 *담고 있는* 것: 행 내용의 밀집 의미
  벡터로, 기하학적 근접성이 의미상 근접성을 나타내게 한다.
- [[nearest-neighbor-search]] — pgvector가 SQL에서 사용 가능하게 만드는
  연산(`ORDER BY <거리> LIMIT k`), 그리고 이를 서브선형으로 만드는 ANN
  인덱스를 포함한다.
- [[cosine-similarity]] — `<=>` 연산자가 채점하는 유사도: 코사인 *거리*는
  `1 −` 코사인 유사도이며, 이것이 "가장 유사함"이 SQL로 정렬 가능한 "가장
  작은 거리"가 되는 이유다.
- [[database-index]] — pgvector의 HNSW/IVFFlat이 특화하는 일반 개념: 엔진이
  전체 스캔을 피하기 위해 유지하는(여기서는 벡터 공간을 가지치기하기 위한)
  보조 구조로, 저장공간과 느려진 쓰기를 대가로 치른다.
