# 관계형 모델

## 요약

**관계형 모델(relational model)**은 *모든* 데이터를 **릴레이션(relation)** — 일상 용어로는
*테이블* — 으로 보관하는 데이터 모델이다. 이 모델의 단 하나의 구조적 아이디어는 정밀하다:
릴레이션은 **튜플들의 [[set]]**이다. *튜플(tuple)*(행)은 각 **속성(attribute)**(이름과 타입이
있는 열)마다 하나씩 값을 갖는 고정된 값의 나열이고, 릴레이션은 같은 속성들을 공유하는 그런
튜플들의 집합이다. 릴레이션이 [[set]]이기 때문에 두 가지 사실이 추가 규칙이 아니라 공짜로
따라 나온다: 행에는 **순서가 없고**(집합은 무순서이므로 "세 번째 행"은 무의미하다), **중복
행이 없다**(집합은 서로 다른 원소만 담으므로 동일한 두 튜플은 하나의 튜플이다). 그 위에서,
**키(key)**는 그 값들이 튜플을 유일하게 식별하는 속성들의 부분집합 — 행을 지칭하는 핸들 —
이고, **외래 키(foreign key)**는 한 릴레이션의 속성이 다른 릴레이션에 있는 튜플의 키 값을
담는 것으로, 별개의 릴레이션들이 서로를 참조할 수 있게 하는 연결 고리다. 이것이 SQL, 조인,
인덱스가 그 위에 세워진 모델이며, 그 힘의 전부는 값이 *보이고 타입이 있다*는 데서 나온다 —
값이 오직 키로만 도달 가능한 불투명한 블롭인 키-값 저장소와는 정반대의 거래다.

## 상세 설명

**단 하나의 구조적 약속: 데이터는 튜플들의 [[set]]이다.** 이름과 타입이 있는 열 몇 개를
고정하자 — 각각을 **속성**이라 부른다. *students* 릴레이션은 `id`(정수), `name`(텍스트),
`year`(정수)라는 속성을 가질 수 있다. **튜플**은 각 속성에 대해 속성 순서대로 값을 하나씩
고른 것이다: `(1, "Ada", 2)`는 이 세 속성 위의 튜플이다. 릴레이션은 그런 튜플들을 원소로 갖는
**[[set]]**이다. 그것이 모델의 전부다 — 아래의 모든 것은 "그것은 집합이다"의 귀결이며, 이것이
이 개념이 가정해야 하는 것이 [[set]]뿐인 이유다. [[set]]은 위치 개념이 없는 *서로 다른*
원소들의 모음이다; 멤버십("이 튜플이 릴레이션 안에 있는가?")이 집합이 답하는 유일한 질문이다.
따라서 테이블이 행들의 집합*이다*라고 말할 때 우리는 느슨하게 말하는 것이 아니다 — 릴레이션이
반드시 가져야 하는 두 성질을 정확히 내장 성질로 갖는 수학적 대상을 선택하고 있는 것이다.

**왜 "릴레이션은 [[set]]이다"가 중복 행을 금지하는가.** [[set]]은 각 원소를 많아야 한 번
담는다: `{a, b}`와 `{a, b, b}`는 같은 집합을 나타낸다. 이것을 튜플에 적용하면, 모든 속성에서
같은 값을 갖는 *동일한* 두 행은 두 행이 아니라 한 행이라는 뜻이 된다. 이미 `(1, "Ada", 2)`를
담고 있는 릴레이션에 그 튜플을 다시 추가해도 아무것도 변하지 않는다; 릴레이션은 이미 그 원소를
갖고 있다. 이것은 데이터베이스 관리자가 선택해서 켜는 정책이 아니라 "집합"이라는 말의 *의미*
그 자체다. (실제 SQL 엔진은 이것을 유명하게도 완화한다 — 키를 선언하지 않은 테이블은 진짜 중복
행을 담을 수 있어 순수한 집합이 아니라 *백/멀티셋(bag/multiset)*이 된다 — 하지만 엔진이
근사하는 모델은 집합이고, 키를 선언하면 두 행이 키에서 일치하는 것을 금지함으로써 집합의
행동이 복원된다.)

**왜 "릴레이션은 [[set]]이다"가 행 순서를 부과하지 않는가.** [[set]]은 무순서다: `{a, b}`와
`{b, a}`는 같은 집합인데, 멤버십은 원소가 *있는지*를 기록할 뿐 *어디에* 있는지는 결코 기록하지
않기 때문이다. 따라서 릴레이션에는 첫 번째 행도, 세 번째 행도, "내가 삽입한 순서대로의 행"도
없다. 쿼리 출력에서 보이는 어떤 순서든 *쿼리*가 요청한 것(명시적 정렬)이지 릴레이션의 성질이
아니다. 이것이 행을 그 *값*으로 — "`id`가 1인 학생" — 지칭하고 결코 위치로 지칭하지 않는
이유다. 모델은 데이터에 도달하는 유일한 길이 데이터가 *말하는 내용*이 되도록 위치를 의도적으로
버리며, 바로 그것이 선언적, 값 기반 질의를 가능하게 한다.

**키: 튜플에 이름을 붙이는 속성들의 부분집합.** 멤버십만으로는 "정확히 이 튜플이 존재하는가?"만
물을 수 있지만, 보통 원하는 것은 "학생 1에 관한 튜플은 *어느* 것인가?"이다. **키**는 서로 다른
두 튜플이 그 부분집합 전체에서 같은 값을 가질 수 없도록 하는 릴레이션 속성들의 부분집합이다 —
그래서 키 값을 고정하면 많아야 하나의 튜플이 골라진다. *students*에서 단일 속성 `{id}`는 키다:
두 학생이 `id`를 공유할 수 없으므로 `id = 1`은 정확히 하나의 행을 식별한다. (단일 속성으로
충분하지 않으면 키는 여러 속성의 조합일 수 있다.) 키 중 하나가 **기본 키(primary key)** —
튜플의 정식 핸들 — 로 지정된다. 키는 릴레이션이 마땅히 그래야 할 집합답게 행동하도록 만드는
장치다: 혼동할 수 있는 두 튜플이 없다는 보장, 즉 정체성에 중요한 튜플 부분에 중복이 없다는
보장이 정확히 키다.

**외래 키: 한 릴레이션이 다른 릴레이션의 튜플을 참조하는 방법.** 릴레이션은 중첩되지 않는다 —
튜플의 속성 값은 평평한, 타입 있는 스칼라이지 다른 튜플이 아니다. 그래서 "이 수강 기록은 저
학생에 관한 것이다"를 표현하려면, 한 릴레이션이 *자기* 속성 하나에 다른 릴레이션 튜플의 **키
값**을 저장한다. 그 속성이 **외래 키**다: 상대 릴레이션의 (기본) 키를 *참조*한다. 참조된 값은
저쪽에 실제로 키로서 존재해야 한다 — 이것이 *참조 무결성(referential integrity)*, 외래 키가
결코 없는 튜플을 가리키지 않는다는 모델의 약속이다. 외래 키는 모델이 데이터를 하나의 넓은
릴레이션 대신 여러 개의 좁은 릴레이션으로 펼치는 메커니즘의 전부이며, 나중에 **조인(join)**이
쿼리 시점에 그것들을 다시 꿰매기 위해 따라가는 바로 그것이다.

**모델을 정의하는 대비 — 보이는 값 대 불투명한 블롭.** 관계형 모델을 키-값 모델 옆에 놓아
보자. 키-값 저장소는 유일한 키를 *속을 들여다보지 않는 값*에 대응시킨다: 값은 불투명한
블롭이고 유일한 접근 경로는 키다 — "세 번째 필드가 2인 모든 값을 달라"고 물을 수 없다. 관계형
모델은 정반대의 약속을 한다: 모든 튜플의 모든 속성이 *보이고 타입이 있으므로*, 어떤 속성으로든
튜플을 선택할 수 있고, 속성 값 일치로 릴레이션들을 결합할 수 있고(조인), 엔진이 어떤 속성에든
인덱스를 만들어 그런 쿼리를 빠르게 할 수 있다. 대가는 키-값 저장소의 손쉬운 수평 분할을
포기하는 것(하나의 쿼리가 많은 릴레이션의 많은 튜플을 한꺼번에 건드릴 수 있다)이고, 보상은
구조화된 데이터 위의 풍부한 선언적 질의 표면 — SQL — 이다. 관계형 모델은 값을 숨기기를
거부함으로써 조인과 즉석(ad-hoc) 쿼리를 *얻어내는* 데이터 모델이다.

**구체 예시 — 두 릴레이션, 실제 행.** 작은 스키마를 정의하자.

*students* — 속성 `id`(int, **기본 키**), `name`(text), `year`(int):

```
id │ name    │ year
───┼─────────┼─────
 1 │ Ada     │ 2
 2 │ Linus   │ 3
 3 │ Grace   │ 1
```

*enrollments* — 속성 `student_id`(int, **외래 키** → `students.id`), `course`(text);
쌍 `{student_id, course}`가 **기본 키**다(한 학생은 한 과목을 많아야 한 번 수강한다):

```
student_id │ course
───────────┼────────
         1 │ CS101
         1 │ MATH200
         2 │ CS101
```

이것들을 집합으로 읽자. *students*는 세 튜플의 집합
`{ (1,"Ada",2), (2,"Linus",3), (3,"Grace",1) }`이고, *enrollments*는 집합
`{ (1,"CS101"), (1,"MATH200"), (2,"CS101") }`이다. 이제 각 성질이 작동하는 것을 보자:

- **중복 없음([[set]]이므로).** *enrollments*에 `(1,"CS101")`을 다시 추가해 보자 — 이를테면
  다시 제출된 폼. 그 튜플은 이미 집합의 원소이므로 집합은 변하지 않는다; 중복이 될 뻔한 수강
  기록은 그냥 존재하지 않는다. 그리고 `{student_id, course}`가 기본 키이므로, 이 두 속성에서
  일치하는 *준*중복조차 같은 키를 가진 두 번째 튜플로서 거부된다.
- **순서 없음([[set]]이므로).** 학생이 `1, 2, 3`으로 나열되고 수강 기록이 그 순서로 나열된
  것은 아무 의미도 담지 않는다 — 어떤 순서로 다시 출력해도 *같은 두 릴레이션*이다. "Ada의 행이
  Grace의 행보다 앞에 온다"는 모델이 저장하는 사실이 아니다. 순서를 얻으려면 순서를 요청해야
  한다(`year`로 정렬).
- **키가 튜플을 식별한다.** "학생 2는 누구인가?" 키 `id = 2`를 고정하면 *students*에서 정확히
  하나의 튜플이 일치한다 — `(2,"Linus",3)` — `id`가 키라는 것이 어떤 두 번째 튜플도 그것을
  공유하지 못하게 하기 때문이다. 조회는 구성상 모호하지 않다.
- **외래 키가 다른 릴레이션의 키를 참조한다.** *enrollments*에서 튜플 `(1,"CS101")`은
  `student_id = 1`을 갖는다. 그 값은 학생의 데이터가 *아니라* 참조다 — *students*의 어떤
  튜플의 `id`(키)와 같아야 하고, 실제로 같다: `(1,"Ada",2)`. 참조 무결성은 `student_id = 9`인
  수강 기록을 금지한다. 키 `9`를 가진 학생 튜플이 없기 때문이다. 각 수강 기록에서 이 참조를
  따라 학생으로 돌아가는 것이 정확히 "각 수강 기록을 학생 이름과 함께 나열하라"는 조인이며,
  이는 `(1,"CS101")`을 `"Ada"`와, `(1,"MATH200")`을 `"Ada"`와, `(2,"CS101")`을 `"Linus"`와
  짝짓는다. 이 중 어느 것도 키-값 저장소에서는 불가능하다. 거기서는 `students`의 값이
  불투명하고 `student_id`가 들여다볼 수 있는 어떤 것과도 일치할 수 없기 때문이다.

이것이 움직이는 모델 전체다: 두 릴레이션, 각각 이름과 타입이 있는 속성 위의 튜플들의
[[set]](따라서 무순서이고 중복이 없다); 각 튜플에 이름을 붙이는 키; 한 릴레이션의 키 값을 다른
릴레이션으로 나르는 외래 키 덕분에 둘을 조인할 수 있다 — 그리고 모든 값이 보이며, 바로 그 위에
SQL, 조인, 인덱스가 서 있다.

## 선행 개념

- [[set]] — 릴레이션은 튜플들의 집합*이다*. 따라서 모델은 자신의 두 정의적 성질을 집합
  의미론에서 직접 물려받는다: 서로 다른 원소(중복 행 없음)와 고유 순서 없음(행 위치 없음).
  [[set]] 노드는 키-값 대응이 정확히 순서쌍들의 집합임도 언급한다; 릴레이션은 그것을 *n*-튜플의
  집합으로 일반화하며, 멤버십("이 튜플이 존재하는가?")이 릴레이션이 답하는 원초적 질문이다.
