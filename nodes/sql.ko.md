# SQL (구조화 질의 언어)

## 요약

**SQL**은 [[relational-model]] 위에서 동작하는 **선언적 질의 언어**다. 그
핵심 약속은 *선언적*이라는 단어에 있다: 여러분은 원하는 **결과**가 무엇인지 —
어떤 컬럼을, 어떤 릴레이션에서, 어떤 키로 조인하여, 어떤 필터로 남기고, 어떤
집계로 요약할지 — 를 적을 뿐, 그것을 계산하는 절차는 **적지 않는다**.
루프도 없고, "이 릴레이션을 열어서, 행 단위로 스캔하고, 저것은 인덱스에서
찾아라" 같은 것도 없다. 여러분은 답을 서술하고, 데이터베이스의 *쿼리
플래너*가 단계를 결정한다. 핵심 쿼리는 `SELECT … FROM … WHERE …`다: `FROM`이
릴레이션(들)을 이름 짓고, `WHERE`는 조건에 매치되는 튜플을 남기며(**선택**),
`SELECT`는 요청한 속성을 남긴다(**투영**). `JOIN`은 한 릴레이션의 값이 다른
릴레이션의 값과 일치하는 곳마다 두 릴레이션의 튜플을 결합한다 — 거의 항상
**외래 키**가 그것이 참조하는 **기본 키**와 매치되는, [[relational-model]]이
정의하는 바로 그 연결이다. 집계와 함께 쓰인 `GROUP BY`(`COUNT`, `SUM`)는
여러 튜플을 그룹당 하나의 요약 튜플로 축소한다. 그리고 모든 쿼리의 결과는
**그 자체가 릴레이션**이다 — 이름 붙은 속성에 대한 튜플의 집합 — 이것이
하나의 쿼리가 다른 쿼리에 입력될 수 있게 하는 *폐쇄성(closure)* 속성이다.
선언적이라는 것의 보상은, 하나의 `SELECT`가 같은 답을 내면서도 여러 다른
방식으로 실행될 수 있어서, 엔진이 가장 빠른 방식을 자유롭게 고를 수
있다는 것이다.

## 상세 설명

**핵심 아이디어: 어떻게가 아니라 무엇을.** [[relational-model]]은 우리에게
데이터를 **릴레이션**으로 준다 — 이름 붙은 타입의 속성에 대한 튜플의
집합으로, 각 튜플을 이름 짓는 **키**와, 한 릴레이션의 키 값을 다른
릴레이션으로 실어 나르는 **외래 키**가 있다. SQL은 그런 릴레이션에 *질문을
던지는* 언어다. SQL을 SQL답게 만들면서도, 단순한 편의처럼 들려서 놓치기
쉬운 하나의 아이디어는, SQL 쿼리가 **선언적**이라는 것이다: 그것은 *결과의
서술*이지, *그것을 만들어내는 레시피*가 아니다. 하나의 과제 — "2학년
학생을 나열하라" — 에 대한 두 태도를 대조해 보자.

- **명령형**(어떻게): *"빈 리스트를 할당한다. students 릴레이션을 연다.
  각 튜플에 대해, `year` 속성을 읽는다; 2와 같으면 튜플의 `name`을
  리스트에 추가한다. 리스트를 반환한다."* 모든 단계 — 반복, 순서, 비교,
  누적 — 를 여러분이 명시한다.
- **선언형**(무엇을): `SELECT name FROM students WHERE year = 2`. 릴레이션
  (`FROM students`), 튜플이 만족해야 할 조건(`WHERE year = 2`), 돌려받고
  싶은 속성(`SELECT name`)을 이름 짓는다. 여러분은 결코 *스캔하라*고
  말하지 않고, *어떤 순서로*도 말하지 않고, 아무것도 할당하지 않는다.

둘 다 같은 답을 반환한다. 차이는 **누가 절차를 선택하는가**이다. 명령형
버전에서는 *여러분이* 선택했고; 선언형 버전에서는 그 선택을 엔진에게
넘겼다. 그 넘겨줌이 핵심 전체이며, 그 보상은 끝에 나타난다: 여러분은 결과만
서술했기 때문에, 엔진은 그 결과를 내는 어떤 절차로든 계산할 수 있고 —
사용 가능한 것 중 가장 저렴한 것을 고른다 — 이는 전체 스캔과 인덱스 조회
사이만큼이나 자릿수 단위로 다를 수 있다. 여러분은 방법을 무시해도 되고,
엔진은 그것을 최적화할 수 있다.

**핵심 쿼리의 세 조각, 릴레이션에 대해.** `SELECT … FROM … WHERE …`는
단일 [[relational-model]] 릴레이션에 대한 두 연산으로 직접 대응된다.

- **`FROM r`**은 원재료가 되는 튜플을 가진 릴레이션 `r`을 이름 짓는다.
- **`WHERE 조건`**은 **선택**이다: 조건이 참인 튜플만 남긴다 — *행*에
  대한 필터다. 결과는 `r`의 튜플의 부분집합이다. 릴레이션이 집합이기
  때문에, "`year = 2`인 튜플을 남겨라"는 위치나 순서에 대한 참조 없이도
  잘 정의된다.
- **`SELECT a, b`**는 **투영**이다: 속성 `a, b`만 남긴다 — *열*에 대한
  필터다. 살아남은 각 튜플에서, 이름 붙지 않은 모든 속성을 버린다.

따라서 `SELECT name FROM students WHERE year = 2`는 다음과 같이 읽힌다:
`students`를 가져와서, `year = 2`인 튜플을 *선택*한 뒤, 단일 속성
`name`으로 *투영*하라.

**`JOIN` — 키 일치로 두 릴레이션을 결합하기.** 단일 릴레이션은 자기
자신에 관한 질문에만 답한다. "각 *학생*이 **이름으로** 어떤 *강좌*에
등록되어 있는가"에 답하려면, 두 릴레이션을 결합해야 한다 — 그리고
[[relational-model]]이 이미 그 다리를 만들어 두었다: 한 릴레이션의
**외래 키**가 다른 릴레이션에 있는 튜플의 **키 값**을 담는다. `JOIN`은
*그 다리를 따라가는* 연산이다. `students JOIN enrollments ON
students.id = enrollments.student_id`는 학생의 기본 키 `id`가 등록의
외래 키 `student_id`와 **정확히 같을 때** `students` 튜플과
`enrollments` 튜플을 짝짓는다. 그런 매치되는 쌍마다 두 릴레이션의
속성을 모두 담은 하나의 더 넓은 튜플이 된다. 이는 SQL에 덧붙여진 새로운
아이디어가 아니다 — [[relational-model]]의 외래 키 참조를 *따라간* 것일
뿐이다: 모델은 데이터를 좁은 릴레이션들로 퍼뜨려 키로 연결하는데, 이는
정확히 질의 시점에 조인이 그것들을 다시 이어붙일 수 있도록 하기 위함이다.
조인 조건은 거의 항상 *바로 이* 키/외래 키 동등성인데, 그것이 스키마가
표현하도록 설계된 관계이기 때문이다.

**`GROUP BY` + 집계 — 튜플을 요약으로 축소하기.** 선택과 투영은 개별
튜플을 반환한다; 종종 질문은 튜플의 *그룹*에 관한 것이다: "각 학생은
등록이 몇 개인가?" `GROUP BY student_id`는 조인된 튜플을 서로 다른
`student_id`마다 하나의 그룹으로 나누고, **집계**는 — `COUNT(*)`는 각
그룹의 튜플 수를 세고, `SUM(x)`는 그것들에 걸쳐 속성 하나를 더한다 —
각 그룹을 *하나의* 요약 튜플로 축소한다. 출력은 입력 튜플당 하나가
아니라 그룹당 한 행이다. 그런 다음 `HAVING` 절은 `WHERE`가 개별 튜플을
필터링하는 방식으로 그런 *그룹* 요약을 필터링한다(예를 들어 카운트가
1을 초과하는 그룹만 남긴다).

**폐쇄성: 답 자체가 릴레이션이다.** 모든 SQL 쿼리는 릴레이션을 입력받아
릴레이션을 출력한다 — 이름 붙은 속성에 대한 튜플의 집합으로, 같은
[[relational-model]] 규칙을 따른다(정렬하지 않는 한 순서가 없고, 이름
붙은 결과 컬럼이 그 속성이다). 이것이 **폐쇄성** 속성이며, SQL이 조합
가능한 이유다: 쿼리의 출력이 그 입력과 같은 종류의 객체이기 때문에,
한 쿼리를 다른 쿼리에 먹일 수 있다 — 조인의 출력을 그룹화할 수 있고,
그룹화된 결과를 다시 조인할 수 있으며, 서브쿼리의 결과 릴레이션이 다른
쿼리의 `FROM`에 앉을 수 있다. 이 모델은 정수가 덧셈에 대해 닫혀있는
것처럼, 질의에 대해 닫혀있다.

**실제 사례 — JOIN + WHERE + 집계, 구체적인 행으로.**
[[relational-model]]의 스키마를 재사용한다.

*students* — `id`(정수, **기본 키**), `name`(텍스트), `year`(정수):

```
id │ name    │ year
───┼─────────┼─────
 1 │ Ada     │ 2
 2 │ Linus   │ 3
 3 │ Grace   │ 1
```

*enrollments* — `student_id`(정수, `students.id`를 참조하는 **외래
키**), `course`(텍스트); 기본 키 `{student_id, course}`:

```
student_id │ course
───────────┼────────
         1 │ CS101
         1 │ MATH200
         2 │ CS101
```

퇴화하지 않은 질문을 하나 던져 보자 — *"2학년 또는 3학년인 각 학생에
대해, 몇 개의 강좌에 등록되어 있는가? 학생의 이름과 그 수를 나열하라."*
SQL로는 다음과 같다.

```sql
SELECT   students.name, COUNT(*) AS course_count
FROM     students
JOIN     enrollments ON students.id = enrollments.student_id
WHERE    students.year >= 2
GROUP BY students.id, students.name;
```

결과에 대한 서술로서 이를 추적해 보자(아래의 순서는 *하나의* 읽기
방식일 뿐, 엔진이 반드시 써야 하는 절차가 아니다).

1. **`FROM students JOIN enrollments ON students.id =
   enrollments.student_id`** — 외래 키를 따라간다. 각 등록은 자신의
   `student_id`와 `id`가 같은 유일한 학생과 짝지어진다.
   - `(1,"CS101")` → 학생 `(1,"Ada",2)` → `(Ada, 2, CS101)`
   - `(1,"MATH200")` → 학생 `(1,"Ada",2)` → `(Ada, 2, MATH200)`
   - `(2,"CS101")` → 학생 `(2,"Linus",3)` → `(Linus, 3, CS101)`

   Grace(`id 3`)가 사라짐을 주목하라: 어떤 등록의 `student_id`도 3이
   아니므로, 짝이 만들어지지 않는다. 조인은 매치된 튜플만 만들어낸다.
2. **`WHERE students.year >= 2`** — 조인된 튜플에 대한 선택. Ada의
   `year`는 2이고 Linus는 3으로, 둘 다 통과한다; 조인된 세 튜플 모두
   살아남는다. (만약 `>= 3`을 물었다면, Ada의 두 행이 여기서 탈락했을
   것이다 — 필터는 카운트 *이전에* 작동하므로, "3학년 이상 학생의
   강좌"는 Linus의 것만 셀 것이다.)
3. **`GROUP BY students.id, students.name`** — 생존자를 학생별로
   나눈다: *Ada* 그룹 = `{(Ada,2,CS101), (Ada,2,MATH200)}`, *Linus*
   그룹 = `{(Linus,3,CS101)}`.
4. **`SELECT students.name, COUNT(*)`** — 투영과 집계. 각 그룹이 하나의
   튜플로 축소된다: Ada 그룹의 카운트 = 2, Linus 그룹의 카운트 = 1.

**결과 릴레이션** — 그 자체로 속성 `(name, course_count)`에 대한
튜플의 집합이다.

```
name  │ course_count
──────┼─────────────
Ada   │ 2
Linus │ 1
```

그 출력은 그 자체로 하나의 릴레이션이므로(폐쇄성), 이를 감싸는 쿼리에
의해 다시 필터링, 조인, 그룹화될 수 있다.

**왜 선언적인 것이 이득인가 — 같은 답, 두 절차.** 쿼리 어디에도
*어떻게* 계산할지는 말하지 않았다. 엔진의 플래너는 자유롭게 선택할 수
있고, 적어도 두 가지 진정으로 다른 절차가 정확히 이 결과 릴레이션을
낸다.

- **스캔-후-필터(네스티드 루프 조인).** `enrollments`의 모든 튜플을
  읽는다; 각각에 대해, `students`를 스캔하여 `student_id`와 `id`가
  일치하는 것을 찾는다; `year >= 2`를 검사한다; 그런 다음 학생별 집계에
  누적한다. 비용은 `students`의 반복적인 스캔이 지배한다.
- **인덱스 조회(인덱스 네스티드 루프 / 해시 집계).** `students`에
  기본 키 `id`에 대한 인덱스(키 값에서 튜플로의 정렬되거나 해시된
  접근 경로)가 있다면, 엔진은 각 등록에 대해 매치되는 학생을 직접
  *조회*할 수 있다 — 스캔 없이 — `year >= 2`를 적용하고,
  `student_id`로 키가 매겨진 해시 테이블에 그룹 카운트를 유지한다.
  큰 릴레이션에서 이는 극적으로 더 저렴하다.

둘 다 같은 두 행짜리 답을 계산한다. **SQL이 결과만 선언했기 때문에,
엔진은 어떤 인덱스가 존재하는지에 따라 더 빠른 쪽을 자유롭게 선택할 수
있다** — 그리고 데이터나 인덱스가 바뀌면 쿼리 텍스트가 전혀 바뀌지
않아도 다시 결정할 수 있다. 그 자유가 바로 선언적 태도가 사는 것이다:
절차를 이름 짓기를 거부함으로써, SQL은 엔진에게 최적화할 여지를
넘겨준다. 이것이 언어와 모델 사이의 전체 관계다: [[relational-model]]은
모든 값을 가시적이고 키로 연결되게 만들어서 *선택, 투영, 조인, 집계*가
애초에 물을 수 있는 것이 되게 하고; SQL은 그것들을 묻기 위한 선언적
표면이며; 선언성이야말로 "물을 수 있음"을 "물을 수 있고 *또한*
빠름"으로 바꾸는 것이다.

## 선행 개념

- [[relational-model]] — SQL은 *릴레이션에 대한* 질의 언어다. 모든 SQL
  구성 요소는 모델의 객체에 대한 연산이다: `WHERE`/`SELECT`는 릴레이션의
  튜플과 속성에 대한 선택과 투영이고; `JOIN`은 모델의 외래 키 → 기본
  키 참조를 따라가 두 릴레이션을 결합하며; `GROUP BY`는 릴레이션의
  튜플을 나누고; 어떤 쿼리의 결과든 *그 자체가* 릴레이션이다(폐쇄성).
  모델의 릴레이션, 키, 외래 키가 없다면 SQL의 어떤 구성 요소도 지칭할
  대상이 없을 것이다.
