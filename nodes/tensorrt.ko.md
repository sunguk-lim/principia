# TensorRT

## 요약

**TensorRT**는 NVIDIA의 **추론 최적화기이자 런타임**이다: *학습된* [[neural-network]]를
받아 이를 **사전에**([[jit-vs-aot-compilation]]에 따라) 같은 순방향 패스를 훨씬 빠르게
실행하는 GPU-특화 **"엔진"**으로 컴파일한다. 이는 학습 프레임워크가 아니며 새로운 수학을
전혀 추가하지 않는다 — 빌드 시점에 적용되는 세 가지 최적화를 통해 기존 계산을
하드웨어에 맞게 *다시 표현*할 뿐이다: **레이어 퓨전**(레이어 체인을 단일
[[cuda-kernel]]로 병합하여 중간 결과가 GPU 메모리를 왕복하지 않게 함 — [[roofline-model]]이
예측하는 메모리 바운드 개선), **정밀도 감소**([[quantization]]을 통해 가중치/활성화를
FP16이나 INT8로 저장하여 훨씬 적은 바이트를 이동), 그리고 **커널 오토튜닝**(각 레이어에
대해 여러 후보 [[cuda-kernel]] 구현을 벤치마크하여 *이* GPU와 *이* 텐서 형태에 대해 가장
빠른 것을 남긴다). 결과물은 하나의 GPU 아키텍처에 특화된 직렬화된 엔진이다 — 빠르고
웜업이 필요 없이 실행되지만, [[jit-vs-aot-compilation|AOT]] 아티팩트가 모두 그렇듯
경직되어 있다: 다른 GPU를 위해서는 다시 빌드해야 한다.

## 상세 설명

### TensorRT는 무엇*인가* — 프레임워크가 아니라 추론용 컴파일러

학습 프레임워크는 [[neural-network]]를 **범용적으로** 실행한다: 모델을 레이어별로
훑으며 각 연산(합성곱, 편향 더하기, 활성화, 정규화)마다 별도의 범용
[[cuda-kernel]]을 실행하는데, 학습 중에는 네트워크가 계속 바뀌고 그래디언트가 모든
중간 지점을 통해 역방향으로 흘러야 하기 때문이다. 그 범용성은 **추론** 시점에는
낭비된다. 가중치가 고정되고 순방향 패스만, 그것도 같은 형태로 반복해서 실행되기
때문이다. TensorRT는 이것을 활용하는 도구다: 학습된 네트워크를 *빌드 시점*에 **한
번** 소비하여, 하나의 목표 GPU를 위한 고정된, 최적화된 실행 계획인 특화된 **엔진**을
내보낸다. 붙잡아 둘 개념은 **컴파일러**다: 이식 가능한 모델을 입력하면, 하드웨어에
특화된 최적화된 코드를 출력하며, 최적화 작업은 미리 한 번만 지불된다. 아래는 모두
*어떤* 최적화가 적용되며 각각이 *왜* 이기는지에 관한 것이다.

### 문제: 순진한 순방향 패스는 메모리 바운드이고 실행 부담이 크다

학습된 모델을 연산별로 실행하면 두 비용이 지배하며, 둘 다 산술적이라기보다는 구조적이다.
첫째, **많은 레이어가 메모리 바운드다.** [[roofline-model]]에 따르면, 연산의 속도
상한은 그 *산술 강도* — GPU 메모리로부터 끌어온 바이트당 수행된 FLOP 수 — 에 의해
정해진다. 편향 더하기나 ReLU는 원소당 대략 하나의 저렴한 연산을 하면서 그 원소를
읽고 다시 쓰므로, 강도는 능선(ridge)에서 훨씬 *왼쪽*에 있어, GPU는 자신의 연산
상한에 전혀 근접하지 못한 채 메모리 트래픽을 기다리며 놀게 된다. 둘째, **각 연산은
자기만의 [[cuda-kernel]] 실행**이며, 모든 실행은 고정 오버헤드와 필수 왕복을 동반한다:
레이어는 자신의 입력 텐서를 GPU 메모리에서 읽고 출력 텐서를 다시 쓰며, 그래야 다음
레이어가 그것을 다시 읽을 수 있다. 열 개 레이어의 체인은 필요하지도 않았을 아홉 개의
중간 텐서를 쓰고 다시 읽는다. 게다가, **FP32 가중치는 저정밀도 사본보다 2–4배 더
많은 바이트를 이동한다.** TensorRT의 세 가지 최적화는 정확히 이것들을 공격한다:
퓨전은 왕복을 없애고, 정밀도는 바이트를 줄이며, 오토튜닝은 남은 것에 대해 가장 빠른
커널을 고른다.

### 최적화 1 — 레이어/텐서 퓨전(더 적은 커널, 왕복 없음)

TensorRT는 네트워크를 훑어 **함께** 계산될 수 있는 레이어 체인을 찾아 이들을 **단일**
[[cuda-kernel]]로 퓨전한다. 전형적인 경우는 *합성곱 → 편향 → 활성화*다: 각각
전체 특징 맵 텐서를 읽고 쓰는 세 개의 커널 대신, 하나의 퓨전된 커널이 합성곱을
계산하고, **각 출력 원소가 아직 레지스터에 있는 동안** 편향을 더하고 활성화를
적용한 뒤, GPU 메모리로의 단일 쓰기-되돌림을 수행한다.

이것이 이기는 이유는 정확히 퓨전에 대한 [[roofline-model]]의 교훈이다: 편향과
활성화는 그것들만으로는 메모리 바운드이지만, 퓨전되면 *이미 로드되었고* 어차피
쓰였을 바이트에 산술을 더하는 것이다 — 이제 한 번의 로드와 한 번의 저장이 세
레이어 몫의 작업을 나른다. 원소당 산술 강도가 상승하여 연산을 능선 **쪽으로
오른쪽으로** 밀며, 제거된 중간 텐서들은 순수하게 제거된 트래픽이다. 커널이
줄어드는 것은 실행 횟수도 줄인다는 뜻이므로, 고정된 실행당 오버헤드도 줄어든다.
퓨전은 값이 사는 *언제와 어디*(레지스터 대 GPU 메모리)를 바꿀 뿐, *무엇이*
계산되는지는 결코 바꾸지 않는다 — 결과는 순방향 패스와 비트 단위로 동일하다.

### 최적화 2 — 정밀도 감소와 INT8 캘리브레이션([[quantization]])

TensorRT는 네트워크를 FP32 대신 **FP16**이나 **INT8**로 저장하고 계산할 수 있다.
이것이 [[quantization]]이다: INT8 값은 공유된 **스케일** `s`를 곱한 작은 정수
코드이며, 복원된 값은 `code × s`이고 반올림 오차는 `≤ s/2`로 제한된다. 그 성과는
이동되는 바이트다 — INT8 가중치는 FP32의 **4분의 1** 크기다 — 이는 위의 메모리
바운드 레이어들을 직접 완화한다(원소당 바이트가 적어지면 ⇒ 같은
[[roofline-model]] 기울기 위에서 강도가 높아진다). 저정밀도 행렬 연산도 GPU의
전용 유닛 위에서 더 빠르게 실행된다.

위험은 정확도다. INT8의 격자는 거칠고, ([[quantization]]에서 보았듯) 오차는
스케일 `s`가 커질수록 자라므로, 잘못 선택된 `s` — 드문 이상치 활성화에 의해 정해진
것 — 는 모든 정상적인 값을 거칠게 만든다. TensorRT의 해법은 **캘리브레이션**이다:
실제 입력의 작고 *대표적인* 표본에 대해 FP32 모델을 실행하여 각 레이어의 활성화의
실제 범위를 기록하고, FP32와 INT8 값 분포 사이의 불일치를 **최소화**하도록 각
`s`를 선택한다(두 분포를 통계적 거리로 비교하여 INT8 히스토그램이 FP32의 것과
가장 잘 맞는 스케일을 고른다). 스케일들이 최악의 경우 경계가 아니라 관측된
데이터에 맞춰지기 때문에, INT8 추론은 **재학습 없이** 정확도의 거의 전부를
유지한다 — 캘리브레이션은 측정 패스이지 학습 패스가 아니다.

### 최적화 3 — 커널 오토튜닝(경험적, 하드웨어-특화)

단일 레이어에 대해 하나의 "최선" [[cuda-kernel]]은 없다 — *많은* 유효한 구현들
(서로 다른 타일 크기, 메모리 레이아웃, 알고리즘)이 있으며, 어느 것이 가장 빠른지는
정확한 텐서 형태**와** 특정 GPU(연산 유닛 수, 메모리 대역폭, 지원되는 정밀도)에
달려 있다. TensorRT는 추측하지 않는다. 빌드 시점에 **실제 목표 GPU에서 각 레이어의
후보 커널들을 벤치마크**하고 가장 빠른 것을 남긴다 — NVIDIA는 각 후보를 *택틱
(tactic)*이라 부른다. 그래서 엔진은 레이어마다, 이 하드웨어와 이 형태들에 맞춰
경험적으로 선택된 커널을 담는다. 이것이 빌드가 **하드웨어-특화적이고 느린** 이유다:
그저 코드를 번역하는 것이 아니라 실제 타이밍 실험을 돌리고 있는 것이다.

### 엔진 빌드는 사전에 이루어진다 — AOT의 트레이드오프와 함께

세 가지 최적화 모두 **한 번**, 빌드 시점에 일어나며 직렬화된 **엔진** 파일로
고정된다. 이는 교과서적인 [[jit-vs-aot-compilation|AOT 컴파일]]이다: 값비싼
작업(퓨전 결정, 캘리브레이션, 커널 벤치마킹)이 배포 전에 지불되므로, 런타임에는
컴파일 정지도 호출별 최적화도 *없다* — 엔진은 첫 추론부터 백만 번째까지 웜업된
상태로 그저 실행된다. 그리고 그 노드가 서술하는 AOT의 경직성을 정확히 물려받는다:
엔진은 하나의 GPU 아키텍처와 그것이 빌드된 범위의 입력 형태에 특화되어 있으므로
**이식 가능하지 않다** — 다른 GPU 세대나, 빌드된 범위 밖의 형태는 엔진을 **다시
빌드**해야 한다. TensorRT는 빌드 시점 비용과 유연성을, 웜업 없이 하드웨어에 맞춰진
추론 속도와 맞바꾼다.

### 구체적 사례 — 합성곱 → 편향 → ReLU 블록, 퓨전되고 양자화됨

**M = 1,000,000**개 원소의 특징 맵 텐서 하나가 *합성곱 → 편향 → ReLU*를 통해
흐르는 경우를 상정하자. 이 칩의 [[roofline-model]] 능선은 대략 33 FLOP/바이트
근처에 있다.

**퓨전되지 않은 FP32(원소당 4바이트).** 편향과 ReLU는 별도의 메모리 바운드
커널이다:

- 편향: M개 원소 읽기(4 MB) + M개 쓰기(4 MB) = **8 MB** 이동, 대략 M개의 저렴한
  덧셈 수행.
- ReLU: 4 MB 읽기 + 4 MB 쓰기 = **8 MB** 이동, 대략 M개의 최댓값 연산 수행.

이는 약 2M FLOP에 대해 **16 MB**의 메모리 트래픽이다 — 강도 `≈ 2×10⁶ / 16×10⁶ =
0.125` FLOP/바이트로, 메모리 바운드 기울기 깊숙이 있다: 상한은 `대역폭 × 0.125`이며,
연산 최고치의 1% 미만이다. 합성곱의 출력 텐서는 GPU 메모리에 쓰였다가 두 번이나
곧바로 다시 읽혔을 뿐이다.

**퓨전된 FP32.** 편향과 ReLU를 합성곱의 에필로그로 접는다: 이미 레지스터에 있는
각 합성곱 출력 원소는 단일 쓰기-되돌림 *전에* 편향을 더하고 ReLU를 적용받는다.
두 개의 추가 커널 — 그리고 그것들의 **16 MB** 왕복 트래픽 — 이 **완전히 사라지며**,
편향/ReLU 산술은 이제 추가 바이트를 전혀 들이지 않는다. 동일한 수치 결과, 메모리
바운드 꼬리는 제거되었다.

**퓨전 + INT8(원소당 1바이트).** 이제 양자화한다. 살아남은 로드/저장과 합성곱
자신의 가중치가 옮기는 모든 바이트가 **4배** 줄어들어(4바이트 → 1바이트), 합성곱 —
연산이 많은 부분 — 은 4분의 1의 바이트만 이동하면서 빠른 저정밀도로 자신의 행렬
연산을 실행하며, 캘리브레이션은 출력을 `≤ s/2` 오차 경계 안에 유지하여 정확도를
지킨다. 두 효과를 쌓아 보면: 퓨전은 메모리 바운드 왕복을 제거했고, INT8은 남은
것의 바이트를 4분의 1로 줄였다 — 한때 GPU를 놀게 했던 그 블록이 이제 자신의 연산
상한 근처에서 실행된다. 그 복합 효과 — 강도를 높이도록 재구성한 다음 바이트를
줄이는 것 — 가 학습된 모델을 빠른 TensorRT 엔진으로 바꾸는 것이며, 네트워크가
계산하는 내용에는 아무런 변화가 없다.
