# 사용자 모드 대 커널 모드

## 요약

CPU는 두 가지 **특권 수준(privilege level)** 중 하나로 명령어를 실행한다 —
이는 프로세서 자체의 회로에 설정된 내부 상태의 한 조각으로, 실행 중인
명령어가 얼마만큼을 할 수 있는지를 결정한다. **커널 모드**(x86 칩에서는
*링 0(Ring 0)*이라 부른다)는 완전히 특권을 가진 수준이다: 그곳의 코드는
어떤 명령어든 실행할 수 있고 어떤 메모리나 하드웨어든 건드릴 수 있다.
바로 여기서 [[kernel]]이 실행된다. **사용자 모드**(*링 3*)는 제한된
수준이다: 여러분의 셸, 파이썬 스크립트, 브라우저 같은 평범한 응용
프로그램 코드가 이곳에서 실행되며, 하드웨어에 의해 특권 명령어로부터,
하드웨어를 직접 건드리는 것으로부터, [[kernel]]이나 다른 프로그램의
메모리를 읽는 것으로부터 차단된다. 이 구분 전체의 요점은 *보호*다:
그 경계가 CPU 자체에 의해 강제되기 때문에, 버그가 있거나 악의적인
사용자 프로그램은 [[kernel]]이나 다른 프로그램을 물리적으로 **손상시킬
수 없다**. 그것은 오직 좁고 통제된 진입점을 통해 [[kernel]]에게 자신을
대신해 행동해 달라고 요청할 수 있을 뿐이다.

## 상세 설명

### 핵심 발상: 하드웨어가 복종하는 특권 비트

여기서 다루는 개념은 [[kernel]]도 아니고 어떤 단일 명령어도 아니다. 그것은
**하드웨어가 강제하는 특권 경계** 그 자체다 — CPU가 "지금 실행 중인
코드는 신뢰된다" 또는 "지금 실행 중인 코드는 신뢰되지 않는다"고 말하는
작은 상태 조각을 지니고 있으며, 그 상태가 "신뢰되지 않음"을 말할 때
프로세서가 위험한 연산을 *물리적으로 거부한다*는 사실이다.

점점 더 높아지는 허가 등급의 층들을 가지고, 오직 하나의 경비된
엘리베이터를 통해서만 도달할 수 있는 정부 건물을 떠올려 보라:

- **링 0 — 금고.** 완전한 하드웨어 접근. 오직 [[kernel]]만이 여기서
  실행된다. 한 번의 실수가 기계 전체를 멈출 수 있다.
- **링 3 — 로비.** 매우 제한적이다. *모든* 평범한 프로그램이 여기서
  실행된다.

(x86 칩은 실제로는 0부터 3까지 네 개의 링을 정의하며, 링 1과 2는
장치 드라이버를 위한 것이었지만 리눅스 같은 실제 시스템은 그것들을
비워 두고 0과 3만을 사용한다. 그래서 실질적으로 세상은 정확히 두
값만 가진다: 커널 모드 또는 사용자 모드.)

결정적인 단어는 *강제된다*이다. 특권 수준은 소프트웨어가 지키기로
합의한 관례가 아니다 — 그것은 1985년 이래로 모든 x86 칩에 존재하는
CPU 내부의 회로다. 링 3에서 실행되는 소프트웨어는 **자신이 어느
링에 있는지에 대해 거짓말할 수 없으며**, 스스로를 링 0으로 승격시킬
수도 없다. 결정하는 것은 하드웨어다.

### 왜 우리에게 이것이 필요한가: 물리적 사실로서의 보호

이 경계가 없다면 모든 프로그램이 기계 전체의 열쇠를 갖게 될 것이다.
텍스트 편집기의 버그 하나가 [[kernel]]의 코드를 덮어쓸 수도 있고,
악의적인 프로그램이 다른 프로그램의 메모리에서 여러분의 비밀번호를
읽어낼 수도 있으며, 부주의한 루프가 시스템이 프로그램들 사이를
전환하는 데 쓰는 타이머를 꺼버려 모든 것을 멈추게 할 수도 있다.

이 두 단계 구분은 프로그램이 잘 행동해 주기를 요구함으로써가 아니라,
잘못된 행동을 *실행 불가능하게* 만듦으로써 그런 가능성들을 없앤다.
그 근거는 정확히 이렇다: 모든 프로그램이 잘 작성되어 있다는 것에
의존하는 보장은 전혀 보장이 아니지만, CPU에 배선된 보장은 적극적으로
적대적인 코드에 대해서도 유지된다. 격리는 소프트웨어에 대한 희망이
아니라 실리콘의 속성이 된다.

### 각 모드가 할 수 있는 것과 할 수 없는 것

이 경계는 CPU의 명령어 집합과 메모리를 관통하는 선을 그어 정의된다.
**사용자 모드(링 3)**에서 프로그램은 *할 수 있다*:

- 자신의 **자신** 메모리를 읽고 쓸 수 있다;
- 산술, 비교, 분기, 루프 같은 평범한 명령어를 실행할 수 있다;
- 더 많은 것을 요청하는 유일하게 승인된 방법인 **시스템 콜**을 할 수
  있다.

사용자 모드에서 프로그램은 *할 수 없다*:

- 하드웨어와 직접 대화할 수 없다(장치 포트를 읽고 쓰는 명령어는
  특권 명령어다);
- 메모리를 매핑하는 표를 바꾸거나 다른 프로그램의 메모리로 전환할
  수 없다;
- CPU의 인터럽트를 끌 수 없다(그렇게 하면 기계를 독점할 수 있게
  된다);
- 다른 프로그램의 메모리를 읽을 수 없고, [[kernel]]의 메모리조차
  *읽을* 수 없다.

**커널 모드(링 0)**에서 코드는 사용자 모드가 할 수 있는 *모든* 것에
**더해**, 위의 모든 금지된 연산도 할 수 있다: 특권 명령어를 실행하고,
메모리를 재매핑하고, 인터럽트를 켜고 끄고, 시스템의 어떤 주소에도
도달하고, 하드웨어를 직접 조종한다. 이것이 바로 모두를 위해 모든
하드웨어를 관리하도록 신뢰받은 유일한 프로그램인 [[kernel]]만이
그곳에서 실행되는 이유다.

### 하나의 명백하지 않은 단계: 선을 넘는 것은 공짜가 아니다

사용자 모드가 이렇게 적은 것만 할 수 있다면, 파일을 열고, 네트워크
패킷을 보내고, 더 많은 메모리를 얻는 것 같은 실제 작업은 어떻게
일어나는가? 답은 직접 보기 전까지는 마법처럼 보이는 부분이다:
**프로그램은 스스로를 승격시키지 않는다. 그것은 요청하고, 하드웨어가
고정된 문을 통해 그것을 대신해 모드를 전환해 준다.**

제어권이 사용자 모드에서 커널 모드로 넘어가는 방법은 정확히 세 가지가
있으며, 그 모두는 [[kernel]]이 미리 정해 둔 주소에서 [[kernel]]에게
제어권을 넘긴다:

1. **시스템 콜** — 프로그램이 의도적으로 특별한 "커널로 진입하기"
   명령어, 즉 위로 가는 엘리베이터를 실행한다;
2. **[[interrupt]]**(인터럽트) — 디스크 작업 완료나 키 입력 같은
   하드웨어 장치가 CPU에 신호를 보낸다;
3. **폴트(fault)** — 실행 중인 명령어가 무언가 위법한 일을 해서
   CPU가 트랩한다.

어느 경우든 CPU는 특권 수준을 링 0으로 뒤집고 [[kernel]]의 일부인
처리기로 점프한다. 사용자 프로그램은 링 0에서 무엇이 실행될지 결코
*선택*할 수 없다. 그것은 오직 이 전환들 중 하나를 촉발할 수 있을
뿐이며, 무엇을 할지는 [[kernel]]이 결정한다. 이것이 초당 수백만
번씩 넘어지는데도 이 경계가 안전하게 유지되는 이유다: 문은 고정되어
있고, 그 반대편에는 오직 [[kernel]]만이 있다.

### 구체적 사례: 선을 넘으려는 프로그램

한 구체적인 시도를 각 단계를 이전 단계로부터 유도하며 추적해 보자.
작은 C 프로그램이 [[kernel]] 메모리에서 바이트 하나를 직접 읽으려
한다 — 그것이 건드릴 이유가 전혀 없는 주소다:

```c
int main() {
    char *k = (char *)0xffffffff81000000UL;  // 커널 메모리 안의 한 주소
    printf("Kernel byte: %c\n", *k);          // 그것을 역참조한다
    return 0;
}
```

특권 수준을 지켜보며 한 단계씩:

1. **프로그램은 링 3에서 실행된다.** 그것은 평범한 프로세스로
   시작되었으므로, `main`을 실행하는 내내 CPU의 특권 상태는 *사용자
   모드*를 가리킨다.
2. **프로그램은 역참조 `*k`를 실행한다.** 이는 평범한 메모리 읽기
   명령어다 — 그 명령어 자체에는 특별한 것이 없다. 하지만 주소
   `0xffffffff81000000`은 [[kernel]]이 링-0-전용으로 표시해 둔 영역
   안에 있다.
3. **CPU는 읽기를 완료하기 전에 특권을 확인한다.** 현재 수준(링 3)을
   그 주소에 요구되는 수준(링 0)과 비교한다. 링 3은 허용되지
   *않는다*. 그래서 읽기는 결코 일어나지 않는다.
4. **CPU가 폴트를 일으킨다.** 바이트를 반환하는 대신 하드웨어는
   트랩한다: 특권 수준을 링 0으로 전환하고 [[kernel]]의 폴트
   처리기로 점프한다 — 위 목록의 3번 전환 유형이다.
5. **이제 링 0에 있는 [[kernel]]이 프로그램의 운명을 결정한다.**
   그것은 사용자 모드 프로세스가 읽어서는 안 되는 주소를 읽으려
   했음을 본다. 기계를 멈추지는 않고, 그저 그 프로세스 하나만
   종료시킨다(리눅스에서는 `SIGSEGV`, "세그멘테이션 폴트" 신호를
   전달한다).
6. **시스템의 나머지는 건드려지지 않는다.** [[kernel]]의 메모리는
   결코 읽히지 않았고, 다른 프로그램들은 결코 방해받지 않았으며,
   기계는 계속 실행된다. 그 시도는 안전하게 실패했다.

여기서의 예시적인 경우는 *금지된* 분기다 — 프로그램은 그 선에
부딪혀 저지당했다. 이제 같은 형태로 *허용된* 분기를 대비시켜 보자.
그래야 이 메커니즘이 끝에서 끝까지 드러난다. 대신 프로그램이
**파일**에서 바이트 하나를 읽고 싶어 했다고 하자. 그것은 디스크를
직접 건드릴 수 없으므로(특권을 요구하는 하드웨어 연산), **시스템
콜**을 한다: "커널로 진입하기" 명령어를 실행하고(1번 전환 유형),
CPU는 링 0으로 전환하며, [[kernel]]은 프로그램을 대신해 디스크를
읽고, 그 바이트를 프로그램 *자신의* 메모리로 복사하고, 링 3으로
다시 전환하고, 돌아온다. 같은 경계, 같은 문 — 하지만 이번에는
프로그램이 선을 가로질러 도달하는 대신 승인된 진입점을 통해
*요청했으므로*, 폴트 대신 자신의 바이트를 얻는다.

이 두 분기가 이 개념 전체를 축소해 보여 준다: 사용자 모드로부터의
**직접적인** 특권 행동은 물리적으로 거부되고, 통제된 전환을 통해
**요청된 같은 행동**은 [[kernel]]에 의해 수행되어 돌려받는다. 그
선은 결코 지워지지 않는다 — 그것은 언제나 오직 그 문을 통해서만
넘어질 뿐이다.
