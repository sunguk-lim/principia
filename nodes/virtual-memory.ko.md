# 가상 메모리

## 요약

**가상 메모리(virtual memory)**는 모든 [[process]](프로세스)에게 자신만의
*사적이고 상상된 메모리 관(view)*을 부여하는 요령이다. 각 프로세스는
수십 개의 프로세스가 하나의 물리 RAM 뱅크를 공유하고 있음에도, 마치
자신이 0 근처에서 시작해 기계 전체를 소유한 것처럼 번호가 매겨진
깨끗하고 연속적인 메모리 주소 범위를 본다. 프로세스가 지칭하는 주소는
**가상 주소**다: RAM 안의 실제 위치가 아니라 그 프로세스의 사적인 착시
안의 이름표다. *모든* 메모리 접근마다 운영체제와 CPU 안의 전용
하드웨어 조각이 프로세스가 사용한 가상 주소를 실제 **물리 주소** — 그
바이트가 실제로 사는 RAM(즉 [[memory-hierarchy]]의 빠르고 희소한 상위
단) 안의 진짜 위치 — 로 **변환**한다. 각 프로세스가 자신만의 변환 맵을
지니기 때문에, 두 프로세스는 완전히 동일한 가상 주소를 써도 결코
충돌하지 않는다: 맵들이 그것들을 서로 다른 물리 바이트로 보낸다. 이
하나의 메커니즘은 동시에 두 가지를 사 준다 — **격리**(프로세스는
문자 그대로 다른 프로세스의 메모리를 지칭할 수 없으므로, 버그가
그 안에 갇힌다)와 **추상화**(프로그램은 실제 RAM의 어디에 놓일지
알지도 신경 쓰지도 않고 고정된 주소를 위해 작성되고 컴파일된다).

## 상세 설명

### 가상 메모리가 해결하는 문제

맨 하드웨어에서 시작하자. 기계는 하나의 물리 RAM 블록 — 가령 16GB —
을 가지고 있으며, 이는 [[memory-hierarchy]]의 빠르고 희소한 상위 영역이다:
디스크에 비하면 용량이 작지만, CPU가 자신이 다루고 있는 숫자를 직접
읽고 쓸 수 있는 유일한 장소다. 이제 [[process]]가 실행 중인 프로그램이며,
커널의 일에는 브라우저, 셸, 음악 재생기, 그리고 이백 개의 다른
프로세스처럼 *여러* 프로세스를 동시에 실행하는 것이 포함된다는 사실을
떠올리자. (하드웨어를 관리하고 프로세스를 만드는 특권을 가진 상주
프로그램인 커널은 [[process]]를 쌓아 올릴 때 이미 확립되었다.)

여기 위험이 있다. 프로세스는 메모리를 **주소** — "0x400000번
바이트"처럼 바이트 하나를 지칭하는 평범한 숫자 — 로 지칭한다. 만약
모든 프로세스가 원시 물리 RAM을 직접 지칭한다면, 두 프로세스는
필연적으로 *같은* 숫자를 고를 것이고, 두 번째 것이 첫 번째 것의
데이터를 덮어쓸 것이다. 더 나쁘게는, 버그가 있거나 악의적인 프로세스가
커널 자신의 데이터가 놓인 숫자에 써서 시스템 전체를 손상시킬 수도
있다. 하나의 공유된 실제 주소 풀만 있다면, 어떤 두 프로그램 사이에도
벽이 없다. [[process]] 노드는 각 프로세스가 다른 것들이 건드릴 수
없는 사적 메모리 영역을 받는다고 *약속*했다 — 가상 메모리는 그 약속을
실제로 이행하는 메커니즘이다.

### 발상: 각 프로세스에게 사적이고 가짜인 주소 공간을 주기

두 용어를 정확히 정의하자. 모든 것이 이 구분에 달려 있기 때문이다.

- **물리 주소**는 RAM 안의 실제 위치다 — 칩 안의 진짜 바이트다. 기계
  전체가 공유하는 이런 것은 정확히 하나의 집합만 존재한다.
- **가상 주소**는 *프로세스*가 사용하는 주소다. 이는 그 프로세스
  자신의 사적인 번호 체계 안의 숫자이며, RAM 안의 어떤 고정된
  자리에도 직접 대응하지 **않는다**.

가상 메모리의 요령은 이렇다: 각 프로세스는 자신만의 **주소 공간** —
관례적으로 0 근처에서 시작하는, 거대하고 사적이며 연속적인 가상
주소의 범위 — 를 부여받고, 사실상 "이것은 전부 네 것이다"라는
말을 듣는다. 프로세스는 마치 자신이 기계를 홀로 소유한 것처럼 이
가상 주소들을 읽고 쓴다. 프로세스는 실제 RAM 주소를 전혀 본 적이
없다.

주택 번호 매기기 비유가 이 착시를 구체적으로 만들어 준다. 각자
자신이 0부터 1000까지 번호가 매겨진 방을 가진 저택에 산다고 확신하는
200명의 세입자를 상상하라. 실제로는 그 건물에 100개의 물리적 방만
있다. 건물 관리자는 각 세입자마다 사적인 작은 조회표를 유지한다:
*이* 세입자의 "5호실"은 실제로는 물리적 37호실이고, *저* 세입자의
"5호실"은 실제로는 물리적 82호실이다. 세입자가 "내 5호실로
가겠다"고 말하면 관리자는 조용히 그 세입자의 조회표를 참고해
올바른 실제 방으로 안내한다. 어떤 세입자도 실제 방 번호를 알게
되지 않으며, "5호실"을 요청하는 두 세입자는 서로 다른 실제 방으로
보내진다 — 그래서 결코 충돌하지 않는다. 세입자는 프로세스이고,
"방 번호"는 가상 주소이며, 실제 방은 물리 RAM이고, 세입자별
조회표는 프로세스별 변환 맵이다.

### 가상 주소가 물리 주소가 되는 방법

이 착시는 **모든 접근마다 이루어지는 변환**에 의해 유지된다.
프로세스가 메모리를 건드릴 때마다 — 명령어를 실행하거나, 포인터를
따라가거나, 변수를 읽거나 — 지칭한 가상 주소는 RAM에 도달하기 전에
물리 주소로 바뀌어야 한다. 모든 접근마다 이를 소프트웨어로 하는
것은 절망적으로 느릴 것이므로, 이는 CPU 안의 전용 칩인 **메모리
관리 유닛(Memory Management Unit, MMU)**이 수행한다. 커널이 변환
맵을 만들고, MMU는 각 접근마다 하드웨어 속도로 조회를 수행한다.

이 맵은 어떻게 개별 바이트마다 하나씩의 항목을 저장하는 것을
피할까(그러면 메모리 자체만큼 큰 표가 필요할 것이다)? 이는
**페이지** 단위로 작동한다 — 보통 4096바이트(4KB)인 고정 크기
청크다. 가상 주소 공간과 물리 RAM 모두 페이지 크기의 청크로 잘려
있다. 이 맵은 각 *가상 페이지*마다 그것이 어느 *물리 페이지*에
놓이는지를 기록한다. 주어진 가상 주소는 **페이지 번호**(어느 4KB
청크인지)와 **오프셋**(그 청크 안의 얼마나 깊은 곳인지)으로
나뉜다. MMU는 오직 페이지 번호만 변환하고 — "가상 페이지 X는
물리 페이지 Y에 산다"를 조회하고 — 오프셋은 바꾸지 않은 채
그대로 넘긴다. 그래서 매핑은 바이트 단위가 아니라 페이지 단위로
이루어지며, 이는 맵을 작게 유지한다. (맵 자체는 커널이 프로세스별로
유지하는 계층화된 데이터 구조다 — 그 전체 구조와, 그것을 채우는
페이지당 일회성 설정 비용은 별도의 노드들의 주제다. 여기서는
*프로세스별 맵이 존재하며 MMU가 모든 접근마다 그것을 참고한다*는
것만으로 충분하다.)

### 이유, 첫 번째 — 격리

이제 첫 번째 보상, 그리고 이 설계가 작동하는 더 깊은 이유다. 각
[[process]]는 **자신만의** 변환 맵을 갖는다. 맵은 가상 주소에 의미를
부여하는 것이다. *여러분의* 맵이 없다면 숫자 0x400000은 아무 의미도
없다. 프로세스는 자기 자신의 공간 안의 가상 주소만을 지칭할 수 있고,
자신의 맵은 그것들을 오직 커널이 자신을 위해 골라 둔 물리 페이지로만
보낸다. *프로세스가 다른 프로세스의 물리 페이지를 지칭하도록 적어
둘 수 있는 가상 주소는 그냥 존재하지 않는다* — 다른 누군가의
메모리를 참조하는 어휘 자체가 그 주소 공간에는 존재하지 않는다.
그러므로 격리는 각 접근을 *확인해* 나쁜 것을 금지하는 경비원이
아니다. 그것은 구조적이다 — 나쁜 접근은 **이름 붙일 수 없다.**
자신의 주소 공간 전체에 마구 휘갈기며 폭주하는 프로세스는 오직
자기 자신만을 손상시킬 수 있다. 메모리 버그의 피해 범위는 정확히
프로세스 하나이며, 이는 정확히 [[process]] 노드가 보장했던
프로세스별 사생활이다.

### 이유, 두 번째 — 추상화

두 번째 보상은 프로그램 자신을 위한 것이다. 프로그램은 실행되기
훨씬 전에 다른 어떤 기계에서 미리 컴파일된다. 컴파일러는 코드에
고정된 주소를 구워 넣어야 한다 — "함수는 0x400000에서 시작한다",
"이 전역 변수는 0x600000에 산다." 하지만 컴파일 시점에는 그
프로그램이 결국 물리 RAM의 어디에 적재될지, 그 곁에서 무엇이
함께 실행되고 있을지, 심지어 그 물리적 자리가 비어 있을지조차
아무도 모른다. 가상 메모리는 이 문제를 녹여 없앤다: 프로그램은
언제나 사용 가능하고 언제나 같은 방식으로 배치되는 *가상* 주소에
대해 컴파일되며, 커널은 자신이 원하는 어느 곳에든 실제 페이지를
물리 RAM 안에 자유롭게 놓을 수 있다 — 맵이 그 배치를 감춘다.
모든 프로그램은 자신이 새롭고 비어 있으며 동일한 기계에 적재된
것처럼 가장할 수 있다.

이 추상화에는 또 다른 면이 있다. 가상 주소 공간은 그저 번호
매기기일 뿐이므로, 프로세스는 존재하는 물리 RAM보다 훨씬 *큰*
가상 공간 — 겨우 16GB RAM을 가진 기계에서도 64비트 기계에서는
약 128TB에 이르는 — 을 부여받을 수 있다. 그 공간의 대부분은
실제로 건드려지지 않으므로 어떤 실제 RAM도 그것을 뒷받침할
필요가 없다. 그리고 실제로 *사용되지만* RAM에 들어맞지 않는
부분은 디스크([[memory-hierarchy]]의 느리고 널찍한 바닥)에
치워 두었다가 접근될 때만 RAM으로 끌어올릴 수 있다. 주소 공간이
*가상*인 것은 정확히 그것이 자신을 뒷받침하는 물리 저장소에
얽매일 필요가 없게 하기 위해서다. 모든 프로세스가 진정으로
공유하는 것, 그리고 정말로 유한한 것은 물리적 뒷받침 — RAM
더하기 디스크 — 이다. 비록 각 프로세스의 사적인 가상 관은
거대하지만 말이다.

### 구체적 사례: 두 프로세스, 같은 주소, 충돌 없음

이 메커니즘을 실제로 촉발하는 가장 작은 예로 구체화해 보자 —
하나가 아니라 두 프로세스로, *요점*(충돌하지 않는 동일한 주소들)
전체가 보이게 한다. 퇴화된 단일 프로세스 예시는 정확히 볼 가치가
있는 것을 감출 것이다.

두 프로세스 A와 B를 실행하자. 각각은 가상 주소에 대해 컴파일되었고,
공교롭게도 **둘 다 자신의 코드를 위해 가상 주소 0x400000을
사용한다** — 둘 다 같은 방식으로 만들어졌고 각자 자신이 0 근처에서
시작한다고 생각하므로, 이는 완전히 평범한 충돌이다. 원시 물리
주소 지정 아래에서라면 이는 재앙일 것이다: 하나의 실제 RAM의
바이트 0x400000을 두 프로그램이 요구하는 셈이다.

가상 메모리 아래에서는 아무 일도 아니다. 추적해 보자:

1. 프로세스 A가 자신의 가상 주소 **0x400000**에서 명령어를
   실행한다. MMU는 **A의** 맵을 참고한다: 0x400000을 담고 있는
   A의 가상 페이지는 물리 페이지 **0x12000**(RAM 안의 실제
   자리)에 매핑된다. CPU는 그곳의 바이트를 읽는다.
2. 프로세스 B가 자신의 가상 주소 **0x400000** — *같은 숫자* —
   에서 명령어를 실행한다. MMU는 **B의** 맵을 참고한다: B의
   가상 페이지는 다른 실제 자리인 물리 페이지 **0x57000**에
   매핑된다. CPU는 그곳의 바이트를 읽는다.

같은 가상 주소, 둘 다 *0x400000*이지만, 서로 다른 물리 바이트,
*0x12000* 대 *0x57000*이다. A가 자신의 0x400000에 쓸 때는 오직
A의 맵과 A의 프레임 0x12000만이 관련된다. B의 0x400000은 여전히
건드려지지 않은 B 자신의 프레임 0x57000을 가리킨다. A는 심지어
0x57000을 *지칭조차* 할 수 없다 — 그 물리 페이지는 오직 A가
갖고 있지 않은 B의 맵을 통해서만 도달할 수 있다.

페이징이 작동하는 모습을 보기 위해 오프셋도 추적해 보자. A가
자신의 가상 주소 **0x400210**을 읽는다고 하자. 이를 나누면:
페이지 번호 0x400, 오프셋 0x210이다. MMU는 페이지를 변환하고 —
A의 가상 페이지 0x400 → 물리 페이지 0x12 — 오프셋 0x210은
바꾸지 않은 채 그대로 넘긴다. 인출되는 바이트는 물리 0x12210이다.
프로세스만 바꾸고 가상 주소는 그대로 유지하면: B의 0x400210은
물리 0x57210이 된다. 오프셋(페이지 안의 얼마나 깊은 곳인지)은
프로세스의 일이고, 페이지 번호(어느 실제 페이지인지)는 커널의
일이다 — 그리고 그 분할이 바로 하나의 작은 맵이 4KB 청크
전체를 한 번에 재배치할 수 있게 해 주는 것이다.

그러므로 같은 가상 이름표가 서로 다른 물리 바이트로 해석되는
것은 순전히 두 프로세스가 서로 다른 맵을 지니기 때문이다. 그것이
메커니즘 전부이며, 그로부터 두 가지 보상이 동시에 떨어져 나온다:
A와 B는 하나의 RAM 안에서 충돌 없이 공존하고(**격리**), 각각은
물리적으로 어디에 떨어지든 상관없이 의존할 수 있는 고정되고
편리한 주소를 위해 자유롭게 컴파일될 수 있었다(**추상화**).
