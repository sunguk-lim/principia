# 선행 기록 로깅(Write-Ahead Logging, WAL)

## 요약

**선행 기록 로깅(Write-Ahead Logging, WAL)**은 데이터베이스가 [[transaction]]의 **지속성(Durability)**을 실제로 구현하는 메커니즘이다. 지속성의 약속을 떠올려 보자: `COMMIT`이 반환되면 트랜잭션의 효과는 충돌에도 살아남아야 한다. 그 장애물은 [[writeback]]이 가르친 모든 것이다 — 트랜잭션이 어떤 행을 수정하면, 데이터베이스는 [[page-cache]]에 있는 *데이터 페이지*를 변경하고, 그 페이지를 **더티(dirty)**로 표시한 뒤 RAM 속도로 반환한다; 더티 페이지는 오직 백그라운드 [[writeback]]에 의해 **나중에**야 디스크로 플러시되며, 만약 그 전에 충돌이 일어나면 **영영** 플러시되지 않는다. 그래서 트랜잭션이 `COMMIT`되어 성공했다고 알려졌는데도, 데이터 페이지가 디스크에 도달하기 전에 충돌이 나면 **소실**될 수 있다. WAL은 하나의 규칙 — **선행 기록 불변식(write-ahead invariant)** — 으로 이 틈을 막는다: 데이터 페이지의 변경이 디스크로 가도록 *허용되기 전에*, **먼저 그 변경을 설명하는 레코드를 순차 로그에 추가**하고, `COMMIT` 시점에는 **그 로그를 `fsync`로 안정 저장소에 강제 기록하고 대기**한다 — 그런 다음에야 커밋 성공을 보고한다. 데이터 페이지 자체는 여전히 더티 상태로 남아 통상적인 [[writeback]]에 의해 느긋하게 기록된다; 커밋 시 강제되는 것은 오직 *로그*뿐이다. 이것이 저렴한 이유는 로그가 **순차적 추가(append)**이기 때문이다 — 하나의 연속된 [[block-layer]] 쓰기로 빠르다 — 반면 더티 데이터 페이지들은 디스크 여기저기에 **흩어져** 있어 그것들을 강제로 쓰면 느린 무작위 쓰기가 여러 번 발생한다. 충돌 후 재시작 시, 엔진은 **로그를 재생(replay)**한다: 데이터 페이지가 아직 플러시되지 않은 커밋된 변경은 **REDO**하고, 커밋되지 않은 변경은 **무시**하여, 마지막으로 커밋된 상태를 재구성한다.

## 상세 설명

### WAL이 메우는 틈 — 지속성 대 지연된 라이트백

[[transaction]]은 기준을 세운다: **지속성**은 `COMMIT`이 반환되면 트랜잭션의 쓰기가 충돌에도 살아남는다고 말한다. 왜냐하면 데이터베이스가 "먼저 안정 저장소에 쓰기를 강제했기" 때문이다. 그러나 *무엇이* 강제되고 *어떻게* 되는지는 정확히 [[writeback]]이 시급하게 만드는 질문이다. 트랜잭션이 어떤 행을 갱신할 때, 데이터베이스는 디스크 섹터에 쓰지 않는다; [[page-cache]] 안에서 그 행을 담고 있는 **데이터 페이지**를 수정한다. [[page-cache]]와 [[writeback]] 노드가 확립한 대로, 그 쓰기는 단지 캐시된 페이지를 **더티**(RAM에서 변경되었지만 아직 디스크와 일치하지 않는)로 표시할 뿐이며 몇 마이크로초 만에 반환된다. 그 페이지는 오직 **나중에** — 5~30초 타이머의 백그라운드 [[writeback]] 플러시에 의해, 메모리 압박에 의해, 또는 그 사이에 기계가 충돌하면 아예 — 디스크로 옮겨진다.

이제 이 타임라인 위에 지속성을 겹쳐 보면 문제는 극명해진다. 어떤 트랜잭션이 커밋되어 클라이언트가 "성공"을 통보받았는데, 그 트랜잭션이 더럽힌 두 데이터 페이지가 아직 [[page-cache]]에 남아 있고 플러시되지 않았다고 하자. **충돌.** 그 휘발성 더티 페이지들은 사라진다 — [[writeback]]이 경고한 바로 그 손실 — 그리고 재부팅하면 디스크는 *트랜잭션 이전*의 내용을 담고 있다. 커밋된 트랜잭션이 **사라져서**, 지속성이 깨진다. 순진한 해결책은 [[writeback]]이 이름 붙인 바로 그것이다: 커밋 시 모든 더티 데이터 페이지를 `fsync`하고 기다리는 것. 하지만 그것이 바로 너무 느린 방법이며, *왜* 그것이 너무 느린지가 아래에서 다룰 WAL의 핵심이다.

### 선행 기록 불변식 — 먼저 로그를 쓰고, 로그를 강제하고, 데이터는 나중에 플러시한다

WAL은 지속성을 순서가 엄격히 정해진 두 개의 별도 쓰기로 나눈다. 데이터 페이지와 나란히 **로그**를 유지한다: 하나하나가 한 가지 변경을 설명하는 작은 레코드들의 추가 전용(append-only) 시퀀스다 — "트랜잭션 T가 페이지 P의 행 R을 이전 값에서 새 값으로 설정했다." 이 기법 전체의 이름이 유래한 정의 규칙은 다음과 같다:

> **선행 기록 불변식: 데이터 페이지의 변경이 디스크에 도달하도록 허용되기 전에, 그 변경을 설명하는 로그 레코드가 이미 안정 저장소에 있어야 한다.** 로그는 페이지보다 *앞서* 나간다.

구체적으로, 커밋하는 트랜잭션은 순서대로 세 가지를 한다. (1) 각 행을 수정할 때마다, 로그의 인메모리 꼬리에 **로그 레코드를 추가**하고 [[page-cache]] 안의 해당 데이터 페이지를 더럽힌다 — 둘 다 아직 RAM에 있다. (2) `COMMIT` 시점에, **커밋 레코드**를 추가한 뒤 **로그를 `fsync`**한다 — [[writeback]]이 정의한 것과 같은 강제 블로킹 플러시를, 여기서는 *로그 파일*을 대상으로 수행한다: 이 레코드들이 물리적으로 디스크에 도달할 때까지 반환하지 않는다. (3) 그 `fsync`가 반환된 뒤에야 데이터베이스는 커밋 성공을 보고한다. 데이터 페이지는 강제되지 **않으며**, 통상적인 [[writeback]]이 처리할 때 — 몇 초 뒤, 또는 재생을 통한 충돌 이후 — 더티 상태로 남아 플러시된다. 이제 지속성은 전적으로 로그가 짊어진다: `COMMIT`이 반환되는 순간, 모든 변경의 *레코드*는 지속적이지만, 변경된 *페이지*는 아직 그렇지 않다.

### 왜 빠른가 — 여러 번의 무작위 쓰기 대신 한 번의 순차 쓰기

왜 로그는 강제하면서 데이터 페이지는 강제하지 않는가? 디스크가 쓰기 비용을 매기는 방식 때문이며, 이는 [[block-layer]]가 정확히 설명한다. [[block-layer]]는 파일의 논리 블록을 장치상의 **섹터** 범위로 변환하고, 그 요청들을 큐잉하고 병합하고 순서를 정한다; 그 핵심 교훈은 저장 장치에서 비싼 것은 **요청당 위치 잡기(per-request positioning)** — 회전식 디스크에서는 멀리 떨어진 섹터 사이의 탐색, 더 일반적으로는 *흩어진 요청마다* 지불하는 고정 비용 — 라는 것이다. **연속적인** 섹터의 연속은 하나의 저렴하고 병합 가능한 전송이지만, 같은 바이트 수라도 **멀리 떨어진** 섹터에 흩어져 있으면 여러 개의 별도의 느린 전송이 된다.

이 두 쓰기를 그 비용 모델에 대입해 보자:

- 트랜잭션이 건드리는 **데이터 페이지**는 **흩어져** 있다. 갱신된 두 행이 장치상 멀리 떨어진 섹터에 매핑되는 서로 다른 두 페이지에 있을 수 있다. 커밋 시 그것들을 강제로 쓰는 것은 **여러 번의 무작위 쓰기**다 — 정확히 [[block-layer]]가 느리다고 보여주는 접근 패턴이며, 헤드(또는 요청당 오버헤드)가 멀리 떨어진 위치 사이를 오간다.
- **로그**는 **하나의 순차 파일로, 그 끝에 추가만 하여 기록**된다. 모든 트랜잭션의 모든 커밋이 같은 커지는 꼬리에 레코드를 더하므로, 연속적인 로그 쓰기는 **인접한 섹터**를 때린다 — [[block-layer]]가 하나의 빠른 전송으로 병합하는 연속적인 경우다. 로그 꼬리에 대한 한 번의 `fsync`는 잘 국지화된 하나의 쓰기다.

그래서 WAL은 **커밋당 지속성 비용을 (흩어진 데이터 페이지들의) 여러 무작위 쓰기에서 (로그 추가라는) 한 번의 순차 쓰기로 전환한다.** 그것이 지속적인 커밋을 저렴하게 만드는 거래다: 커밋당 강제된 디스크 쓰기는 여전히 한 번 지불하지만, 그것은 저렴하고 연속적인 종류이며, 비싼 흩어진 쓰기들은 백그라운드 [[writeback]]으로 미뤄져, [[writeback]]이 설명하는 대로 그것들을 여유 있게 일괄 처리하고 재정렬할 수 있다.

### 충돌 복구 — 로그를 재생한다

데이터 페이지를 미루는 것이 안전한 이유는 오직 로그가 데이터베이스로 하여금 충돌 후 그것들을 **재구성**할 수 있게 해주기 때문이다. 재시작 시, 아무에게도 서비스를 제공하기 전에, 엔진은 마지막 체크포인트부터 **로그를 재생**한다:

- **REDO.** 로그에 **커밋 레코드**가 있는 트랜잭션의 모든 변경에 대해, 그 변경을 데이터 페이지에 다시 적용한다 — 디스크에서 (오래되었거나 변경 전인) 페이지를 [[page-cache]]로 읽어 들여 기록된 새 값을 그 안에 쓴다. 이것은 충돌 전에 데이터 페이지가 결코 플러시되지 않았던, 정확히 커밋된 변경들을 복구한다. 커밋 레코드는 클라이언트에게 "성공"이 통보되기 *전에* `fsync`되었으므로, 통보된 모든 커밋은 재생할 레코드를 디스크에 가지고 있다 — 지속성이 성립한다.
- **무시 / UNDO.** 로그에 커밋 레코드가 **없는** 트랜잭션(충돌 당시 아직 진행 중이었던)에 속한 변경은 적용하지 **않으며** — 만약 부분적으로 적용된 커밋되지 않은 변경이 이미 어떤 데이터 페이지로 새어 나갔다면, 기록된 이전 값을 사용해 그것을 **취소**한다. 이것은 충돌을 가로질러 [[transaction]]의 원자성을 강제한다: 커밋되지 않은 트랜잭션은 마치 `ROLLBACK`이 그랬던 것처럼 *아무런* 효과도 남기지 않는다.

재생 이후 [[page-cache]]는 정확히 마지막으로 커밋된 상태를 담게 되고, 통상적인 [[writeback]]이 결국 그 복구된 페이지들을 디스크로 플러시한다.

### 실전 사례 — 서로 다른 두 페이지의 두 행, 커밋, 충돌, 재생

두 개의 서로 다른 **데이터 페이지**에 있는 두 행을 갱신하는 트랜잭션 T를 보자:

```
BEGIN T
  W1:  page 5, row "A.balance":  500 → 400      (append log record L1)
  W2:  page 9, row "B.balance":  200 → 300      (append log record L2)
COMMIT T                                         (append commit record L3)
```

페이지 **5**와 **9**는 의도적으로 서로 다른 페이지이며, 디스크상으로는 멀리 떨어진 [[block-layer]] 섹터 — 예컨대 섹터 `40000`과 `93000` — 에 매핑되므로, 둘 다 플러시하면 **두 번의 무작위 쓰기**가 된다. 선행 기록 순서를 따라가 보자:

1. **W1.** 엔진은 로그 꼬리에 **L1** = "T: 페이지 5 행 A 500→400"을 추가하고 **페이지 5**를 [[page-cache]]에서 더럽힌다. 아직 디스크에는 아무것도 없다; 페이지 5는 더티 상태다.
2. **W2.** **L2** = "T: 페이지 9 행 B 200→300"을 추가하고 **페이지 9**를 더럽힌다. 여전히 디스크에는 아무것도 없다; 페이지 5와 9 모두 더티 상태다.
3. **COMMIT.** **L3** = "T committed"를 추가하고 **로그를 `fsync`한다.** 이제 L1, L2, L3는 로그 파일에 대한 **하나의 연속된 추가**(빠른 순차 [[block-layer]] 쓰기 하나)로 물리적으로 디스크에 있다. 이제서야 `COMMIT`이 클라이언트에게 "성공"을 반환한다. 결정적으로, **페이지 5와 9는 여전히 [[page-cache]]에서만 더티 상태다** — 섹터 40000이나 93000 어느 쪽으로도 아직 라이트백되지 않았다.
4. **충돌** — 클라이언트가 "성공"을 본 지 1초 후, 어떤 [[writeback]] 플러시도 일어나기 전에 정전이 발생한다. 휘발성 RAM이 지워진다: 더티 페이지 5와 9는 **사라진다.** 디스크에는 데이터 파일이 여전히 *이전* 잔액(A=500, B=200)을 담고 있다; 로그 파일은 L1, L2, L3를 담고 있다.

   WAL이 없다면 이것은 커밋 소실 참사다: T는 커밋되었지만 데이터 페이지가 결코 디스크에 도달하지 못했으므로, 잔액은 되돌아가고 `400 + 300`은 사라진다. **WAL이 있으면 로그가 이를 구한다.**

5. **재시작 — 재생.** 엔진은 로그를 읽어 **L3**(T가 커밋 레코드를 가짐)를 발견하고 T를 **REDO**한다: 디스크에서 페이지 5를 읽고(여전히 A=500을 보임), L1을 적용하여 → 캐시된 페이지에 A=400을 쓴다; 페이지 9를 읽고(여전히 B=200), L2를 적용하여 → B=300을 쓴다. 복구된 [[page-cache]]는 이제 A=400, B=300 — **커밋된** 상태 — 를 담고 있으며, **어느 데이터 페이지도 충돌 전에 디스크에 기록된 적이 없었다는 점에** 주목하라. 통상적인 [[writeback]]이 나중에 자기 페이스로 복구된 페이지 5와 9를 섹터 40000과 93000으로 플러시한다.

만약 충돌이 대신 W2와 `COMMIT`의 `fsync` *사이에* 일어났다면 — 그래서 로그가 L1, L2는 담고 있지만 **L3는 없다면** — 재생은 T에 대한 커밋 레코드를 찾지 못하고 두 변경 모두 **무시/UNDO**하여, 마치 T가 실행된 적 없는 것처럼 A=500, B=200으로 남긴다. 그래서 모든 충돌은 합법적인 [[transaction]] 결과로 귀결된다: 완전히 적용됨(커밋됨, REDONE) 또는 완전히 없음(커밋되지 않음, 무시됨), 결코 절반이 아니다.

이것은 한 예제의 세 층위를 하나로 묶는다: **구조**는 흩어진 데이터 페이지들 앞에 서 있는 로그(순차 레코드 시퀀스)이고; **알고리즘**은 *로그 추가 → 페이지 더럽히기 → 커밋 시 로그 fsync → 재시작 시 재생*이며; **기반**은 [[block-layer]]의 디스크로, 그곳에서 로그의 연속된 섹터는 커밋 `fsync`를 하나의 저렴한 쓰기로 만들고, 데이터 페이지의 멀리 떨어진 섹터는 느긋한 [[writeback]]에 맡겨진다.

## 선행 지식

- [[transaction]] — WAL은 이 노드의 **지속성**(커밋이 충돌에도 살아남음)을 구현하고 충돌을 가로질러 그 **원자성**(커밋된 것은 REDO, 커밋되지 않은 것은 무시/UNDO)을 강제하는 *메커니즘*이다; 실전 사례는 지속적으로 만들어진 100달러 송금 사례다.
- [[page-cache]] — 행 갱신은 더티 상태가 되어 디스크에 도달하기 전에 반환되는 캐시된 **데이터 페이지**에 대한 쓰기다; 이것이 WAL이 보호해야 하는 휘발성 상태이며, 복구 시 로그가 재생하는 대상 캐시다.
- [[writeback]] — WAL이 고치는 틈(더티 페이지가 나중에야 플러시되거나, 충돌 시 소실됨)을 확립하고, WAL이 *로그*를 향해 겨냥하는 **`fsync`-후-대기** 원시 연산을 제공한다; 흩어진 데이터 페이지는 통상적인 백그라운드 라이트백에 맡겨진다.
- [[block-layer]] — WAL을 정당화하는 순차-대-무작위 비용 모델을 제공한다: 로그 추가는 하나의 연속된(저렴한) 섹터 쓰기이고, 흩어진 데이터 페이지들은 여러 무작위(비싼) 쓰기이므로, 페이지 대신 로그를 강제하는 것이 빠른 선택이다.
